# 离职接收与异常处置

可靠接收以数据库事务提交可见为准。接收事务先取得全局管理锁，规范化业务事件去重，再按用户 ID 升序锁定全部相关映射和用户。Inbox、逐员工处置、最终禁用状态、认证代次、系统审计及旧代次清理意图原子提交；供应商成员查询不进入该事务。SDK 回调在事务返回之后才产生 SUCCESS。事务或审计失败全部回滚并返回 LATER，不能把进入内存队列计为接收成功。

当前迁移 V29–V33 保存独立人工状态、限制、认证代次、映射、证明、历史、回执及事件数据；V33 给逐员工记录增加内部游标和人工解决时间。事件和映射历史不随清理任务删除。相同作用域与业务 eventId 重投保留首次依据，传输 messageId 只用于回复当前投递。相同业务键但内容不同会标记冲突并隔离未完成项；原员工列表、摘要、已完成处置及已有停权不会被替换。

拒绝范围外企业/应用、损坏字段、未知事件和消息/员工数量超限时，记录固定 input_rejections 类别；网络分片超限也在进入解析前计数。日志和指标不含原始员工、企业或消息内容。内容冲突使用独立 CONFLICT 告警，即使全部员工项已完成、没有积压，也会提示人工核对。

V35 新增接收提交区间、原认证代次的不可变撤销依据，以及每次 AI 执行的停止证据。撤销依据与访问限制同事务写入；接收的 commit_before 来自该主库事务内的时钟，commit_after 只在成功提交后以独立事务补记。原事务回滚不产生提交后证据；补记失败保留 NULL，重投不把当前时间冒充原始提交。补映射的限制标记为延后处置，不计入首次已映射用户的 30 秒样本。

逐员工状态含义：

| 状态 | 含义与下一步 |
| --- | --- |
| OFFBOARDED | 已在同一事务写入持久访问限制与代次撤销。Redis 清理可能仍在重试，AI 本地停止另行观测。 |
| UNMAPPED | 缺少准确内部账号映射。已可靠保存，但不能计为停权成功。先核对准确员工 ID 和目标账号，再显式登记。 |
| REVIEW | 迟到事件、应急异常或内容冲突需要人工核对。有关受管账号保持访问限制；不得直接启用或删除映射绕过。 |
| FAILED | 原事件恢复尝试失败，保存固定错误类别和下次尝试时间。依赖恢复后用原事件重试。 |
| IGNORED | 明确支持的非离职通知不产生账号操作；事件列表可按 IGNORED 筛选，不自动建号或复职。 |

事件先到后补映射时，登记事务会检查该员工未解决记录，并在返回之前处理相关原事件、建立限制。事件过多时分批继续核对；未处理记录仍保留，后续复职不能绕过它们。内容冲突会拒绝补登记，不能任意选择客户端提供的一份事件覆盖来源依据。已经受限、存在未解决事件或正在复职核对的映射不可改绑或退出。

`POST /api/admin/identity/lifecycle/events/{id}/retry` 需要 `identity:lifecycle:manage`，只接收 `reason`、`requestId`；路径 id 为系统内部事件 ID。员工列表、来源或原始载荷字段均被拒绝。请求回执绑定操作者、操作、目标和规范化请求；相同请求重放前仍先检查当前权限。已完成员工项保持幂等，复职之后重试原已处置事件也不会再推进认证代次。

失败恢复每五秒检查一次，每轮至多四个原事件，每个事务最多五秒。恢复失败退避由五秒逐步增加到最多五分钟。内容冲突项转为人工核对，不自动反复尝试；清理作业有独立领取租约与退避。上述任务不依赖 Stream 接收开关，关闭订阅不会解除已有事实。

应急保障损坏时，自动离职入口仍限制命中的普通受管账号，并将其记录为 REVIEW / EMERGENCY_UNAVAILABLE；不能借最后管理员保护放行。普通管理入口继续拒绝削弱最后保障。通过独立本地应急流程修复资格后，再做成员核对与人工复职。

观测边界：数据库事件 `recordedAt` 是事务中记录的时间，用于列表与保守积压年龄；它不冒充精确提交时刻。可靠接收计数及最后接收时间在 `afterCommit` 发布。首次接收事务中明确完成 OFFBOARDED 的项才提供持久访问门禁耗时样本，因为限制与接收同事务可见；未匹配、冲突、REVIEW、回滚及缺失证据不生成停权成功样本。补映射或恢复的访问限制单独计数，不能用零值猜测原始接收至处置的耗时。

会话清理独立记录 PAGE / DONE / FAILED，完成表示领取的旧代次范围已处理；不会使用用户全量 logout，也不会撤销复职后新登录。接收、访问门禁、AI 本地停止和终态/费用收尾是不同事实，不能以其中一个替代其余结果。

进程内事务替身测试覆盖提交/回滚、重启后重投、旧事件重放、未映射补录及可控时钟的提交后计时。没有启动数据库、Redis、钉钉或前端服务，也没有将这些测试作为真实多实例三十秒目标的验收证明。

# 对象存储对账与孤儿清理运维

对账能力全部位于 kb-app：以桶列举为起点识别“桶中有、库中无引用”的孤儿对象，并只读地抽样检查“库中有引用、桶中缺失”的反方向异常。默认只报告，删除需要显式开启。kb-worker
的存储接口保持只读，不参与对账。

## 两类孤儿与存活引用

孤儿定义为“扫描前缀下的桶对象键减去存活引用”。按成因分两类，同一轮扫描同时覆盖：

- **上传侧孤儿**：上传先写对象、后提交数据库事务；事务失败时尽力补偿删除，补偿也失败（或进程在提交前崩溃）即产生无库痕迹的孤儿对象。这类对象在数据库中没有任何记录，只能从桶方向发现。
- **删除侧孤儿**：删除只做软删除（`kb_document.status='deleted'`），对象删除在事务提交后尽力执行，失败仅记
  WARN。这类残留行同样被存活谓词覆盖。

存活引用定义为 `kb_document_version` 连接 `kb_document`（`d.status <> 'deleted'`）的全部 `object_key`
，与文档状态（draft/in_review/published/archived）、空间是否归档、是否为当前版本均无关：它们仍可被下载、预览与引用，误删即数据丢失。

扫描按每页 1000 个键分页列举，每页一次 `IN` 比对；不在内存中保存全桶键集合或全库存活键集合。每轮开始先用一次 `EXISTS`
探测存活引用是否为空。

## 删除护栏与单飞

删除默认关闭（报告模式）。开启后，候选对象必须依次通过：

1. **前缀校验**：列举请求本身带扫描前缀，服务仍对返回键做前缀防御；前缀外对象只记 WARN 并跳过。
2. **宽限期**：`LastModified` 必须早于 `orphan-grace-seconds`（默认 1 小时）；`LastModified` 缺失的对象不作为候选。
3. **删除前复核**：以同一存活谓词复核，发现存活引用则跳过。

其余保证：

- 列举或数据库访问失败即中止本轮，不做任何删除；已识别的孤儿计数仍如实上报。
- 单个对象删除失败只记 WARN 并继续本轮其余删除；失败对象由下一轮自然重试，不建重试表。
- 单轮删除数量受 `max-deletes-per-cycle` 约束；候选键与日志键按上限保留，计数独立累加，不随候选规模放大内存。
- 存活引用整体为空而桶中存在孤儿时，按“疑似连接错误数据库”处理：只报告、拒绝删除、记高优先级 WARN。
- **单飞**：多实例部署下，对账从连接池取一条专用连接，整轮持有会话级 `pg_try_advisory_lock(741306012)`，`finally`
  显式解锁后归还。未获锁的实例跳过本轮（INFO 日志）。连接断开时锁随会话终止自动释放。整轮占用 1 条池连接（上限
  10），对账为低频轮询，可接受。

## 缺失检测

每轮按版本 ID 倒序取最近 `missing-check-max-per-cycle` 条（默认 100）存活引用，对每个对象键执行只读 HEAD：

- `NotFound` 计入缺失数并记 WARN。
- 其他异常（网络、权限、限流）计入检查失败数，与缺失分开。
- 不写库、不重建、不触发重解析，只回答“当前是否能看到这个对象”。

这是近端窗口抽样，不是全量巡检：旧对象的个例缺失可能不被命中；宽限期内的孤儿在下一轮才进入删除候选；对账结果不能作为数据一致性的证明。

## 配置清单

配置位于 kb-app `application.yml` 的 `kb.storage-reconciliation` 块：

| 键                             | 环境变量                                                    | 默认值          | 含义                  |
|-------------------------------|---------------------------------------------------------|--------------|---------------------|
| `interval-ms`                 | `KB_STORAGE_RECONCILIATION_INTERVAL_MS`                 | `3600000`    | 轮次间隔（fixedDelay，毫秒） |
| `initial-delay-ms`            | `KB_STORAGE_RECONCILIATION_INITIAL_DELAY_MS`            | `300000`     | 启动后首轮延迟（毫秒）         |
| `orphan-grace-seconds`        | `KB_STORAGE_ORPHAN_GRACE_SECONDS`                       | `3600`       | 孤儿保护窗口（秒）           |
| `prefix`                      | `KB_STORAGE_RECONCILIATION_PREFIX`                      | `documents/` | 扫描前缀，与上传对象键同源       |
| `delete-enabled`              | `KB_STORAGE_RECONCILIATION_DELETE_ENABLED`              | `false`      | 删除开关（默认报告模式）        |
| `max-deletes-per-cycle`       | `KB_STORAGE_RECONCILIATION_MAX_DELETES_PER_CYCLE`       | `500`        | 单轮删除上限              |
| `missing-check-enabled`       | `KB_STORAGE_RECONCILIATION_MISSING_CHECK_ENABLED`       | `true`       | 缺失检测开关              |
| `missing-check-max-per-cycle` | `KB_STORAGE_RECONCILIATION_MISSING_CHECK_MAX_PER_CYCLE` | `100`        | 缺失抽样上限              |

时间类字段非正数回填默认值；删除上限与缺失抽样上限为空回填默认值，显式 0 或负数表示该项关闭（删除上限为 0
时即使开启删除也不删除对象；缺失抽样上限为 0 时不执行检测）。`prefix` 为空时使用上传对象键同源常量。

kb-app 已配置 `spring.task.scheduling.pool.size: 2`，避免对账长轮次推迟既有 Embedding 就绪探测。

## 日志字段

- 每轮一条 INFO 汇总：`对账轮次完成: 扫描=N 孤儿=N 删除=N 删除失败=N 缺失=N 检查失败=N`。
- 孤儿键以 INFO 逐条打印 `孤儿对象: key=…`，每轮至多 100 条，超出部分只进计数。
- WARN：单个删除失败、前缀外对象、存活引用缺失、HEAD 检查失败、空存活引用拒绝删除（高优先级）；ERROR：列举/比对/复核/探测/抽样查询失败、无法获取连接或单飞锁；INFO：未获锁跳过本轮。
- 日志只含对象键、计数、固定文案与异常堆栈，不打印对象内容与凭据。

## 报告模式到删除模式的启用步骤

1. 给 kb-app 的 S3 凭据增加前缀内 `s3:ListBucket` 权限；删除模式复用既有 `s3:DeleteObject`
   ，不需要桶级管理权限。缺失该权限时对账每轮失败告警，上传、下载、检索等主业务不受影响。
2. 以默认配置（报告模式）部署并运行至少一个完整周期（默认首轮延迟 5 分钟、间隔 1 小时），人工核对日志中的孤儿清单与缺失抽样计数。
3. 确认清单符合预期后，设置 `KB_STORAGE_RECONCILIATION_DELETE_ENABLED=true`；建议初期保持较小的 `max-deletes-per-cycle`
   ，并观察后续轮次的删除数、删除失败数与孤儿数收敛情况。

## 回滚

- 退回报告模式：把 `KB_STORAGE_RECONCILIATION_DELETE_ENABLED` 恢复为 `false`，重启 kb-app 后即不再执行任何删除。
- 完全停止对账：把 `interval-ms` 调大，或撤销前缀内 `s3:ListBucket` 权限。
- 以上均无数据影响：对账不建表、不改库、不迁移数据。已删除的孤儿对象不可恢复，但孤儿对象本身已无存活引用。

## 已知噪声与边界

- **dev 种子噪声**：`db/dev/V3__dev_seed.sql` 的版本对象键为 `dev/1.md`…`dev/5.md`，不在 `documents/`
  前缀下且桶中不存在。缺失检测按存活引用抽样（不按前缀过滤），dev 环境会每轮把它们计为缺失，属预期噪声；生产无此类数据。
- **宽限期内孤儿被漏过本轮**属预期：对象超过宽限期后才进入候选，下一轮自然覆盖。
- **报告不等于一致**：缺失检测是近端抽样，孤儿判定有宽限期窗口。

## 验证范围

本能力的验证仅包含进程内单元测试与静态检查：对账服务、调度器、Mapper SQL 结构与 S3 列举/HEAD 映射均以 mock 驱动，不连接真实
PostgreSQL/ParadeDB、MinIO、Redis，不启动完整应用。

**未在真实桶/数据库上执行**：真实桶的列举与删除效果、缺失检测的真实 HEAD 行为、多实例单飞互斥，以及与生产凭据（前缀内
`s3:ListBucket`）的联调，都不在已完成的验证范围内。单元测试通过不等于真实环境已验证；启用删除前必须按上文的报告模式步骤在部署环境观察。

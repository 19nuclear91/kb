# 知识问题单运维说明

## 当前交付状态

领域、V37/V38、本域 Mapper、四项权限、问题读写/状态命令、最小候选、固定资料安全投影、双来源通知、普通/受理页面、网关及生产日志配置已实施，离线验证已完成；2026-11-14 已同步七份主规格并归档。接口合同见 [知识问题单 API](knowledge-gap-api.md)和[主规格](../openspec/specs/knowledge-gaps/spec.md)，发布顺序与止损见 [协调发布清单](knowledge-gap-rollout.md)，实际证据见 [归档验证记录](../openspec/changes/archive/2026-11-14-knowledge-gap-feedback-loop/verification.md)。未部署，不将离线结果或归档当作可上线证明。

本变更仅执行离线单测、代码/配置检查及构建。未连接数据库或执行迁移；外键、触发器、锁、SQL 计划和部署联调均未验证。离线结果不代表上线验收通过。

## 数据归属与保留

只有 `kb-app` 负责 Flyway；Worker 和 AI 不运行新迁移，不负责问题处理。

| 数据 | 归属与用途 |
| --- | --- |
| `kb_knowledge_gap` | 原提问者归属、首次明确分享的描述、当前状态及工作身份 |
| `kb_knowledge_gap_entry` | 同单共享说明、方案及退回/终结原因，历史不可修改 |
| `kb_knowledge_gap_event` | 不含正文的操作事实，每单结果版本唯一 |
| `kb_knowledge_gap_event_recipient` | 源事务记录的固定提醒意图，不代表已送达 |
| `kb_knowledge_gap_command` | 请求标识、规范化输入摘要及最小回执，不复制描述、原因或文档正文 |
| `kb_knowledge_gap_actor_guard` | 串行化同一提问者的新建容量检查，不缓存资格 |
| `kb_knowledge_gap_notification_projection` | 问题事件的独立派生进度，数据库时间租约及可接管游标 |
| `kb_user_notification` | 共享收件箱；新来源只增加 `gap_event_id`，既有身份、顺序和首次已读时间不回填 |

首期保留已分享记录，无正文编辑、删除、自动清理或终态重开入口。撤回仅停止处理，不等于删除或收回他人已读内容。问题访问范围是原提问者、当前仍有处理资格的负责人及独立获权受理人员；历史负责人不因曾经处理保留访问。

只保存 MANUAL/SEARCH/CONVERSATION 来源枚举，不保存搜索 ID、会话 ID、轮次 ID、模型回答或引用快照。删除原会话不会删除独立分享的问题，也不能通过问题恢复原会话。资料方案只关联固定版本身份，资料读取另行鉴权，不因问题资格取得文档权限。

## 升级前提

- 现有迁移基线为 V36；V37 建立问题核心表，V38 扩展通知。不得修改或反迁移 V1–V36。
- 全量实现完成后才可协调发布。新增权限目录与双来源通知结构不支持旧 app 混部；先排空旧 app，再由兼容 app 执行迁移。
- 既有 ROLE_ADMIN 的四项权限在 V37 首次升级时一次性绑定，空库走正式引导；重启或重复引导不能恢复管理方已撤销的绑定。
- 旧客户端不声明能力时只接收旧四种通知及其计数；新版列表/未读数均使用单值 `X-Kb-Notification-Contract: KNOWLEDGE_GAPS_V1`。app、gateway、web 须依次协调发布，不能仅有迁移就开放入口；本轮未实际部署。
- 不删除业务记录、权限绑定、旧通知或身份序列来实现回退；二进制回退目标必须仍认识新目录和双来源结构。

## 索引用途

| 索引 | 用途 |
| --- | --- |
| `idx_gap_reporter_page` | 本人问题按内部 ID 倒序分页 |
| `idx_gap_assignee_page` | 当前分派问题分页，只索引存在负责人的行 |
| `idx_gap_state_page` | 统一队列按状态及固定创建位置分页；无状态筛选时使用主键顺序 |
| `idx_gap_reporter_open` | 同一提问者非终态容量计数；配额不靠应用层预读，需与 actor_guard 锁配合 |
| entry 的 `(gap_id, position)` 唯一键 | 每单共享记录有界正序读取，避免无界历史加载 |
| event 的 `(gap_id, result_version)` 唯一键 | 每单操作历史与结果版本唯一，支持历史续页 |
| `idx_gap_event_position` | 有界反连接发现问题事件；不使用可能遗漏晚提交事件的全局高水位 |
| `idx_gap_notification_projection_due` | 仅扫描未完成的到期派生工作 |
| 原 `idx_user_notification_inbox/unread` | 共享收件箱统一位置和本人可见未读查询，不另建第二排序体系 |

全部读取应先按当前可见谓词过滤，再排序、LIMIT 或计数。索引声明及离线 SQL 检查不能证明真实查询性能，本变更不包含执行计划验证。

## 权限配置与处理人池

通过既有角色管理显式授予权限，再将角色分配给对应有效人员。首期建议将受理读取、分派、处理和关闭按职责配置，不依赖角色名自动放行。

1. 为受理人员的角色绑定 `knowledge:gap:read`，开放统一队列读取。
2. 需要分派时另行绑定 `knowledge:gap:assign`；需要带原因关闭时另行绑定 `knowledge:gap:close`。二者不隐含 read，也不允许代替提问者确认解决。
3. 为处理人员角色显式绑定 `knowledge:gap:handle`。处理人还必须启用、主部门有效、完成必需改密；仅管理员名、文档管理或启用账号不足以进入候选池。
4. 处理人员不必持有 read 或 `identity:user:read`。名称查询只经具体问题的候选 POST 入口提交；结果只有 userId 和显示标签，不加载完整人员、部门、角色、密级或外部身份目录。
5. 候选只是查询时事实；实际分派必须再核对合格性，变化返回 409。撤权或改派在下一次请求生效，既有通知和请求回执不延续访问。

问题可读不等于文档可读。方案关联必须是固定已发布版本，提交时双方当前可读；之后资料访问仍独立核验，不自动补 ACL、提升密级、替换最新版或复制正文。

### actor/action 可见性矩阵

下表要求当次有效身份；写入还要求非终态、匹配版本及具体动作状态。组合身份取权限并集，但功能资格不互相蕴含。

| 动作 | 本人提问者 | 当前合格负责人 | 独立获权受理人员 |
| --- | --- | --- | --- |
| 独立创建 | 任一有效用户可主动明确分享 | 同左 | 同左 |
| 问题详情/历史 | 可读本人单 | 仅当前分派且有 handle | 有 read 可读统一范围 |
| 统一队列 | 无隐含资格 | handle 不开放队列 | 必须有 read |
| 分派/改派/人员候选 | 另需 assign | 另需 assign | read + assign；单有 assign 不产生全局访问 |
| 共享说明 | 可追加本人单 | 可追加当前单 | 可访问且有 assign；单有 read 不可追加 |
| 退回受理/提交方案 | 本人身份本身不允许 | 必须当前分派且有 handle | 受理资格不能代处理 |
| 确认解决/仍未解决 | 只能确认当前待确认方案 | 非提问者不能代确认 | 不能代确认 |
| 撤回 | 本人明确带原因 | 不允许代撤回 | 不允许代撤回 |
| 带原因关闭 | 另需 close | 另需 close | 可访问且有 close |
| 关联文档 | 独立按本人文档权限读取 | 独立按本人文档权限读取 | read 不授予文档权限 |

终态可按剩余资格读取，不能追加、改派、重开或修改正文。旧负责人改派后不保留历史访问，除非仍以提问者或 read 身份获得访问。人员停用/失权保留原分派事实用于人工接管，不自动算作解决。

## 受理、接管与页面恢复

1. 普通人员从 `/knowledge-gaps` 读取本人单，合格 handle 人员可选择“分派给我”；统一受理从 `/admin/knowledge-gaps` 进入，必须独立 read。无资格、空范围和依赖故障分别处理，不将通知数量当作待办总数。
2. 受理人员按状态和服务端游标读取队列。需接管仅为受控提示；有 assign 时人工查询该单最小处理人池并分派，候选失效为 409，清空选择后重新核对，不自动补角色或读身份目录。
3. 改派使旧方案不可确认，但历史保留；只有提问者针对新的当前方案明确确认才解决。需要终结且无法继续确认时可由有 close 的可见人员带原因关闭，CLOSED 与 RESOLVED 不混淆。
4. 切单、隐藏、换号、撤权或强制改密清理描述/历史/方案/候选和未决绑定；恢复先核对身份。结果未知不等于失败，刷新不恢复或重发写入。退回后 404 不延续旧负责人访问，由当前合格受理人员核对。
5. 新通知列表和计数同头同契约；旧客户端不声明时只读旧四类/旧游标。点击问题只进入相同 gapId，重新检查资格和当前状态，不能从提醒恢复旧正文。明确已读不会执行分派、提交方案或本人确认。

这里只交付使用和排障流程，不新增外部 IM 推送、内部私有评论或文档内容断言测试；发布动作及当前状态见协调发布清单。

## 通知协议与排障

问题事件不写入协作事件表，notification 使用自己的问题来源 Mapper 和短事务，独立发现、租约、分批、退避与 DONE。现有调度入口每轮分别处理两类来源，一类失败不跳过另一类。详见 [站内通知](in-app-notifications.md) 的完整参数及指标说明。

- CREATED/RETURNED 固定当时 read 池，ASSIGNED 固定新负责人，SOLUTION_SUBMITTED 固定提问者，SOLUTION_REJECTED/RESOLVED/WITHDRAWN 固定当时负责人，CLOSED 固定提问者及当时负责人；全部排除操作者、去重，不追发给后来获权者。NOTE_ADDED 不提醒。
- 源意图不等于已生成、已读或已解决；按来源/eventId/recipientUserId 唯一去重，重试不重置创建顺序或首次已读时间。派生失败保留工作、不回滚已提交方案；源事件或回执保存失败属于源事务故障，不能混淆。
- 创建/退回提醒绑定当前队列事件，分派/拒绝绑定当前负责人及分派代次，待确认绑定当前方案；普通 note 增加版本不失效提醒。旧分派/旧方案不再充当待办，终态通知也须当前可读该单。
- 新能力头只控制类型集合，不是问题资格。缺省旧四类/旧游标继续可用；新列表与新计数必须一起声明，游标不能跨人或跨契约，未知/重复头为 400。旧前端看不到问题提醒，应由合格人员从问题入口核对，不能靠去掉头重试掩盖协议错误。
- 问题目标只有 kind/gapId，无正文、资料身份或外链；点击重新核对同一问题。资料不可读由详情独立隐藏，不从通知补授权。已读不执行确认，通知数量不是问题待办数量。

### 故障定位

1. 先重读本人或合格受理的问题状态，确认是否真正提交；不要因为没有提醒而重新分派、重提方案或代确认。
2. 检查源事件的固定意图与独立 projection 状态；无自身提醒、后来获权不补发或工作身份已失效都是正常边界。WAITING_SOURCE 安装对应解析器后按退避恢复；实例退出按租约接管，不手工删除 projection 或改 DONE。
3. `kb.notification.derivation.backlog` 一次汇总两类完整来源，尚未登记 projection 归入 pending，DONE 排除；最老年龄以源事件时刻为准。它统计事件，不是收件人或送达量。发现失败也不会天然显示零积压。
4. `failures{stage=backlog}` 增长时保留值只是上次可靠快照，启动初值也不是可靠零。检查依赖与聚合超时，不清零指标掩盖故障；发现/领取/分批失败按既有固定 stage 计数，无来源或人员标签。
5. 列表 503 且 `read.mismatch` 增长时检查同源 SQL 与 `GapNotificationTargets` 的授权和工作身份规则；不靠修改业务数据恢复。读取故障不能解释为空列表或无人待确认。

本节是协议与运维边界交付，不是实际部署或数据库恢复记录；本轮没有执行数据库、Redis、前后端联调或真实浏览器验证，也不以文档断言测试证明业务。

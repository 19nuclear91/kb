# AI 聊天观测配置与运维

新能力仅采集单轮和多轮聊天元数据。模型、Embedding、rerank 及第三方文档解析服务不由本变更接入。采集关闭时可查询已有保留数据，尚未首次启用时明确显示未采集；旧 Redis 列表及旧多轮记录不自动导入。

## 权限与部署

`ai:usage:read` 保护统计，`ai:audit:read` 保护事件列表和详情，两者互不蕴含，也不授予会话或文档正文读取权。新增迁移只向当时已有的 ROLE_ADMIN 一次性绑定，正式空库引导按目录授予；撤权后不会因重启或重复引导恢复。

新增 code 入库前须排空旧 app；不认识新 code 的版本不能混部或直接回退。本文件交付部署说明，当前开发验证不运行迁移或外部环境。

## 配置

app 与 AI 使用相同 `kb.ai.observability.enabled`（默认 false）、`secret`（启用至少 32 UTF-8 字节，生产拒绝开发示例密钥）。该配置独立于 `kb.conversation.enabled`。默认 signature-window-seconds=60、nonce-ttl-seconds=180、registration-window-seconds=300、timeout-seconds=5、retry-attempts=3、lease-seconds=180、renewal-ms=30000。

缺省关闭且没有密钥时，内部采集端点拒绝工作。只要显式配置非空密钥，即使停采也必须通过强度和生产环境检查；停采后继续保留原有效密钥，才能安全处理已有收尾。

app 的 retention-days 默认 180，cleanup-enabled 默认 true、cleanup-batch-size 默认 500。停用清理与停采独立；停采只阻止新登记，既有调用仍可安全收尾和结算。实例以 90 秒心跳租约报告配置，心跳先通过独立事务提交，配置冲突或区间同步失败不会撤销活实例声明。区间同步和清理取得同一策略互斥锁后再次核对配置；仍存活实例的采集开关或保留天数不一致时拒绝清理，切换配置需停流并等待旧实例租约退出。

有效范围为 retention-days=1..36500、cleanup-batch-size=1..5000、timeout-seconds=1..60、retry-attempts=1..5；签名窗口1..300秒，nonce期限至少两倍签名窗口且最多3600秒，登记意图窗口至少覆盖签名窗口且最多3600秒。租约30..3600秒，续期至少1000毫秒且严格小于半租约。两侧绑定后都会校验，非法值使初始化失败。密钥只通过服务端秘密配置注入，不能放入 VITE 配置、日志或公共文件。

仅已终结且 SETTLED 或确认 NOT_REQUIRED 的记录可以过期；保留起点取生成终结和结算确认较晚时刻。执行中、RESERVED、PENDING、REVIEW 继续保留，清理只删除本模块调用及事件，不删除会话、业务账本、Redis 配额和管理审计。

## 收尾与核查

实际用量 KNOWN、UNKNOWN、NOT_INVOKED 与结算状态分别展示。UNKNOWN 的实际 token 是 null；有可靠最终统计且为零才是 KNOWN 零值。单轮与多轮沿用各自的额度计算策略，额度不是模型实际 token，也不是货币费用。

生成端中断后，单轮观测租约恢复只关闭元数据并保留 INTERRUPTED/REVIEW，不自动重启模型或重新扣费。旧单轮 Redis 释放无法核对时保持 REVIEW。多轮使用原持久结算意图、去重和安全重试窗口，查询模块不扩展这些窗口。

单轮元数据提交超时或响应丢失时只重试固定载荷，生成与原 RELEASE 不随元数据重试重放。SETTLED 只表示原流程对这次固定额度意图返回确认，不证明整个 Redis 账本已经对账。单轮领取结果不确定而没有可靠租约关联时保持 REVIEW；多轮明确配额拒绝可确认无需结算，无法确认的领取同样保留核查。

单轮在实际领取配额前再次解析当前主体，并与登记绑定的用户和部门精确比较。主体变化、停用或失效会话导致的明确拒绝不会领取配额或调度模型，保留 NOT_INVOKED / NOT_REQUIRED 事实。生成 FINALIZED 确认后停止观测续期；原配额续期单独运行，并继续遵守原释放和收尾规则。在途续期遇到终态拒绝时，只有终态确认成功才能忽略该拒绝。

已终结的单轮 PENDING 如果经过一个观测租约期限仍无结算确认，维护任务将其转为 REVIEW，不更改生成结果或扣费。晚到的可信固定结算确认必须匹配原租约和额度，才能独立完成该结算；它不能修改原生成终态。

## 升级、停采和回退顺序

1. 备份观测策略及原角色权限绑定，关闭新采集和自动清理，停流并等待旧聊天收尾。排空所有旧 app 后才交付 V21，避免旧权限目录读取新 code。
2. 运维发布支持 V21、V22 与新权限目录的 app，由部署流程按既有 Flyway 管理迁移；本次开发未运行数据库迁移。V21 只对当时 ROLE_ADMIN 绑定两项权限一次；空库由引导授予全目录，已有角色缺权仅告警，不会修复已撤权。V22 新增历史清理界限表；首次采集前的空库界限为空，已有采集区间的升级库保守标记到迁移时刻，避免将无法证明完整的既往历史宣称为完整。
3. 发布相同协议的全部 AI 实例，配置匹配的独立密钥和受保护内部网络/TLS，继续关闭采集；再发布网关与前端。公共管理路由复用现有 app 转发，内部采集端点不能公开。
4. 停流期间统一启用两侧采集，等待旧实例90秒心跳退出和新配置一致后再恢复聊天流量，记录覆盖起点。不能混用不能采集的新旧 AI 承接流量后宣称覆盖完整。
5. 初期保持 cleanup-enabled=false；按部署方单独的发布验证流程核对真实迁移、数据和依赖行为后，再统一开启有界清理。本仓库本次只完成离线验证，不将外部联调列为待执行开发任务。
6. 停采时先停新流量、等待原请求尽量收尾，再统一关闭两侧新登记；保留 app/AI 的已有收尾、观测恢复及原多轮结算投递。查询仍可用，不删除表或伪造结算完成。停止清理只改 cleanup-enabled=false，不关闭原业务维护。
7. 兼容回退先停流、停采、停清理并完成可确认收尾。选择仍识别新权限目录、V21/V22 Flyway 历史、历史清理界限和固定收尾协议的兼容构建；不能直接混回完全不认识这些信息的旧包，也不要删除迁移历史或观测表来绕过校验。无法收尾的记录保留 INTERRUPTED/REVIEW，以后核查。权限调整使用当前授权机制，保留原审计，不自动恢复撤销绑定。

保留策略改变会关闭原采集区间并开启新策略区间，firstCoverage 不重置。缩短保留期可能删除原来仍在保留期内的完整记录，部署方应先停清理核对策略，再统一恢复。清理每批默认500、最多5000，删除前重新取调用锁并核对状态、anchor和实例配置，仅删除本模块事件与调用。

每批实际删除的调用起始时间和事件发生时间共同推进持久化清理界限，删除与界限更新在同一事务提交，失败向事务边界传播。界限只向后推进，延长保留期不会恢复已删除历史；用量和审计查询的起点不晚于该界限时，均显示历史可能不完整。此全局界限采取保守口径，不存储被删除明细或尝试补造历史。

## 指标与页面

app 注册无主体标签的 `kb.ai.observation.ingest_failures`（采集接口拒绝/失败）、`failures`（维护失败）、`cleaned`（删除调用数量）、`unresolved`（未解决调用数量）和 `oldest_age_seconds`（最老未解决记录年龄）。成功清理日志只包含固定类别及批次数量，失败日志不含异常、查询值或密钥。指标导出仍服从现有运维端点鉴权和暴露配置，本变更不公开 metrics 端点。

页面入口、筛选与 asOf 口径见 [管理页面说明](admin-ai-usage-web.md)，内部签名和公共 API 见 [协议说明](ai-usage-api.md)。同一次调用的多个事件不能相加当作调用数；保留期之外仍存在异常记录也不能证明历史覆盖完整。

## 验证边界

本变更只运行离线单元/架构、无连接 Mapper 映射、类型检查、静态构建和 OpenSpec 结构校验。真实迁移、SQL 聚合、数据库约束、锁与回滚、Redis 和跨事务清理竞态不在执行范围；不为本文件或其他说明文档编写内容断言测试。

# 离职同步的独立应急管理

首次部署保持 `kb.identity.lifecycle.dingtalk.enabled=false`。先为独立账号配置有效主部门、本地密码及显式管理权限，完成首次改密，再由候选本人使用本地密码登录并登记。开发登录、SSO 登录和他人代输密码不能作为登记证明。

所需权限为角色目录/分配/写入、用户读取/写入/密码、部门读取/写入，以及 `identity:lifecycle:read`、`identity:lifecycle:manage`、`identity:lifecycle:restore`、`identity:emergency:manage`。服务端按用户跨角色的权限并集校验，不依据角色名称，不自动补回已撤销权限。应急身份不能同时纳入员工映射。

调用 `POST /api/admin/identity/lifecycle/emergency/verification` 提交本人的 `userId`、用户 `version` 和 `password`；轮换时同时提供旧登记的 `replaceUserId`、`replaceMappingVersion`。返回一次性证明、五分钟到期时间及当前登记版本（尚无登记为 -1）。再调用同路径的 `POST`，携带这些版本、`proof`、原因 `reason` 和独立 `requestId`。证明绑定当前会话、凭据、部门、角色权限及目标事实；任一变化须重新核验。只保存证明哈希，密码及原始证明不入日志和审计。

登记确认和轮换在同一事务先建立新的合格保障，再退役指定的旧登记。请求结果不明时保留原请求及版本，匹配重试返回首个回执；不能换目标或参数沿用请求标识。撤去操作权限后不能读取回执。

启用接收前必须通过应急就绪检查。停用账号、重置密码导致强制改密、使主部门失效、迁移部门、解绑角色或收缩权限，均不能削弱最后一个合格保障。关闭接收开关不会改变此规则，也不会解除已有员工限制或清理待处理记录。

合法退役采用先建后换：新候选证明本地可用并成功登记后，同事务撤销旧登记；随后才可按普通账号规则处理旧账号。最后一名登记没有单独退出通道。退出受管能力须先合法核对并处置所有限制、未完成事件及映射，不能以修改配置、删除数据或直接修改角色绕过保障。保留独立应急登记不妨碍关闭订阅。

运维负责保管本地凭据及应急账号可用性；系统的登记证明只能确认当次本地登录、再次密码校验与持久资格，不能证明密码一直被妥善保管。不要把应急密码放入部署配置或共享说明。

所有涉及资格、映射和身份事实的写入采用固定管理事务锁，再取得映射行锁、最后按内部用户 ID 升序取得用户行锁；无映射时的插入竞争也在管理锁内串行化。部门和角色写入同样先取得管理锁。供应商网络调用不在这些锁内进行。内存状态交错测试检查领域决策，不作为真实数据库并发验收结论。

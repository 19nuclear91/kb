# Design

## Context

动机见 proposal.md，行为以本变更三份规格为准。前置审核变更提供版本发布证据、`COMMENT_TARGET` 访问目的、无正文协作事件及覆盖起点；通知变更提供事件消费、本人通知和目标解析扩展点。两者必须实施并同步后再应用本变更，特别是共享 `space-authorization`，不能直接以本增量替换未经审核变更更新的主规格。

现有 `PermissionScope` 与 ACL 表已预留 comment，但 `SpaceAclService` 和文档例外写入口拒绝授予；需要启用业务执行和授权两端，不能只开放下拉框。既有固定版本访问、收藏和会话实现可复用身份门禁、精确 ID、当前权限与有界游标；现有评论模块、表和接口均不存在。

## Goals / Non-Goals

**Goals:** 固定版本上的轻量讨论；正文、幂等墓碑与最小业务事实分别管理；通知和报表只读可信事实，不接管创建事务。

**Non-Goals:** 不改变发布策略，不对未发布版本提供讨论；不做自动内容识别、管理员代删、修改／恢复评论、富文本、附件、深层线程、知识索引或新的用户目录。

## Decisions

### D1. 新模块与固定版本数据模型

在 `kb-app/comment` 新增 controller/service/model/mapper。`kb_document_comment` 使用单调内部 ID 和对外 UUID comment_id，保存 doc_id、version_id、root_id（根为 null）、author_user_id、纯文本 body、created_at、deleted_at。文档／版本使用复合归属约束，回复的根也必须同文档版本；SQL 和服务双重拒绝回复的回复，不能只靠客户端约束。

正文上限与合法 Unicode 规则在入口统一校验，数据库长度及正文／删除状态约束作为最后防线。根列表索引 `(doc_id, version_id, id DESC)`，回复索引 `(root_id, id ASC)`；不复制文档标题、文件名或正文，亦不因新版发布迁移评论。

替代方案：绑定文档而非版本会令旧意见漂移；绑定 chunkId 会因重解析失效，本期均不采用。作者投影只提供当前讨论所需的内部身份和显示标签，不返回用户名、部门、密级、角色或外部绑定；通过受限服务批量解析标签，不能从前端查询全局目录。

### D2. 访问目的与独立 comment 范围

每次读取先使用 document/service 的 `COMMENT_TARGET`：要求当前 view、密级、空间未归档、文档未删除，且版本有 PUBLISHED 或 OBSERVED_CURRENT 证据。LEGACY_COMPAT 单独不足，indexed 及审核参与身份也不足。实际历史发布时间未知不妨碍已观察当前版本评论，但不能补造过去发布事件。

创建另用当前主体解析 comment 范围，空间与文档例外取并集。comment 不暗含 view；空间 review 保留、文档 review 仍拒绝。列表响应提供当次 canCreate 及每项 isOwn/canDelete；这些是 UI 提示而非后续授权凭证。读取不会预取审核意见或把审核通过视为意见公开。

替代方案：复用 edit 或 manage 会扩大写入主体，靠父文档 view 则会开放待审版本，均不采用。

### D3. 创建、幂等与回复竞争

新增 `kb_comment_command` 保存操作域、请求标识、操作者、目标版本、根节点、规范化正文摘要及 comment_id；唯一绑定采用项目现有操作域／标识模式。只保存摘要与最小回执，不存正文副本或完整原始请求，避免删除后从幂等记录恢复内容。

去首尾空白但不做隐式 Unicode 兼容折叠或静默截断；规范化后的正文参与摘要。合法 X-Request-Id 为 1–128 个非控制 code point；相同标识匹配仍重新检查当前有效主体和版本／comment 资格，随后返回原身份及 replayed。原评论已删时只返回 deleted 最小回执；不能执行第二次插入或重发事件。不同操作者／内容复用返回 409，不返回他人回执。

锁序为 command -> document（FOR SHARE，只锁文档行）-> root -> child（插入时外键对版本行取 KEY SHARE）-> event/receipt；版本发布证据写入后不可变，不对版本行显式加锁，与审核、Worker 发布“先文档后版本”的顺序一致。创建与删除都不反向获取 Embedding 控制或解析 task 锁。回复事务锁定根并确认未删；根删除也取得根锁，因此并发结果只能是回复先提交并保留、或根先删除而新回复被拒。搬迁、删除等既有文档事务与评论写入通过文档锁线性化；提交时重读实际空间与密级，不沿用页面快照。

匹配重放不重新套用“根必须未删”这一新建前置条件：已提交回复在根删除后仍合法，重放只返回原事实并执行当前读取／写资格检查。唯一键冲突使用 ON CONFLICT 后另一个语句读取，不能在数据库已中止的事务中继续查回执。

### D4. 本人删除、墓碑和正文清理

删除先验证当前会话、用户及主部门有效性和强制改密，再按完整路径与 author_user_id 找本人记录；不要求 view/comment，也不读取文档标题或其他评论正文。无目标或非本人同为 404，本人已删除返回 204。

首次删除同事务置 body=null、deleted_at 并写 COMMENT_DELETED；保留 comment_id、author、版本归属、根结构和创建回执，避免重试复活。根删除不级联他人回复，不再接受新回复；列表墓碑只保留定位、删除状态与必要结构，不返回原正文或旧作者标签快照。已存在回复仍可按版本资格读取，删除回复不影响其他项。

删除后通知目标解析不返回已删回复；根已删但回复仍在时，回复通知可定位合法回复及无正文根。源事件没有正文，因此不用破坏创建事实来完成删除。首期不自动清理这些最小事实；未来物理销毁、备份保留和治理删除需单独定义，不能承诺改写已送达副本或历史备份。

### D5. HTTP 与有界投影

所有端点沿用 `/api/documents/**`、R 封装（204 无正文）、严格参数及应用／网关 no-store。

| 方法与路径 | 输入／输出要点 |
| --- | --- |
| GET `/api/documents/{d}/versions/{v}/comments` | 仅 limit/cursor；根倒序，items/hasMore/nextCursor/canCreate |
| GET `.../comments/{root}/replies` | 仅 limit/cursor；回复正序，独立游标 |
| GET `.../comments/{c}` | 无参数；固定目标最小详情，用于回复通知定位；仍按版本权限读取 |
| POST `.../comments` | X-Request-Id；严格 `{body, parentId?}`，根 parentId 缺省，禁止其他字段 |
| DELETE `.../comments/{c}` | 无请求体／查询参数；本人幂等 204 |

创建正常返回 201，匹配重放 200，均提供精确 commentId、固定版本、创建时间、deleted、replayed；需要正文时通过受保护读取取得，不把正文固化进回执。列表项包含 commentId、parentId、固定版本、创建／删除状态、安全作者投影与未删正文，不嵌入回复全集。

游标按项目现有严格编码规则绑定查询种类、doc/version/root 和最后内部 ID，limit 默认 20、最大 100，SQL 只取 limit+1。不存在／归属不符／无 view 为 404，可读但无 comment 的创建为 403，合法同版本的深层或已删根为 409；格式问题 400，无法可靠鉴权或读写依赖故障 503。UUID、数字 ID 和 JSON 均严格验证，不接受身份、创建时间或删除状态覆盖。

### D6. 追加事实与通知接入

复用协作事实表，扩展固定事件类型 COMMENT_CREATED（仅根）、COMMENT_REPLIED、COMMENT_DELETED；必要字段是 comment_id、root_id、doc/version、actor、服务器时间及固定结构类型，无正文。创建／回复与对应事实、回执同事务，删除事实仅首次产生；业务唯一键按 kind + comment_id 去重。

回复同事务记录根作者为收件人，排除自身；根创建及删除不产生个人提醒。注册通知目标解析器，使用当前 COMMENT_TARGET 和回复未删事实，不在 notification Mapper 里直连 comment Mapper；提供可组合的集合式访问规则给通知列表及 count 共同使用。通知 projection 可从 WAITING_SOURCE 安全恢复，不更改原事件、已读状态或正文。通知消费者离线不影响源提交。

以全部新版评论生产者启用时为 COMMENT coverage 起点，无历史评论回填；根创建与回复创建按不同 kind 为报表提供计数，不能使用现存正文条数或投递条数代替。

### D7. 页面与授权管理接入

在 `kb-web` 文档详情的所选版本下挂载独立评论组件及 API/hooks；键包含 Session epoch、documentId/versionId，根及回复各自管理请求代次与游标。服务端未确认目标可评论时不发正文请求，不按 index_status 推断发布证据。

显式发表绑定不可变写意图；不确定结果保留匹配标识，用户改变正文后用新标识。成功后重新读取有界页，不乐观追加未经确认的评论。同一目标重读首页期间，继续显示上一次成功读取的讨论，但暂停发表、回复和匹配重试，直到服务端重新确认资格；这是有意取舍，避免每次发表后列表闪烁。重读得到 401/403/404 时立即清理，身份或目标变化立即清空，不沿用旧内容。本人删除成功立即清理所有本地正文副本与草稿，使用墓碑；收到资源 404 后清理正文，最多保留当前身份已知本人 commentId 的无正文删除动作，退出／切换／隐藏后也清除该动作。

ACL 管理在空间及文档面板增加 comment，空间保留 review，文档不展示 review。沿用资源上下文主体选择器及管理写意图，不添加新全局功能权限、不自动补授任何 ACL。

## Risks / Trade-offs

- [纯文本也可能被用户粘贴敏感材料] -> 按固定版本当前权限保护，明确不承诺自动语义识别；不把评论送往模型或索引。
- [保留墓碑令列表长期存在删除项] -> 明确无正文结构与有界分页，不暗删他人回复或让创建重试复活。
- [读取期间权限变化] -> 每请求重新授权、写入锁内核对与前端恢复清理；不承诺撤回已送达文本。
- [大讨论与作者标签查询放大] -> 独立回复分页、批量最小标签投影、限定索引和语句超时，不加载全线程／身份目录。
- [共享授权规格覆盖审核改动] -> 前置实施及同步检查；本增量完整保留审核后同名 requirement 的所有场景。

## Migration Plan

1. 确认审核和通知均已实施、验证并同步主规格，追加新迁移和必要约束／索引，不预占固定迁移编号或修改旧迁移。
2. 部署评论后端、事件类型与目标解析器，确认所有写入实例认识新协议后建立 COMMENT 覆盖起点；再开放授权管理和文档面板。已有 ACL 不自动加 comment，历史 indexed 版本不回填发布证据。
3. 旧版评论定位、根删除／回复状态分支、撤权后本人删除及派生重复／恢复采用 Mock 依赖和内存对象的独立单测；本变更不安排真实并发、数据库锁互斥或跨服务验收。
4. 回退先关闭前端入口与新建能力，保留新版本人删除路径、正文清理、墓碑及源事件；停止评论目标显示时通知安全隐藏或等待，不能删除历史事件／重放根创建来回退。

本变更验证仅限独立内存单测、无连接 Mapper 投影、架构边界、前端组件／状态单测、类型检查及静态构建；版本、权限、评论、通知等依赖使用 Mock／stub，不组装跨模块运行环境。不得启动完整应用，不运行集成测试、跨服务联调或浏览器端到端验收，不启动或连接数据库、Redis、对象存储、消息中间件或第三方 API，不使用 Testcontainers／内嵌服务替代。迁移任务只编写脚本，不实际执行；说明文档作为交付物，不对 README／Markdown／文案或 SQL 文本做断言。真实迁移、事务回滚、锁互斥、并发及生产环境保留为未验证限制，不列入本变更待办或完成前置条件，不以静态或替身检查宣称其已经通过。

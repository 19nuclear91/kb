# Design

## Context

动机与边界见 [proposal.md](proposal.md)。本次设计依据以下已有实现：

- `kb-app/.../auth/model/Permission.java` 定义固定权限目录，`IdentityManagementAuthorizer` 从持久化角色绑定解析资格；
  `IdentityService.resolvePrincipal` 校验用户、部门并提供当前密级。
- `kb_document.security_level` 是权威值；`DocumentMapper.xml` 依此过滤列表、详情与文件读取，`SearchMapper.xml` 按
  `kb_doc_chunk.security_level` 过滤检索。内容版本没有独立密级。
- `kb_document` 只有内容指针 `current_version_id` 和通用更新时间，没有密级版本号。
- `DocumentRelocationService` 已在同一事务锁定文档并同步全部分块的空间归属；搬迁会清理 ACL，本操作不需要这一步。
- `kb-worker/.../parse/ChunkPublisher.java` 先锁解析任务和版本/文档，再写分块；插入时从文档行读取当前空间和密级。
- `sys_identity_audit` 已有 JSON 前后摘要、原因、时间和 `(operation_scope, request_id)`
  唯一约束。现有成功审计接口不接收原因，新操作还需要比旧幂等判断更严格的请求绑定。
- 最新正式迁移为 V13；新建管理员角色会获得 `Permission.codes()` 全集，既有管理员角色不会由引导自动补齐缺失权限。

## Goals / Non-Goals

**Goals:**

- 将规则 A 落实到服务端真实身份、文档锁内状态和重试回执，避免只在控制器或客户端做校验。
- 使用同一个数据库事务保证文档、全部版本分块及审计共同提交；本次以代码审查与无外部依赖单元测试检查实现。
- 让客户端获得专用版本号和稳定回执，无须读取正文或依赖内容版本变化。

**Non-Goals:**

- 不重构现有用户密级、空间搬迁或通用审计的全部幂等逻辑；共用组件只作新增能力必需的兼容扩展。
- 不对身份、角色变更与所有在途请求引入全局串行化；在等待业务锁后重新读取身份事实，已完成授权后开始的在途处理沿用现有请求边界。
- 不增加逐内容版本定级，也不自动清空 ACL、修改归档状态或重新执行解析任务。

## Decisions

### 1. 专用权限与最小管理投影

在 `Permission` 中增加 `DOCUMENT_SECURITY_LEVEL_WRITE`，code 为 `document:security-level:write`
。控制器与服务共用服务端认证主体，服务层自己检查权限和启用主体，不能接受客户端提供 `actorUserId` 或 `clearance`。

该权限是跨空间的密级管理资格，不额外要求空间 manage 或正文 view。原密级与目标密级均须不高于当前主体密级；正文访问继续走原有
ACL、密级、状态过滤。查询接口只暴露 `documentId/securityLevel/securityVersion`，同样要求专用权限且文档密级在主体上限内。

复用用户密级权限会使两种管理能力无法分别授予；复用空间 edit/manage
会扩大普通空间管理员的能力；依赖普通详情接口又会把正文阅读资格变成管理操作的隐性前置条件，因此采用独立权限和独立投影。

### 2. 接口与输入契约

| 方法与路径                                                    | 输入                                                                      | 成功输出                                           |
|----------------------------------------------------------|-------------------------------------------------------------------------|------------------------------------------------|
| `GET /api/admin/documents/{documentId}/security-level`   | 正整数文档 ID                                                                | `documentId`、`securityLevel`、`securityVersion` |
| `PATCH /api/admin/documents/{documentId}/security-level` | `securityLevel`、`securityVersion`、`reason`；`requestId` 或 `X-Request-Id` | 前后密级和密级版本、文档 ID、规范化请求标识、首次事件时间、`replayed`      |

沿用项目现有响应包装及异常映射。无会话 `401`，无资格或密级越界 `403`，不存在/已删除 `404`，参数无效 `400`，版本过期、无实际变化或幂等冲突
`409`，事务持久化失败按既有服务端错误处理。

请求标识和原因去除首尾空白再校验，分别限制为 128 和 500 个字符；实现以 Unicode code point 计数，避免同一业务字符因 UTF-16
长度不同被误判。双来源标识规范化后必须相同；原始未知业务字段拒绝，特别是不接收空间、ACL、用户身份或其他文档元数据的变更。服务层再次执行关键校验，字典校验复用
`SecurityLevelDictionary`。

所有非 deleted 文档均可管理，包括没有分块的草稿、审核中、已发布、已归档文档和归档空间内文档；这延续管理与内容读取分离的现状。目标等于当前密级的非重放请求返回
`409`，避免没有实际变更却推进版本、写入成功事件。以上是本提案的具体默认行为；规则 A 为用户已确认决策。

### 3. 独立密级版本

新增 `kb_document.security_version BIGINT NOT NULL DEFAULT 0`，带非负约束；仅本调整操作在实际变更时递增。新上传文档使用数据库默认值，读取管理投影暴露该值；不要求向所有现有正文
DTO 扩散字段。

锁定文档后比较 `securityVersion`；更新仍带预期版本和未删除条件，受影响行数必须为 1。同步更新 `security_level`、
`security_version` 和更新时间。分块只同步密级，不增加密级版本列。

不用 `current_version_id`，因为它描述内容发布；不用 `updated_at`，因为其他元数据写入会造成无关冲突；不用单独的旧密级值，因为
A→B→A 不能识别过期请求。

### 4. 事务、锁顺序与发布一致性

新增 `document/service/DocumentSecurityLevelService` 和专用 Mapper、管理 DTO/控制器，沿用 `kb-app` 的 Spring 事务与
MyBatis。一次调整的逻辑顺序：

1. 验证会话和独立权限，校验请求结构、规范化请求标识和原因。
2. 开启事务，对操作域和请求标识取得 PostgreSQL 事务级 advisory lock，防止同一标识跨文档并发。
3. 重新检查当前资格，读取既有成功事件。事件绑定不同操作者、文档、目标、预期版本或原因时，返回不含历史内容的 `409`。
4. 按文档 ID 读取未删除文档并 `FOR UPDATE`；缺失返回 `404`。等待锁后重新解析当前主体、密级与权限，避免使用等待前的快照或
   MyBatis 一级缓存结果。
5. 非重放请求先检查目标字典，再校验当前文档与请求目标的密级上限，保证非法字典值返回 `400`
   。匹配重试额外检查首次前后密级上限，再从历史事件重建首次回执；此分支不比较当前密级版本，不产生写入。
6. 非重放请求检查预期密级版本与实际变化，更新文档；按 `doc_id` 更新全部版本的分块密级，零分块为合法结果。
7. 写入成功审计并构造回执；全部完成后提交，任一步异常整体回滚。

文档锁之后不再锁解析任务或内容版本，避免与 Worker 的「任务/版本 → 文档」顺序反转。调整和搬迁均先锁文档，且各自只修改自身负责的字段；两者的最终结果可共存。

Worker 先获得文档锁时，其发布完成后调整同步已提交分块；调整先获得锁时，Worker 之后从文档当前行取新密级。必须保持
`ChunkPublisher` 的 `INSERT ... SELECT d.security_level` 以及写分块前的同文档锁，不能改成使用解析任务开始时的密级快照。

### 5. 幂等绑定与审计复用

新增 `AuditScope.DOCUMENT_SECURITY_LEVEL_CHANGE`，目标类型为 `document`。请求标识只在此操作域内唯一，与用户密级调整、文档搬迁分离。

专用 Mapper 使用稳定 64 位摘要对 `scope + ':' + normalizedRequestId` 取得 `pg_advisory_xact_lock`
；所有新操作入口必须遵守同一协议。摘要碰撞只造成额外串行等待，真实匹配仍比较完整操作域和请求标识及请求字段。

审计保存内容：

- 现有列保存操作者、文档 ID、操作域、请求标识、`reason`、事件 ID 和时间。
- `before_state` 保存旧密级和旧密级版本。
- `after_state` 保存新密级、新密级版本及规范化请求绑定需要的字段。
- 首次回执的 `changedAt` 直接使用事件时间；重试从事件恢复相同回执，只将 `replayed` 改为 true。

给 `IdentityAuditService` 增加兼容的带原因成功写入入口，旧入口保留原行为。新操作在 advisory lock
保护下先精确判定重放后再插入，不依赖「唯一约束报错后在同一 PostgreSQL 事务继续查询」恢复并发冲突；异常直接回滚。使用结构化
JSON 序列化，不手拼字符串。

重放不会豁免资格、当前文档存在性或密级上限。文档已删除返回 `404`，权限撤销或当前/历史密级超出操作者上限返回 `403`
。文档之后发生其他合法调整时，在这些检查通过后返回原事件，不返回当前文档状态。这比仅按标识查到事件就返回当前值更准确，也不会泄露其他操作者的回执。

### 6. 读取生效边界

文档与分块在同一提交点改变密级，现有 `DocumentMapper.xml` 和 `SearchMapper.xml` 的过滤继续生效，不另建权限缓存。所有内容版本继承文档级密级，降密不替用户增加
ACL，空间归档仍使新读取不可见。

提交后才开始的新读取必须使用新密级。提交前已获取正文的下载或 AI 请求不在本事务的撤回范围内；不把元数据同步描述成已发送内容可撤销。若以后需要持续流式撤权，应另立能力处理。

## Risks / Trade-offs

- 全量分块同步持有文档行锁时间可能较长 → 使用已有 `doc_id` 相关索引，静态核对多版本文档的更新范围；不改成异步同步，以免升密后仍可搜到旧分块。本次不执行数据库执行计划或性能实测。
- 仅检查 controller 或使用旧身份快照会绕过规则 A → 服务层执行资格与密级校验，锁等待后刷新事实；单独覆盖停用、撤权、降密后的下一请求及重试。
- Mock 测试不能证明数据库锁和回滚语义 → 按用户要求移除集成测试及外部组件验证任务，仅用单元测试和静态检查验证业务分支、调用契约与事务边界，不声称已实测数据库并发、迁移、回滚或检索一致性。
- 新权限使旧版本应用的目录校验失败 → 发布与回退协调处理全部新权限绑定，不能直接启动旧二进制。
- 归档文档仍可管理可能被误认为降密恢复可见 → 回执只报告密级结果，读取仍执行原有状态和归档约束，并提供对应测试。
- 保留 ACL 意味着降密后部分已有授权主体开始满足密级条件 → 文档与验收场景明确这是调整的预期效果，完整审计原因及前后级别。

## Migration Plan

1. 实现前确认迁移序号仍可用，预计新增 `V14__document_security_level.sql`；只增加新迁移，不改 V1 至 V13 或 dev 种子。
2. 在迁移中添加密级版本列与约束，历史文档回填为 0；给当时已存在的 `ROLE_ADMIN` 一次性插入新权限绑定。无此角色时不创建角色，由正式引导负责。
3. 部署时使用包含新权限目录、接口和审计操作域的 `kb-app`，Worker
   沿用现有协议；静态核对写入仍从文档当前行读取密级。旧应用节点在新绑定存在时重启会触发未知权限校验，需要协调版本。本次任务不执行部署或运行外部组件。
4. 静态核对升级迁移的版本默认值、约束及一次性权限绑定；使用管理员引导单元测试覆盖新增权限和撤销后不自动补齐，不执行隔离数据库迁移验证。
5. 使用模拟依赖的服务单元测试与 MockMvc standalone 测试覆盖资格、规则 A、版本、请求绑定及回执；运行指定的无外部依赖测试和
   OpenSpec 严格校验。本次任务不包含集成测试或测试数据库、Redis 等环境准备。
6. 回退优先修复新版本或关闭新入口，不逆向恢复文档密级和审计。确需回退二进制时，先停止新请求、保存并移除所有角色上该新 code
   的绑定，再启动旧版；保留新增列、已生效密级与不可变审计。恢复新版本时按保存的明确授权恢复，不能假定 Flyway
   会重跑迁移，也不能由启动引导自动补齐。

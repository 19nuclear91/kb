## Purpose

为知识空间提供可逐步启用的版本审核，使解析完成、业务批准和内容发布各自可辨认；通过当前权限、固定版本和并发控制保护未发布材料，并让旧发布版本在新版本待审期间继续服务。

## ADDED Requirements

### Requirement: 空间发布策略必须显式配置且默认免审

系统 SHALL 提供空间审核策略读取与修改，默认 AUTO，另支持 REVIEW_REQUIRED；修改仅允许当前空间 manage 或 space:manage-all，要求版本前置条件与请求标识并留下无正文审计。策略读取不授予正文或审核资格。

#### Scenario: 默认空间及策略修改
- **WHEN** 新建空间未显式选择策略，或合格管理员基于当前空间版本启用审核
- **THEN** 前者使用 AUTO，后者仅改变之后创建版本的策略并推进空间版本

#### Scenario: 策略冲突或无管理资格
- **WHEN** 修改基于过期版本，或调用者没有当前管理资格
- **THEN** 分别返回 409 或 403，不修改策略或生成成功审计

### Requirement: 版本必须固定创建时发布策略及真实上传者

新版本 SHALL 在创建事务内固定其空间发布策略及服务端确认的上传者，所有者不能替代上传者。空间策略开关或文档搬迁 MUST NOT 改写既有版本策略；审核申请另保存本次送审者与送审空间。

#### Scenario: 开关变化时存在在途上传
- **WHEN** 版本已创建但尚未解析完成，之后空间从 AUTO 切为 REVIEW_REQUIRED 或反向切换
- **THEN** 已创建版本继续遵守原策略，新版本使用创建时的最新策略

#### Scenario: 为他人文档上传新版
- **WHEN** 用户 B 为所有者 A 的文档上传新版本
- **THEN** 上传者保存为 B，不以 A 代替候选版本参与者或后续送审通知收件人

### Requirement: 需审版本必须手动送审且保留审核轮次

REVIEW_REQUIRED 版本 SHALL 在解析成功后由当前有 edit 的用户手动送审，保存独立递增轮次；未解析、失败、存在活动审核或已发布版本不得再次送审。没有其他合格审核人时返回 409，不能降级自动发布。驳回或撤回后可基于最新事实重新送审，不覆盖旧轮次。

#### Scenario: 首次送审与重复点击
- **WHEN** 编辑者对已索引需审版本提交合法送审请求并发生匹配重试
- **THEN** 至多创建一轮 IN_REVIEW 申请，回执包含固定版本、审核轮次和并发版本

#### Scenario: 无审核人或解析失败
- **WHEN** 除上传者与送审者外无合格审核人，或版本未完成解析
- **THEN** 拒绝送审，保留版本与旧发布内容，不产生待审成功事件

#### Scenario: 驳回后再次送审
- **WHEN** 编辑者对已驳回版本再次明确送审且满足当前门禁
- **THEN** 创建新轮次，旧意见、决定和时间保持原样，旧轮次请求不能处理新轮次

### Requirement: 审核必须使用空间审核人池并禁止自审

任一当前启用且主部门有效、具有文档当前 view、当前空间 review 和足够密级的用户 SHALL 可处理该空间的活动审核。上传者及本轮送审者 MUST NOT 审批本版本；manage、space:manage-all、所有者或角色名称不能代替审核资格，文档例外 review 不作为资格来源。

#### Scenario: 审核人池中任一人处理
- **WHEN** 两名当前合格审核人先后处理同一轮次
- **THEN** 首个合法决定生效，后到的非匹配请求返回 409，不构成会签

#### Scenario: 自审与职责分离
- **WHEN** 上传者或送审者同时具有 review，或管理员只有 manage 而没有 view/review
- **THEN** 不能完成审批，也不能通过身份名称、管理兜底或委托送审绕过自审限制

#### Scenario: 读取后审核资格变化
- **WHEN** 待办显示后调用者失去 review、view、密级或有效主体状态
- **THEN** 下一次处理按最新事实拒绝，待办和旧回执不保留操作资格

### Requirement: 审核通过必须与合法发布原子完成

审批通过 SHALL 同一原子操作完成决定、发布证据及当前版本推进。仅允许目标版本比当前版本新、文档及空间未归档未删除、索引完整且向量身份匹配当前 ACTIVE 配置。维护、过期索引或旧版本请求 MUST 拒绝，不先保存通过再悄悄等待发布，不回退已发布指针。

#### Scenario: V2 待审而 V1 已发布
- **WHEN** V2 完成解析但尚未通过，之后合格审核人成功批准
- **THEN** 批准前普通搜索、文件与 RAG 继续使用 V1，批准事务提交后切换到 V2

#### Scenario: 迟到批准旧版本
- **WHEN** 文档已发布 V3，又收到 V2 的非匹配批准请求
- **THEN** 返回 409，不改写 V3 或产生 V2 已发布证据

#### Scenario: 维护或模型身份变化
- **WHEN** 系统处于 Embedding 维护，或候选索引由旧 profile 生成
- **THEN** 分别返回可识别的维护冲突或索引待刷新冲突，审核仍未通过，旧版本保持服务

### Requirement: 驳回和撤回必须保持旧发布内容

驳回 SHALL 要求合格审核人提供 1–2000 个 Unicode code point 的非空纯文本原因；撤回 SHALL 仅允许本轮送审者在仍有当前 edit 时处理未决定申请。两者只结束对应轮次，不删除原件、不修改旧发布版本、不将意见公开为评论。

#### Scenario: 驳回及意见查看
- **WHEN** 审核人驳回活动申请并给出合法原因
- **THEN** 本轮为 REJECTED，意见仅按候选版本的当前查看与参与资格读取，普通读者不能取得

#### Scenario: 撤回与批准竞争
- **WHEN** 本轮送审者撤回时审核人同时批准
- **THEN** 至多一个决定提交，另一方得到冲突；撤回成功不得同时留下本轮批准和发布效果

### Requirement: 未发布版本访问必须独立于父文档查看权

新建但从未发布的版本 SHALL 仅向其上传者、已记录送审者或合格审核人开放，且这些身份均必须另有当前 view 和足够密级。读取覆盖父文档元数据、版本列表、进度、预览、引用及文件；下载仍须独立 download。无任何可见版本的首版待审文档对普通读者统一 404，不返回隐藏版本计数。

#### Scenario: 普通读者猜测待审版本 ID
- **WHEN** 用户可读 V1，但直接请求未发布 V2 的列表项、进度、原件或引用
- **THEN** V2 不出现在普通列表，直接读取统一 404，不能因父文档 view 绕过门禁

#### Scenario: 仅有 edit 的上传者
- **WHEN** 用户有上传资格但没有当前 view
- **THEN** 保留上传受理和本人最小状态回执，不自动授予正文、文件名、私有意见或预览；edit 不替代 view

#### Scenario: 合格审核人无下载权
- **WHEN** 审核人可以查看候选版本但没有 download
- **THEN** 可按既有格式支持预览，下载仍拒绝，不返回对象存储直链

### Requirement: 审核上下文变化必须使旧决定失效

搬迁 SHALL 在同一业务事务内结束该文档活动审核为 CANCELLED，旧轮次不能在新空间审批；版本固定策略不改变，可在新空间重新送审。删除同时使活动审核失效并阻止迟到恢复。归档暂停读取、送审和审批但不自动批准，取消归档后按当前资格重新判定。

#### Scenario: 送审后搬迁
- **WHEN** 文档从 A 搬到 B 时仍存在 IN_REVIEW 轮次
- **THEN** 该轮次终结并保留无正文事实，B 的审核人不能沿用 A 的决定，原例外清除规则仍执行

#### Scenario: 归档或删除期间回调
- **WHEN** 审核页面保持打开而文档所在空间归档或文档被删除
- **THEN** 新审批拒绝，不能复活文档、恢复文件入口或覆盖当前指针

### Requirement: 候选索引过期必须显式刷新并重新送审

当前有 edit 的用户 SHALL 可为从未发布且索引身份已过期的候选版本显式申请刷新。刷新保留原件与固定策略，结束旧活动审核并开启新的索引执行周期；完成后需人工重新送审。此能力 MUST NOT 重解析已发布历史、伪造新 profile 标签或绕过维护暂停。

#### Scenario: 旧 profile 候选恢复发布路径
- **WHEN** 编辑者为旧 profile 候选申请刷新，随后解析索引完成
- **THEN** 候选使用合法当前配置并回到可送审状态，不复用原轮次批准或自动发布需审版本

#### Scenario: 已发布版本申请候选刷新
- **WHEN** 调用者尝试用候选刷新入口修改已有发布证据的版本
- **THEN** 返回冲突，不改变历史分块、引用或审核事实

### Requirement: 审核写入必须严格幂等且事件与状态一致

策略修改、送审、批准、驳回、撤回和候选刷新 SHALL 绑定操作域、操作者、目标、轮次、预期并发版本及规范化载荷和 X-Request-Id。标识为 1–128 个非控制 Unicode code point；匹配重试重新鉴权后返回首次回执，冲突为 409。状态、无正文成功事件及回执 MUST 同事务保存，失败不得留下部分成功。

#### Scenario: 同请求并发与载荷冲突
- **WHEN** 同一逻辑批准并发重试，或另一用户／另一原因复用标识
- **THEN** 前者至多一次决定与发布，后者 409，不返回原私有意见或重复事件

#### Scenario: 事实保存失败
- **WHEN** 审核状态变更后无法保存成功事件或回执
- **THEN** 整个状态变更回滚，不返回批准、驳回或送审已确认成功

### Requirement: 协作事实必须可派生且不依赖通知消费者

系统 SHALL 保存可去重的审核送审、批准、驳回、撤回、取消和发布事实，包含稳定事件身份、版本／轮次、服务端时间与必要参与者 ID，不含正文、文件名、审核意见或凭据。事实与业务同事务提交，通知派生与报表读取不得修改它们；通知服务缺失或暂时失败不撤销已提交业务。

#### Scenario: 审核先于通知功能上线
- **WHEN** 审核已提交而通知消费者尚不存在
- **THEN** 决定与事件仍保留，审核待办可直接查询，不向用户宣称已送达通知

#### Scenario: 事件重复消费
- **WHEN** 下游重新读取同一事件
- **THEN** 使用稳定身份识别重复，不能将一次审核计为多次或重新执行发布

### Requirement: 旧版本必须保留兼容边界而不得伪造发布历史

升级 SHALL 保留旧版本的明确兼容标记和原有访问行为；仅可将升级时实际当前发布指针对应版本标记为已观察发布，时间未知保持 null。旧非当前索引版本 MUST NOT 仅因 indexed 被认定曾发布、开放评论或补造历史事件。新版本一律使用新发布门禁；升级需排空旧写入实例。

#### Scenario: 旧非当前版本与旧引用
- **WHEN** 升级遇到 indexed 但没有可核验发布历史的旧非当前版本
- **THEN** 保持显式兼容访问，不伪造审批、发布时刻或评论资格，旧固定版本引用不被改指当前版本

#### Scenario: 新版本或旧程序写入
- **WHEN** 新版本缺少合法策略／参与者数据，或旧 app/Worker 尚未排空
- **THEN** 不允许以兼容标记放行新写入，部署不得声明可安全混部或直接回退

### Requirement: 审核查询必须有界并安全区分故障

审核入口 SHALL 沿用有效会话与强制改密门禁，提供本人版本状态及当前合格审核待办，有界游标 limit 默认 20、最大 100，先过滤权限再分页。未知／重复参数、非法 ID／JSON 或未知字段为 400，不存在或无资源资格统一 404，依赖故障为安全 503；所有响应 no-store，不输出正文到日志或遥测。

#### Scenario: 待办续页后撤权
- **WHEN** 审核人使用旧游标续页而资格已变
- **THEN** 只返回当次仍可处理内容，不泄露隐藏数量，游标不是审核凭据

#### Scenario: 读取依赖失败
- **WHEN** 当前权限、版本或审核事实无法可靠读取
- **THEN** 返回无敏感明细的 503，不伪装成无待办、免审或批准成功

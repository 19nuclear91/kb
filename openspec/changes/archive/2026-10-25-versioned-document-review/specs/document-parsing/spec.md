## MODIFIED Requirements

### Requirement: 解析元数据与分块发布必须原子且可重试

系统 SHALL 将解析版本的质量元数据、解析器版本和分块来源信息与索引结果关联保存；索引结果必须在同一原子操作中完成，重复处理同一文档版本 MUST 得到一个一致的最终结果。索引完成 MUST 不等于业务发布：AUTO 版本满足发布门禁时自动推进，REVIEW_REQUIRED 版本仅完成候选索引，批准后才发布。写入分块 MUST 与文档当前空间一致，不因搬迁并发保留旧空间过滤归属。

#### Scenario: 解析成功并发布

- **WHEN** 解析、切块和向量化均成功且任务租约有效
- **THEN** 系统保存解析元数据和全部分块来源信息，版本进入 indexed
- **AND** 只有满足固定发布策略与发布门禁的版本才可成为当前可检索版本

#### Scenario: 发布过程中发生失败

- **WHEN** 元数据或分块写入中任一步失败
- **THEN** 该版本不得呈现为已索引
- **AND** 重试可以清理不完整结果并重新发布索引结果
- **AND** 不产生重复的同版本分块

#### Scenario: 同一版本重复处理

- **WHEN** 同一文档版本因重试或任务重投被再次处理
- **THEN** 最终只保留一套与最新成功结果一致的分块和元数据
- **AND** 不覆盖更新版本的当前版本指针，不借重试绕过审核

#### Scenario: 发布与文档所属空间变更并发

- **WHEN** 同一文档的分块发布与其所属空间变更在时间上重叠
- **THEN** 两者完成后全部已索引分块都按文档当前所属空间参与权限过滤
- **AND** 不残留按原空间参与过滤的分块

#### Scenario: 需审版本解析完成
- **WHEN** REVIEW_REQUIRED 的 V2 完成合法索引而 V1 已发布
- **THEN** V2 等待手动送审，不推进当前版本，V1 仍按原权限参与两路检索

### Requirement: embedding 维护期间上传必须排队而非伪发布

系统 SHALL 在 embedding 未初始化或维护期间继续受理合法上传与新版本创建，但暂停普通解析领取和发布，也不允许审批切换当前版本。版本仍固定创建时空间发布策略。新文档在满足索引与业务发布条件前 MUST 不可检索；新版本 MUST 不替换旧当前版本。等待状态 MUST 可与真实解析失败及待审区分，不得仅因维护等待消耗尝试次数。

#### Scenario: 维护期间上传新版本

- **WHEN** 有编辑资格的用户在重建期间上传既有文档的新版本
- **THEN** 原件、版本和持久任务正常创建并固定策略，旧当前版本仍可按权限检索和读取，新任务等待维护结束

#### Scenario: 用户查询等待进度

- **WHEN** 用户按既有权限查询处于维护等待中的解析版本
- **THEN** 返回可识别的 embedding 维护等待原因，而不是模型故障、待审完成或虚假的已发布状态

#### Scenario: 维护期间批准
- **WHEN** 合格审核人在非 ACTIVE 状态尝试批准候选版本
- **THEN** 不保存通过决定或切换当前版本，明确提示维护冲突

### Requirement: 普通发布必须验证生成时的 profile 与代次

系统 MUST 使普通解析结果携带生成时固定的 profile 和有效执行代次；只有系统仍允许普通索引提交且身份兼容、租约有效时才原子保存分块及索引状态，是否切换当前版本另受固定审核策略控制。维护结束后新任务 SHALL 使用新 active profile。审批发布仍须验证候选的索引身份兼容，不能将旧向量补标为新 profile。此约束 MUST 不削弱幂等、删除防复活、空间及密级同步。

#### Scenario: 旧任务在新 profile 激活后返回

- **WHEN** 旧代次普通解析结果在维护完成后才返回
- **THEN** 结果不得提交、不得把旧向量标成新 profile，也不得覆盖当前版本

#### Scenario: 新任务与升密或搬迁并发

- **WHEN** 恢复后的普通解析使用新 profile，期间文档完成升密或搬迁
- **THEN** 新分块使用新 profile 以及文档提交时的空间和密级，原发布一致性约束保持成立

#### Scenario: 待审索引未纳入全库重建
- **WHEN** 待审版本仍保留旧 profile，而仅当前版本的全库重建已经完成
- **THEN** 不因重建成功推断该候选就绪；发布拒绝并要求显式刷新候选索引和重新送审

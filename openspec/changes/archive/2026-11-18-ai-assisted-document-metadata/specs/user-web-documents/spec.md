# Spec Delta

## ADDED Requirements

### Requirement: 编辑资料必须支持按当前发布版本逐项核对建议

界面 SHALL 在有编辑资格的文档详情表单中提供主动生成入口，标明实际来源版本，逐项并列展示当前草稿值、建议值及真实来源位置。采用动作只更新被选字段的本地草稿，可继续修订；保存前明确这是整文档资料。标签由原表单处理。无合适分类时保留用户选择。

#### Scenario: 从历史版本页面打开并只采用摘要
- **WHEN** 编辑者查看历史 V1，文档当前发布版本为 V3，用户基于 V3 生成并只采用摘要
- **THEN** 页面标示 V3，保留草稿中的标题、分类和标签，允许改写摘要后由用户明确保存。

#### Scenario: 建议返回时用户已继续手工编辑
- **WHEN** 用户等待期间手工改了标题，模型返回另一候选标题
- **THEN** 结果区对照当前草稿展示，原输入保持，直到用户主动采用对应字段。

#### Scenario: 来源缺少页码或分类没有匹配
- **WHEN** 合法建议只有结构块位置，或分类项明确无建议
- **THEN** 使用已有章节或块位置展示依据，不编造页码；分类草稿保持原值。

### Requirement: 整理不可用与运行状态必须分别可辨认

界面 SHALL 区分无发布版本、快照不可用、解析截断、完整输入超限、额度不足、服务故障及权限变化。等待中重复点击使用同一请求。显式取消与本地停止等待分开表达；响应丢失可核对原请求。收到取消确认后隔离其迟到结果，保留仍有资格的当前编辑者自行输入的草稿。

#### Scenario: 解析截断和输入超限
- **WHEN** 服务端分别报告快照截断或单次容量不足
- **THEN** 页面分别显示“解析时正文已截断”或“正文完整，但超过单次整理上限”，两种情况均可继续手工编辑。

#### Scenario: 取消响应丢失或已确认取消
- **WHEN** 取消请求的响应丢失，或已确认取消后旧响应才抵达
- **THEN** 前者显示待核对并允许查询原请求，后者停止等待并丢弃迟到建议，均不擅自重发生成。

#### Scenario: 切换身份、文档或丧失资格
- **WHEN** 用户退出、换号、切换文档或失去读取资格，先前的请求随后返回
- **THEN** 清除旧上下文的草稿、建议和定位信息，迟到响应无法恢复它们；建议文本不写入浏览器持久存储。

### Requirement: 采用建议的草稿必须带来源保存并能核对结果

界面 MUST 将采用的建议字段及其来源与本地草稿一起绑定，手工修订已采用字段仍使用辅助保存入口。服务端报告来源、资料或目录冲突时，应显示原因并要求重读后重新选择或生成。已确认保存与随后刷新失败分别展示；不自动降为普通手工提交。

#### Scenario: 来源更新或建议过期
- **WHEN** 用户修改了已采用的摘要，保存时服务端报告固定来源已更新或建议已失效
- **THEN** 页面不显示已保存，保留当前仍获授权的手工输入供核对，不以新版本号重发旧建议。

#### Scenario: 保存成功但响应丢失
- **WHEN** 用户选择核对或重试此前提交的辅助保存
- **THEN** 重试复用原保存标识及原载荷，确认成功后重新读取当前资料，整个过程不触发模型。

# Design

## Context

F-06 的来源是当前发布文件版本，写入目标是整文档资料。文件发布不推进 `metadataVersion`，只检查表单版本无法发现正文已经换版。现有资料写入已经处理权限、目录锁、幂等回执和同事务审计；已有快照读取能够核对解析任务 ID、执行代次及索引状态。模型适配器支持有界文本流，现有聊天领域分别维护会话、观测和额度结算。[资料写入](../../../../kb-app/src/main/java/com/zhishiku/kb/app/document/metadata/service/MetadataWriteService.java) · [版本快照读取](../../../../kb-app/src/main/resources/mapper/diff/DocumentDiffMapper.xml) · [模型协议](../../../../docs/chat-model-adapter.md)

## Goals / Non-Goals

同一份可核对的材料用于预算和发送。用户可从另一实例查询或取消本人请求，生成、结算和资料写入各有独立结果。首期只支持主动整理一份已发布文档；上传、审核、批量整理、旧快照回补和分章节摘要留在各自的后续范围。现有聊天报表维持 SINGLE/MULTI 的统计口径。

## Decisions

### 1. app 持有请求状态，AI 服务执行一次推理

沿用 gateway 指向 app 的 `/api/documents/**` 路由。以 `/api/documents/{id}/metadata-suggestions` 为集合，公开协议如下。所有响应均为 `no-store`，ID 沿用前端的精确整数表示。

| 请求 | 输入及结果 |
| --- | --- |
| POST 集合 | `X-Request-Id` 使用前端为本次点击生成的 UUID，体内传预期发布版本和资料版本。app 核实身份与实际文档后唯一登记；返回请求 ID 和当前状态，执行中为 202。原标识可用于首次响应丢失后的核对。 |
| GET 集合下的 `/{requestId}` | 原操作者重新鉴权，读取状态、固定原因、用量与结算状态。只有当前来源、资料、树版本仍匹配且结果有效时，成功响应才附建议。 |
| POST 集合下的 `/{requestId}/cancel` | 对同一请求幂等地尝试取消，返回已确认状态。已完成则返回完成事实。 |
| PUT 集合下的 `/{requestId}/metadata` | 接受独立的保存请求标识、原资料表单及 `adoptedFields`，进入共享资料写入事务。普通手工保存仍使用现有 PUT。 |

未登录、强制改密、资源不可见和不可编辑沿用已有门禁。首次创建时，无发布版本、来源或资料基线冲突以及标识绑定冲突返回 409。若部署方另设入口限流，其 HTTP 429 表示请求在受理前受到限制。

部门配额在受理后异步检查。首次创建运行中的请求返回 HTTP 202；额度不足时，后续 GET 返回 HTTP 200，附 `status=REJECTED` 和 `reasonCode=QUOTA_REJECTED`。快照、输入上限、模型或内部服务的执行错误也通过终态及固定原因表达。创建或查询接口本身无法处理请求时返回 503。尚无发布版本的编辑者可在表单中直接看到原因。

app 为每次请求保存原操作者及认证代次、当时部门、文档、空间、发布版本、资料版本、目录树版本、执行身份和期限。调用者与目标的绑定在同标识重试时先核对。成功后的**建议字段与块编号**作为单独的短期业务结果存储，建议默认自成功起 30 分钟，可配置；读取和首次采用均检查服务端过期时间。原文从快照按需读取。过期清除建议载荷，保留可核对的最小请求事实以及已成功保存的回执。幂等标识不能随短期结果一起释放；若后续清理账本，应保留去重标记或使用可拒绝过期标识的协议。

### 2. 受权材料与模型输入一次固定

app 在同一读取快照内固定发布指针、资料版本、目录树版本和匹配的解析执行周期，先检查头信息、大小与调用者资格，再有界读取按序的全部非空块、完整表格和允许推荐的本空间分类路径。目录逐页读取并核对树版本，配置上限须能区分正好装满和仍有下一页；超限时明确返回输入超限。目录为空仍可生成，分类项为无建议。首期不借助检索命中、文件名或聊天历史补写缺失内容。

AI 服务使用受认证的内部接口接收材料。系统指令与文档、目录数据分开编码，模型只能返回固定结构的三个字段及其块编号。原文中的指令只作为文档数据。系统从实际快照映射章节和页码，从候选 ID 映射分类路径；检查标题 1–512 个 Unicode 码点、摘要至多 2000 个码点且有实际内容、分类单选、每项来源属于本次输入。输出结束、结构和来源均确认后才整体交付。纯文本模型可按约定返回 JSON，首期无需引入新的供应商接口。

AI 服务把提示、完整材料和输出格式组装成不可变请求，计数与发送复用同一对象。设输入计数为 I、最大输出 O、预算余量 M，I + O + M 须同时满足模型窗口和配置的单次上限；内部预留为 I + O，M 作为容量余量。沿用显式预算模式：严格模式匹配本功能实际消息格式，估算模式使用显式窗口和余量，避免把估算当作供应商实际消耗。传输字节数、表格、块数及模型输出各有独立上限。服务地址、凭据由服务端注入，用户令牌、内部签名与追踪头止于内部边界。

### 3. 在持久调度意图处划分调用责任

1. app 登记请求，绑定起始会话，交给有界执行器。执行期间原登录凭据只在可信服务的短期内存中用于实时鉴权，进程重启仅恢复收尾。向客户端应答和内部执行分别管理。
2. AI 服务备好不可变输入和预算，取得绑定本请求的部门预留并向 app 确认。复用既有部门额度池、速率及并发限制；登记预留意图、额度操作和确认均使用同一唯一租约，解决“已预留、确认丢失”的窗口。额度不足时不登记调度意图。
3. 仅持有当前执行身份的 AI 处理器可向 app 申请一次发送许可。app 核对起始会话仍有效、版本及权限仍匹配、请求未取消、预留已确认，以原子状态转换登记调度意图。只有明确收到**首次取得许可**响应的处理器可发送。许可响应丢失、重复领取或进程失联时宁可中断；原请求绝不补发。模型 HTTP 禁止自动重试及重定向。
4. app 以原子条件更新裁决成功、失败、取消、执行超时。结束时再核验可读性和来源，有效成功结果与终态同事务写入，迟到正文不可交付。取消终态提交后，app 向 AI 服务地址发送带执行身份的停止通知。接收实例若正在处理该执行，便立即中止上游。执行实例也会定期向 app 核对状态。通知丢失或落到其他实例时，执行实例会在核对到取消后中止上游。状态查询有超时，整次执行受请求期限约束。网络断开仅意味着本地等待结束，最终事实以 app 为准。

内部服务签名覆盖用途、目标、执行身份、期限与载荷，校验时间和防重放。申请出站许可须重核用户资格；超时释放、结算和恢复仅能使用受限服务身份。外部入口不代理内部执行接口。跨网络边界无法原子证明供应商何时收到请求，所以以本地持久意图界定 UNKNOWN。

### 4. 配额依据与结算确认分别持久化

app 的整理账本分别记录生成终态、调度意图、实际输入与输出、内部预留、应扣额度、扣除依据与结算确认。复用 `UsageSettlement.calculate` 的三态计算，为 F-06 定义独立操作和幂等绑定，不创建聊天轮次或向现有聊天统计追加记录。生成取消或结构校验失败时，已有的可靠最终统计仍参与结算。[用量计算](../../../../kb-common/src/main/java/com/zhishiku/kb/common/conversation/UsageSettlement.java)

| 终结时掌握的事实 | 实际用量 | 内部额度 |
| --- | --- | --- |
| 尚无调度意图 | NOT_INVOKED，输入、输出均为零 | 释放原预留，应扣零 |
| 取得可靠最终累计统计 | KNOWN，保留原始输入和输出，包括明确零值 | 按两者之和结算。低于预留时释放差额，超过预留也记录实际数额 |
| 已登记调度意图且最终统计不可得 | UNKNOWN，输入、输出均为 null | 按预留结算，记录“按预留结算” |

生成可先终结。取消胜出后仍可接收同一执行的可靠用量直至有界收尾期限，但不交付其正文。额度收尾以当时已确认事实冻结唯一结算意图；迟到、冲突的统计留作核查，不能再次扣除。预留/释放/结算按固定租约核对 Redis 标记；只重试同一意图，结算成功但回执丢失时补确认。无法区分已扣和未扣、或去重证据已过期则进入待核查。无法可靠读取依赖时不展示已结算。审计保留最小运行事实，建议载荷、来源正文、名称和秘密不进入审计、日志与指标。

### 5. 采用建议与普通手工保存共用事务

独立的辅助保存 URL 让原接口继续严格校验五字段输入，避免把来源字段设为可随意省略的前置条件。app 提取现有 `MetadataWriteService` 的共用事务逻辑，使用独立操作域进行请求绑定。沿用既有目录、标签和文档的锁顺序，在同一写事务内核对建议请求及有效期、原文档和资料基线、当前发布指针、目录树版本、选中分类及版本权限，再整体写入最终表单。采用字段限于本次实际给出的三项，可在采纳后手改；标签继续按原契约校验。

已成功保存的匹配重放先按当前资格核对原目标和固定来源，再返回无正文原回执；它不依赖短期建议仍在。首次保存的冲突拒绝整个写入。Web 侧为建议、采用字段和原始手工草稿保留分离状态，明确采用才改变所选字段；修订已采用字段保留来源绑定。发生冲突时使旧建议不可提交，编辑者可重读、重新生成或明确舍弃受影响字段并继续手工整理。离页、切换身份或资源时清除敏感状态，服务端确认取消与浏览器中止等待分别显示。

## Risks / Trade-offs

- 长文件、很大的空间目录可能无法一次容纳。先告知具体原因并允许手工编辑，以真实命中频率评估后续分章需求。
- 只要目录树版本变化便使原建议失效，即使变化在另一分支。首期以一次重新生成换取路径与实际可选项的一致性。
- 短期保存结果可支持断连核对，但增加一份由正文派生的敏感数据。结果与账本分开存放，鉴权、限时访问及过期清理均在服务端执行；客户端只在当前页面内存中展示。
- 调度意图与真正的远程接收之间存在不确定窗口。禁止自动补发可防止重复消耗，代价是个别中断请求可能按预留结算；页面应同时展示未知用量和扣除依据。

## Migration Plan

1. 由 app 通过 Flyway 增量创建请求与结算事实、短期结果，以及对应唯一约束、过期和未结算扫描索引。新字段和新操作域与原手工编辑并存；无需迁移旧文档正文。
2. 默认关闭新生成，先发布支持收尾的 app 和 AI 服务，再部署表单。启用前配置模型、预算、部门额度及内部认证，用有完整快照的受控发布版本核对成功、取消、拒绝和结算。
3. 停用时停止接收新生成，保留查询、取消和未完成的结算收尾。先排空在途执行与待确认额度，再回退服务；保留必要的账本、回执和去重证据。真实解析、真实供应商用量及网络终止分别记录其实测范围。

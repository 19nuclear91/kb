# Design

## Context

动机与功能范围见 `proposal.md`，外部行为由本变更的两个增量规格约束。本次技术设计需要处理新增持久关系、权限一致性和多页面交互，因此保留独立设计文档。

已核对的现状：

- `kb-app` 的 document 模块已有列表、详情、版本和操作能力；`DocumentMapper.xml` 的 `documentAccessPredicate` 表达未归档空间中的空间授权或文档例外授权，查询另加密级和未删除条件。
- `PermissionService.principalOf` 支持请求内主体复用，失败态需要显式 `requireEnabled()` 才能区分主体失效与空权限；强制改密由现有 HTTP 拦截器执行。
- 现有普通文档列表按文档更新时间排序，搜索返回分块；二者都没有个人收藏字段。收藏应拥有独立创建顺序，且对搜索中的同文档分块去重读取状态。
- `kb-web` 通过 `Session`、`SessionProvider`、`useResource` 管理认证和页面恢复，通过 `lossless-json` 与字符串 ID 避免 long 精度损失。
- 网关已路由 `/api/documents/**`，CORS 已允许 PUT、DELETE。`/favorites` 需要同时接入 `App.tsx` 与 `navigation.ts` 的合法返回路径。
- 当前正式迁移至 V19；本变更交付新增迁移和查询代码，验证范围按用户要求限定为进程内单元测试与本地静态检查、编译构建。

## Goals / Non-Goals

**Goals:**

- 以数据库约束保证个人关系唯一，权限检查与列表截取在同一查询路径完成。
- 保持现有文档、搜索、文件和能力接口的契约，通过独立状态批次为页面增加收藏交互。
- 将重复同向操作、相反并发操作、网络结果不确定和页面迟到响应区分清楚。
- 使用已有运行时依赖与部署单元，以代码静态审查和隔离单元测试检查查询编排、参数、返回投影与前端状态处理。

**Non-Goals:**

- 版本或答案收藏、收藏夹分组、共享收藏、他人收藏查询、收藏热度推荐。
- 分类、标签、答案反馈，以及收藏改变搜索排名、AI 上下文或文档权限。
- 为此功能建立跨请求权限缓存、完整环境编排或全项目 CI 基础设施。
- 集成测试、端到端测试、依赖运行外部组件的验收，以及针对说明文档本身的测试。

## Decisions

### D1：个人关系留在现有 document 模块

新增 `DocumentFavoriteController`、`DocumentFavoriteService`、`DocumentFavoriteMapper` 和对应模型，分别放在现有 `document.web/service/mapper/model` 下。新 mapper XML 可使用完整命名空间引用既有文档授权片段，避免复制一套权限规则。

入口从 Sa-Token 取得用户 ID；服务通过 `principalOf(userId)`、`requireEnabled()`、`resolve(handle, view)` 得到本次范围。取消收藏也需要当前有效主体，但不解析文档 view。HTTP 强制改密拦截继续覆盖所有新路径。

备选：独立 favorites 业务模块会新增文档元数据与权限查询的跨模块接口，此规模下收益较小；直接调用 auth mapper 会绕开已有服务边界。采用现有 document 分层可复用既有授权与测试设施。

### D2：关系只保存用户、文档及创建元数据

新增迁移暂定 `V20__document_favorites.sql`；实施时若迁移序号已被占用，使用下一个未使用序号，不改既有迁移。

`kb_document_favorite` 字段：

| 字段 | 类型与约束 | 用途 |
|---|---|---|
| id | BIGSERIAL PRIMARY KEY | 固定创建位置，供倒序游标使用 |
| user_id | BIGINT NOT NULL，引用 sys_user | 收藏所属用户 |
| document_id | BIGINT NOT NULL，引用 kb_document | 稳定文档身份 |
| created_at | TIMESTAMPTZ NOT NULL，数据库赋值 | 对外 favoritedAt |

约束与索引：`UNIQUE(user_id, document_id)`；`(user_id, id DESC)` 支持列表；`document_id` 索引支持父文档最终硬删除时的关系清理。父用户或文档硬删除时关系级联清理；当前软删除、归档和权限变化保留关系，由读取过滤控制可见性。没有关系更新业务，重复收藏保持 id 和 created_at。

收藏状态不保存标题、版本、正文或空间副本。这样版本更新和搬迁无需同步收藏表，也不会保留可绕过撤权的旧摘要。

备选：将收藏 ID 数组保存在用户 JSON 或前端存储，不利于并发唯一性、跨设备和授权分页；绑定 versionId 会产生与“返回常用文档当前版本”不同的语义。

### D3：明确的目标状态接口与独立批量读取

| 接口 | 输入 | 成功 R.data |
|---|---|---|
| PUT `/api/documents/{documentId}/favorite` | 路径文档 ID；无正文与查询参数 | `{documentId, favorited: true}` |
| DELETE `/api/documents/{documentId}/favorite` | 路径文档 ID；无正文与查询参数 | `{documentId, favorited: false}` |
| POST `/api/documents/favorites/status` | `{documentIds: [整数...]}` | `{items: [{documentId, favorited}]}` |
| GET `/api/documents/favorites` | limit、cursor | `{items, hasMore, nextCursor}` |

成功统一 HTTP 200，沿用 `R.ok`。收藏列表使用独立 DTO，字段严格按规格，不直接序列化 `DocumentSummary` 的全部文件/版本字段。状态批次返回顺序按原输入 ID 重组，只返回已授权目标。

输入校验限定在新端点：批量 JSON 严格拒绝重复键、未知键、类型转换和多余顶层内容；文档 ID 是正 long，数组非空、去重前最多 100 且出现重复即拒绝。列表复用有界查询参数处理，对重复/未知参数显式报 400。PUT/DELETE 拒绝非空正文，防止调用方误以为提供的 userId 或 versionId 生效。

备选：向 `ChunkHit` 和所有文档 DTO 加收藏字段，会把用户偏好耦合进 AI 检索协议；独立批次只增加每个可见页面一次有界读取，并可保持旧消费者不变。`/api/documents/favorites` 是明确静态路径，其与 `/{documentId}` 的接口声明通过代码静态审查核对。

### D4：PUT 在授权查询上建立关系，DELETE 仅按本人键操作

PUT 使用 `INSERT ... SELECT` 从当前可查看文档集合建立关系，查询包含 `d.status <> 'deleted'`、密级和既有空间/例外授权片段；对 `(user_id, document_id)` 冲突采取保持 id/created_at 的幂等更新并返回关系。无授权源行统一 404，即使之前已经收藏也不例外。不可仅凭旧关系提前返回成功。

可采用 `ON CONFLICT ... DO UPDATE SET document_id = EXCLUDED.document_id RETURNING ...` 的无业务字段变化更新，避免“DO NOTHING 返回零行”被误判为不可见。所有写入是短事务，返回成功以事务提交为前提。

DELETE 只按服务端用户 ID 和请求文档 ID 删除，受影响行数为零也返回相同的 false；不为取消读取文档详情或检查 view。关联 FK 避免永久孤儿。软删除或权限变化与 PUT 重叠时，即使关系按之前已授权的语句快照落地，之后的所有读取仍按新事实过滤；收藏不会赋予访问权。

备选：读出 boolean 后反转无法安全重试；为个人偏好引入持久 requestId 账本会扩大简单状态设置的范围。同向重复操作天然幂等，相反并发操作遵循数据库实际执行结果，不对跨客户端点击时间提供严格顺序保证。

### D5：授权过滤先于分页，游标不缓存权限

收藏列表查询以当前用户关系连接 `kb_document d`，通过 LEFT JOIN 当前版本得到可为空的版本号；在 WHERE 中应用文档可见性和 `favorite.id < cursorId`，按 `favorite.id DESC` 取 `limit + 1`。额外一行只用于判断 hasMore，nextCursor 来自本页最后返回的关系。

使用 `QueryCursor` 的专用 kind `document-favorites`，过滤摘要绑定服务端当前 userId；不包含标题、权限快照或客户端用户字段。它只校验使用场景，真正的数据过滤仍来自当前会话。复用 `QueryCursor` 异常时在收藏入口映射为安全 400。

批量状态查询从指定 ID 的当前可见文档出发，LEFT JOIN 当前用户的收藏关系，一次取得 true/false。无当前 view 的目标省略，绝不通过“先取所有收藏再补标题”返回隐藏关系。请求内主体解析一次，批次不是 N 次详情调用。

备选：收藏关系先分页再逐条做 view 校验，会造成空页、遗漏和错误 hasMore；使用文档 updatedAt 排序，会因为发布新版本改变分页位置。

### D6：前端以页面级文档状态协调多个入口

在 `kb-web/src/favorites/` 新增收藏 DTO/API、页面级状态 hook 和共享按钮；新增 `pages/Favorites.tsx`。复用 `Session` 与现有组件，不增加状态管理依赖。

- 文档中心、详情和搜索在内容读取成功后采集不同 documentId（搜索使用 docId），每组最多 100 个；本页为空不请求状态。
- 状态记录按 documentId 索引，包含 known true/false、loading、unavailable、uncertain 及写入代次。按钮用同一页面状态源，同文档多结果同步更新并互斥提交。
- 初始批量读取失败只影响收藏交互；成功批次省略的目标意味着本次不可访问，通知父页面清理相关标题、片段及打开的引用/预览，而不是生成 false 状态。
- 写入成功更新对应文档状态；来自更早读取代次的结果不得覆盖。对仍在写入或 uncertain 的文档，不接受旧批次作为确认。
- 结果不确定时提供主动只读核对；核对成功只说明当前状态，后续写入由用户重新明确选择。取消后重新收藏是一次新操作，不复用旧请求回执。
- “我的收藏”列表本身即确认该页条目处于已收藏，不额外为每行读取状态；页内取消成功移除该项，失败时核对对应文档或刷新当前列表。
- 导航、路由和 `safeReturnPath` 同时增加 `/favorites`。进入详情继续沿用原版本与能力机制；搜索引用仍使用原三元组。
- JSON 请求数组用 `BigInt(positiveId(value))` 配合现有 `encodeJson` 输出整数，响应 documentId 保持精确字符串；禁止经 Number 转换。
- 所有状态仅存当前页面内存，绑定会话 epoch、资源结果代次和 AbortSignal；复用 `SessionProvider` 后台恢复时的身份重核行为。

备选：每个按钮独立维护状态会导致同文档的多个分块按钮相互矛盾；全局持久偏好缓存则容易在身份切换或撤权后复用旧结果。

### D7：新入口统一投影失败与响应头

新增仅作用于收藏控制器的异常投影，保留 400/401/403/404 等业务结果，将依赖异常映射为固定文案的 503，避免落入全局异常处理的原始堆栈日志。对收藏精确路径应用 no-store，覆盖成功、门禁和失败响应；不开启 mapper 参数日志。

身份门禁首先执行，主体失败不能被 `resolve` 的 denyAll 降级误报为空收藏。写入成功只说明本次数据库操作已提交，收藏状态和列表均不作为下一次访问凭据。

备选：仅在控制器成功返回时设置缓存头会漏掉拒绝响应；全局更改其他文档端点的错误行为会扩大兼容性影响。

### D8：验证限定为进程内单元测试与本地构建

1. 后端使用 mock/stub 替代身份、权限、mapper 和其他服务依赖，单独测试服务编排、DTO 序列化、游标、参数解析和错误投影。控制器与响应策略直接调用，使用内存请求/响应对象，不启动 Spring 应用上下文或 HTTP 服务。
2. 前端使用既有 Vitest/Testing Library，在模拟 DOM 中单独测试组件、hook 和页面逻辑；Session/API 使用替身，路由使用内存状态。覆盖大整数请求、去重批次、同文档状态、响应丢失、旧结果晚到、登录隔离和原版本引用。
3. 不创建或执行集成测试、端到端测试、数据库烟测、数据库并发/回滚测试、真实浏览器测试或应用联调；不连接数据源（含内嵌数据库），不运行 PostgreSQL、Redis、MinIO、Docker、模型等外部组件，也不保留依赖这些环境的待完成验收项。
4. 迁移、SQL、路由和配置交付通过代码静态审查处理；本变更不执行迁移或 EXPLAIN。替身测试只验证调用方的处理逻辑，不作为真实数据库约束、执行计划、事务竞争或完整权限链路的证明。
5. 文档编写任务交付必要的用户、接口、升级和回退说明；不为 README、Markdown、注释、文档内容、链接或示例增加测试，不执行说明中的外部调用示例，也不以文档内容作为业务测试断言。
6. 单元测试执行使用明确的类/文件白名单，避免无范围命令带入已有集成或外部环境测试；另执行跳过测试的 Maven 编译打包、前端类型检查及静态构建，并记录本次实际执行范围。

## Risks / Trade-offs

- [权限稀疏时需要扫描较多本人收藏] → 查询设计使用用户/创建顺序索引、SQL 内授权过滤和有界页面，代码静态审查确认这些约束，不引入过期权限缓存。
- [新增状态批次与内容查询存在时间差] → 以批次的最新不可访问结论清除对应旧内容；依赖故障与明确不可见分别处理。
- [重复 PUT 的无业务变化更新会产生数据库写入] → 保持操作为单行短事务，使用唯一约束和明确字段；若后续负载证明需要优化，保持时间、排序和并发契约不变。
- [权限恢复或取消后重建关系会改变一次游标遍历的可见集合] → 明确非冻结快照，刷新首页获取完整当前集合。
- [在途请求或其他标签页修改使状态再次变化] → 页面拒绝本地旧代次结果；主动核对只承诺当前事实，所有后续操作再次由服务端判定。
- [不可见收藏保留最小关系] → 不保存内容副本、不提供隐藏关系列表；取消可按本人关系执行，父实体最终硬删除级联清理。

## Migration Plan

本节是升级与回退说明的设计依据，仅交付相应脚本和说明，不要求本次任务执行部署、连接数据库或开展外部环境验收。

1. 实施时确认最新迁移序号并交付新增收藏表迁移；既有用户初始没有收藏，不从浏览器或日志推断历史偏好。
2. 升级说明记录由 kb-app 单点负责 Flyway 迁移、后端先于前端发布，以及四个端点复用既有网关路由的关系。旧前端仍可使用原文档接口。
3. 回退说明记录前端先于 kb-app 回退、新表与用户收藏保留、已应用 Flyway 历史不删除或篡改的约定；旧程序与更高迁移版本的兼容问题不得通过自动 repair 或移除迁移处理。

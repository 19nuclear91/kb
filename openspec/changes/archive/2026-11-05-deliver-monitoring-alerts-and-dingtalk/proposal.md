# Proposal

## Why

项目已提供四个应用单元的 Prometheus 指标与任务恢复机制，但缺少可独立部署的监控、告警规则和实际通知链路。现有数据库汇总指标还存在多副本重复观察、采样失败后保留旧值，以及 AI 观测未完成数量不能代表结算故障的问题，需要先补齐可信信号，再交付可验证的告警闭环。

## What Changes

- 在 `ops/monitoring` 交付独立的 Prometheus、Alertmanager、Grafana 和 Java 钉钉适配器部署配置，包含固定版本、持久化、抓取目标、配置检查与启动说明。
- 新增独立 Maven 模块 `kb-alert-notifier`，接收受服务凭据保护的 Alertmanager Webhook，生成中文聚合故障／恢复消息，通过加签调用钉钉群机器人；钉钉确认成功后才确认上游投递。
- 由 Alertmanager 统一负责分组、抑制、静默、重复提醒和失败重试；适配器单实例限流、限制并发和载荷，不另建持久消息队列，不承诺通知恰好一次。
- 在 Worker 与 app 补充采样可用性、最后成功时间、解析器本地就绪和独立的多轮结算指标；保留既有指标名及其含义，结算监控不依赖 AI 用量观测开关。
- 提供服务失联、解析积压／死信、索引阻塞、检索故障／延迟、模型异常、结算积压及通知链路异常的规则，以及服务总览、解析索引、检索 AI 三组面板。
- 以可信采样、同库汇总去重、最小流量、功能开关和维护状态控制误报；通知使用固定管理页面入口，继续由原页面执行登录和权限检查。
- 增加进程内指标行为测试、合成规则时间序列测试、钉钉内存传输替身测试和离线部署配置校验；不包含需启动前端或外部组件的集成测试、真实通知验收入口，以及文档内容断言测试。

首期只提供聚合状态通知，不将单个文档死信逐条发送至钉钉，不扩展站内通知，不改动现有业务恢复与扣费流程；不包含日志／追踪存储平台、基础设施 exporter 全家桶或监控高可用集群。

## Capabilities

### New Capabilities

- `operational-alerting`：独立监控部署、可信指标聚合、告警规则、降噪与恢复、可观测面板及运行验证。
- `dingtalk-alert-delivery`：受控接收聚合告警、中文安全投影、钉钉签名发送、确认／重试边界、单实例限流与投递指标。

### Modified Capabilities

- `metrics-export`：增加数据库采样的新鲜度契约、解析器本地就绪、独立多轮结算汇总及监控相关功能开关的低基数导出；既有导出与管理端口约束继续适用。

## Impact

- 根 `pom.xml` 增加模块；`kb-alert-notifier` 使用 Java 21 和当前 Spring Boot 基线，独立打包，不依赖业务数据库、Redis、用户会话或业务模块。
- Worker 的 `ParseTaskMetrics`、`EmbeddingMetrics` 与解析配置；app 的会话结算只读采样；AI 的会话开关导出。不新增公开业务 API，不改变授权、任务发布或结算状态迁移。
- 新增 `ops/monitoring`、配套运维说明、规则与适配器测试。已有四个应用的生产管理端口和绑定限制保持有效。
- 新增部署期凭据：适配器入站服务令牌、钉钉 access token／加签密钥、Grafana 管理员凭据，均通过受控文件注入，不提交真实值。
- 首期预计无需数据库迁移；结算只查询现有 `kb_conversation_settlement`。索引调整仅在实现阶段有实际查询证据时单独说明，不预先扩大本次数据模型范围。
- 验证范围限于进程内测试、编译打包与本地 CLI 静态检查；真实 SQL、部署网络和钉钉送达未由这些检查验证，不作为本变更的测试任务。运维文档编写与人工审阅保留。

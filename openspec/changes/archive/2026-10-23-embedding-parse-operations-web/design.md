# Design

## Context

动机见 [proposal.md](proposal.md)。本设计基于以下已观察到的实现：

- `kb-web` 使用 React、Ant Design 和既有 `SessionProvider`。`admin/access.tsx` 已按当前功能权限提供导航与守卫；`navigation.ts` 的站内返回白名单尚未包含本次两条路径。
- `admin/hooks.ts` 的 `useAdminWrite` 已处理请求绑定、显式重试和身份世代隔离，但固定调用身份管理写适配器。`identity-management-feedback` 明确排除向量及死信运维接口，因此不能直接扩大其 reasonCode 消费范围。
- Embedding 已有 profiles/status/run 读取及 START/RESUME 写入。`ready` 是查询侧与文档侧联合就绪布尔值；`localEmbedding` 只描述响应所在应用实例。全局 ACTIVE 后 runId 为空，不能据此补造上次作业。
- `ParseDeadLetterService` 目前只凭请求标识返回旧记录；其公共 required 校验将标识及原因先截为 256 个 UTF-16 code unit，外层 2000 限制实际无法发挥作用。列表每次查询都会写审计。
- 死信表已经保存 `replay_request_id`、`resolved_by`、`resolution_reason`，并具有请求标识唯一索引；现有 SQL 按任务、死信顺序取行锁，在同一事务中关闭死信、推进执行周期及记录任务事件。
- 仓库的文档密级修改已有 `pg_advisory_xact_lock(hashtextextended(...))` 与 READ_COMMITTED 事务范式，可供请求级串行化复用。
- 现行 `document-parsing` 使用“管理员角色”表述，Controller 实际按独立功能权限授权；本次增量将其明确为当前功能权限，与现有权限目录一致，不新增或自动授予权限。

## Goals / Non-Goals

**Goals:**

- 在既有管理生命周期内完成状态浏览、发起/恢复重建及单条死信重放，确保用户看到的状态与已确认回执一致。
- 使重放在多实例并发下绑定完整意图，复用现有存储字段与约束；保留合法既有 API 的路径和成功 JSON 结构。
- 将输入长度、查询时间边界、轮询、分页及不确定状态固定为可验收行为，避免实施阶段再猜测协议。

**Non-Goals:**

- 不改 Embedding/Worker 核心状态机、普通解析维护门禁、模型配置加载方式或权限目录。
- 验证仅使用隔离的进程内单元/组件测试、类型检查与静态构建；不新增或执行集成测试、真实数据库烟测、真实浏览器验收，也不启动完整应用、嵌入式数据库/缓存或外部服务。
- 文档更新只交付说明，不对 README、说明文档、注释、静态文本或真实文档样本新增内容/解析测试，不执行文档示例或人工联调验收。
- 页面功能范围以 proposal 和两项新能力规格为准，不新增历史清单或正文读取 API。

## Decisions

### 1. 独立页面复用现有权限与会话

新增 `admin/EmbeddingPage.tsx`、`admin/ParseDeadLettersPage.tsx`、`admin/operationsApi.ts` 及需要的类型/组件。修改 App 路由、管理导航和 safeReturnPath 的精确白名单。向量页面读取使用 `embedding:read`，死信页面读取使用 `parse:deadletter:read`；操作再检查对应写权限。功能权限读取失败时禁用页面；空间目录独立失败不阻止已具备资格的运维页面。

不使用 ROLE_ADMIN、角色 ID 或权限前缀推断资格。仅有写权限者不开放页面，但不改变后端独立写权限的原有语义。页面读取与请求绑定均以会话 epoch、权限事实和当前目标为隔离边界，复用后台恢复后的身份重新确认。

考虑过独立运维应用或统一运维大面板；两者会重复现有会话/守卫，且两项操作的查询频率、版本契约和分页方式不同，因此选择现有管理区的两个页面。

### 2. 运维 API 使用独立错误策略并复用写入状态机

运维适配器复用 `Session.send/json`、`decodeJson/encodeJson`、`positiveId`、精确版本转换和 WriteIntent 结构。对 `useAdminWrite` 增加可选的执行器参数，默认保持原身份管理执行器；运维执行器只按 HTTP 状态显示固定提示，不解析身份管理 reasonCode，也不展示任意服务器 message。

两个页面均复用 submitting/confirmed/uncertain/rejected 状态。网络异常、5xx、成功封装不可读或关键回执字段不匹配均作为结果不确定，保留精确意图和请求标识。原内容重试不会更新原 expectedEpoch/expectedVersion；刷新只更新页面事实。修改内容前需要完成或放弃旧核对，新提交生成新标识。

运维成功响应除 R 封装外还要验证关键身份：START 回执 profileId 与目标一致且 runId 为合法 UUID；RESUME 回执 runId 与目标一致；死信重放回执 ID 与目标一致且状态为 REPLAYED。不能仅凭 HTTP 200/202 或列表中条目消失确认本次成功。

采用可注入执行器保留已有页面行为和测试。复制一套完整写入 hook 会使取消、世代隔离和重试规则分叉；直接使用原错误读取器则违反现有投影范围，两者均不采用。

### 3. 全程保留精确数值和内存状态

实体 ID 继续在前端使用精确十进制字符串，UUID/profileId 按字符串处理；epoch、version、executionGeneration、计数及 total 使用现有无损解码得到的 number 或 bigint，不强转 Number。提交 JSON 整数通过无损编码输出，不改成字符串类型。

死信表关闭内建数值总页数转换，使用显式上一页/下一页及精确 total 文本；用 bigint 比较 `page * size` 与总数，page 仍限制在服务端正 int 范围内。每页提供 20/50/100 选项。筛选和操作原因只在当前内存，地址栏保留固定页面路径；错误摘要和代码都以文本展示。

### 4. Embedding 以全局事实和当前作业分别渲染

初次或手工刷新读取 profiles/status；有 runId 时读取对应 run。保持系统模式与作业阶段两个视图，当前应用实例就绪单独标注。profiles.ready 不拆成不存在的两项独立探测结果。

| 已确认状态 | 页面行为 |
| --- | --- |
| UNINITIALIZED | 说明仅 BM25、新解析等待；可选择就绪目标进行初始化 |
| ACTIVE | 展示当前 profile 和本实例状态；可发起新一轮或同 profile 修复重建 |
| QUIESCING / REBUILDING / VERIFYING | 展示阶段、真实计数和维护影响；不允许新建或恢复 |
| BLOCKED | 展示安全错误码、已保留计数；只对当前原目标提供恢复 |
| 未知状态或读取不可确认 | 展示故障或未知提示，禁用新操作 |

所有 START 使用确认时的 expectedEpoch，RESUME 使用同一 run 的 expectedVersion。确认弹窗固定解释影响和原因限制；原因按 Unicode code point 计数 1–500。无可选 profile、缺少就绪数据或未获资格时，相关表单不可提交。保持服务端 202、409、404、503 的语义，不新增 reasonCode。

状态读取后按最新 runId 发起作业查询，并用请求世代及 runId 排除旧响应。计数到达总数只代表重算覆盖进度，VERIFYING 仍显示自动校验中。当前会话内可短暂保留已跟踪 runId，查询其 SUCCEEDED 并与全局 ACTIVE/目标核对后显示完成；整页刷新而无当前 runId 时只展示全局状态，不重建历史记录。

### 5. Embedding 使用串行定时刷新，死信采用事件触发读取

Embedding 在可见、当前身份/读取资格已确认且处于进行阶段时，上一轮读取结束后用 5 秒延迟安排下一轮，不使用可重叠的 setInterval。每轮最多一项状态读取及其当前 run 读取；profiles 在进入、显式刷新和操作确认核对时更新。进入 ACTIVE/BLOCKED、隐藏、卸载、权限失效或读取故障时取消计时器和请求。后台恢复先经现有 SessionProvider 重新确认身份，再核对权限；故障由显式重读恢复。

死信列表仅响应进入、筛选提交、翻页、刷新及确认重放事件，不加定时器。每次实际 GET 携带新 UUID 请求标识，保留查询审计。筛选改变回到第一页；已确认重放后重读当前页，若总量变化使页码越界，仅执行一次基于当前 total 的回退，避免循环补请求。OFFSET 分页不承诺跨请求固定快照。

### 6. 死信视图只使用现有安全投影

列表默认 OPEN、page=1、size=20，全部选项省略参数，时间采用带偏移的 ISO 格式与 `[from, to)`。抽屉从已加载的行取得摘要，不新增详情端点或根据 versionId 推测 documentId。READ/REPLAY 功能资格不授予正文访问，页面不为了名称或预览联查受限目录。

每次只允许一个重放意图。对 OPEN 行填写 1–2000 code point 原因后确认，弹窗列明任务和版本身份。确认结果显示“已重新入队”，而不是“解析成功”。维护中也允许正常提交；是否等待由既有 Worker 控制，页面不依赖额外 embedding:read 来推测或绕过维护。

### 7. 后端拆分输入校验与内部重放绑定投影

在 Controller/Service 边界使用明确校验：请求标识 strip 后 1–256 code point，原因 strip 后 1–2000，拒绝 NUL 与超长值；移除用同一个 required/bounded 截断两类字段的路径。列表 page/size、枚举和 OffsetDateTime 范围均在访问列表资料前验证；省略或空枚举保持不限，非空值精确匹配白名单。from/to 缺一端时保持开放区间，双边存在才校验顺序，不新增最大时间窗口。

新增仅供内部使用的重放绑定投影，包含死信 ID、resolved_by、resolution_reason 和对外原结果；不把操作者或原因新增到公开 DTO。利用现有字段逐项比较规范化输入，无需新建幂等表。历史记录只使用已保存事实，不能还原被旧实现截断的长原因；无法确认匹配返回 409。

审计摘要使用现有 JSON 序列化能力构造，取代手工字符串转义，保证引号、换行及制表符得到有效 JSON。数据库字段写入经校验的完整文本，避免截断掩盖校验遗漏。

### 8. 按请求标识串行化重放并保留既有行锁顺序

重放事务显式采用 READ_COMMITTED，在读取绑定前取得以固定域前缀加规范化请求标识计算的事务级 advisory lock，沿用仓库 hashtextextended 模式。锁作用域是当前 PostgreSQL 中的请求键，不使用 JVM 锁，不依赖浏览器 UUID 永不碰撞。摘要碰撞至多增加串行等待，真正绑定始终比较完整值。

事务顺序为：

1. Controller 按当前功能权限鉴权，Service 完成字段校验。
2. 获得请求键事务锁，然后读取已提交绑定。匹配则返回原结果，不写任务或成功审计；操作者/目标/原因不同则 409。
3. 无绑定时取得 Embedding 控制共享锁，保持既有任务行、死信行的锁顺序和 OPEN/failed/执行周期前置条件。
4. 事务内关闭原死信、递增执行周期、清除旧执行资格、写任务事件和一次成功审计，然后返回原死信的 REPLAYED 结果。
5. 并发相同键等待首次事务提交后重新读最新绑定；不同键争抢同一死信由现有行锁和前置条件保证最多一个成功，其他按已处置目标 404。

事务和锁等待设置有限超时，等待或数据库暂不可用时安全失败，由客户端保留原绑定核对。保留请求标识唯一索引作为最终防线；不把任意完整性错误都改成匹配成功，不在 PostgreSQL 已失败的同一事务中继续查询。若需处理已知唯一约束异常，只能先回滚再以新事务核对绑定。部署时排空旧版重放写入口，避免没有请求锁的旧实例参与并发。

锁方案复用现有存储，不新增迁移。单纯依赖唯一索引只能防重复存储，无法让第二个相同请求稳定取得已确认结果；单实例互斥无法约束多实例，因此均不足以满足本次契约。

### 9. 验证限定为进程内单元测试与静态构建

- 前端复用现有 Vitest/Testing Library，网络、会话和权限边界使用 Mock/Stub，路由在内存中运行；通过隔离的单元/组件测试覆盖无资格不请求、阶段、计数、筛选、手动刷新、原请求重试、大整数与迟到响应，定时行为使用受控时钟，不启动真实浏览器或前后端服务。
- 后端直接调用控制器并 Mock 鉴权/服务；服务使用 Mock Mapper、控制状态和审计依赖，覆盖输入、完整绑定匹配、内容冲突、历史记录及 JSON 摘要。编排单测只验证协作调用顺序、分支和异常传播，不执行真实 SQL 或验证实际锁互斥、事务回滚。
- 不编写或执行集成测试、数据库多连接烟测、真实 HTTP 请求、真实文档解析或嵌入式组件测试；不将这些项目保留为本变更的可选任务、待办或部署验收门禁。
- 后端只运行明确的进程内单元测试白名单，打包按需跳过测试，避免全量 test/verify 隐式触发现有外部依赖测试；前端运行相关隔离测试、类型检查和静态构建。保留实际命令与结果，不用源码或文档字符串断言替代行为测试。
- 文档任务只交付使用、兼容性和验证边界说明，不为文档新增测试、不运行其示例。本次验证不证明真实数据库并发、分布式故障或生产部署效果。

## Risks / Trade-offs

- [接口输入收紧] → proposal 标记 BREAKING，文档列明 256/2000 边界、400/409 行为和历史截断记录核对限制；合法旧客户端保持原请求结构。
- [页面事实与提交间发生并发更新] → 仅允许基于已确认状态提交，继续由 expectedEpoch/expectedVersion 和后端前置条件最终裁决，409 后重读并重新确认。
- [记录消失或全局变 ACTIVE 不能证明本次成功] → 只用匹配回执和已跟踪作业确认；其他情况显示当前事实或待核对。
- [查询审计随刷新累积] → 死信默认手动刷新，不新增查询审计聚合或保留策略。
- [共享写入 hook 改动影响既有管理页] → 新执行器参数有原行为默认值，保留身份管理错误投影与原调用方回归。
- [锁等待或跨实例竞争] → 实现采用请求锁与既有行锁统一顺序、有限等待；本次仅以 Mock 验证编排和异常分支，不宣称真实数据库并发已验证，也不新增外部验证任务。
- [浏览器刷新丢失待核对绑定] → 明确仅内存保存，重开后读取当前事实，不承诺恢复旧请求或撤回已发送写入。
- [页码分页中的 total 与列表随并发处置变化] → 允许事实刷新，空页仅一次有界回退，不承诺完整快照或稳定总数。

## Migration Plan

以下仅记录部署兼容性与回退约束，不作为本变更的执行任务或验收条件；本次不启动、部署或联调外部组件。

1. 交付后端输入与重放修复及进程内单测结果，不修改历史迁移或权限绑定。
2. 在说明中列明静默截断、非法筛选行为变化，以及部署时需要排空旧版 app 重放写入口、统一绑定规则的兼容约束；Worker 无需为本次页面变更升级。
3. 交付前端静态产物，并说明两条新路径沿用既有 SPA 回退配置；权限与站内返回行为通过 Mock 会话和内存路由组件测试覆盖，不附带真实浏览器验收任务。
4. 记录前端独立回退、后端回退后失去新校验保证及保留现有重放事实的影响，不执行回退演练或数据逆向修改。

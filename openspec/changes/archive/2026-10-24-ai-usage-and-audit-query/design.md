# Design

## Context

动机见 proposal.md。以下实现事实决定接入方式：

- `ChatQuotaAuditService` 在 Redis 维护部门请求窗口、并发租约和 token 预留；`RedisChatAuditSink` 把 `ChatAuditEvent` 放入最多 100000 条的列表。`ConversationSettlementService` 向同一个 auditKey 写入另一种 `SettlementIntent` 结构，列表不是可直接稳定分页的统一历史。
- `ChatService.UsageAccumulator` 缺省为零；单轮 fail/cancel 走现有零值结算，多轮则由 `UsageSettlement` 区分 KNOWN/UNKNOWN/NOT_INVOKED，UNKNOWN 按预留结算。不能为了报表统一而改变这两条路径的额度计算规则。
- V18 的 `kb_conversation_settlement` 已保存稳定 eventId/leaseId、固定意图、部门和 RESERVED/PENDING/SETTLED/REVIEW。`TurnExecutionService` 与既有投递调度器可提供事务内事实，不需要从 Redis 反推多轮状态。
- `kb-ai` 的 `NoDatabaseAccessTest` 禁止 JDBC/MyBatis。现有内部签名实现可复用算法，但装配依赖 `kb.conversation.enabled`，新能力必须有独立配置及 nonce 命名空间。
- `AdminQueryAccess`、`QueryCursor`、前端 `AdminAccessProvider` 和审计页面已有当前资格、时间窗口、大整数及生命周期约定。原审计规格明确排除 AI 事件，维持该接口范围。

## Goals / Non-Goals

**Goals:**

- 让每个被采集的调用有稳定身份和可核对的最小持久事实；统计按调用去重，审计按事件去重。
- 使收尾失败、未知用量和未确认结算可见，保留已有单轮/多轮生成、额度计算和私有会话边界。
- 使同一 PostgreSQL 读取同时返回自洽的汇总及口径元数据，所有查询和清理操作有时间、数量与执行时长上限。

**Non-Goals:**

- 不把 Redis 分钟额度当作历史报表，不将本能力的结算确认值宣称为完整 Redis 账本对账或供应商账单。
- 不对已遗失的旧日志补造事实，不自动回填启用前的 Redis 或多轮记录，不引入长期汇总表、金额、导出和人工改账入口。
- 不为本变更接入真实模型供应商，不改动第三方文档解析边界；实现不依赖真实模型可用。

## Decisions

### 1. 在 kb-app 建立独立事件存储和调用视图

新增 `kb-app/aiusage` 模块，kb-common 只承载无框架的安全元数据和规范化摘要。新增下一号 Flyway 迁移，当前候选为 V21，实施时先核对实际最大版本，保留全部旧迁移。

| 数据 | 用途与约束 |
| --- | --- |
| `kb_ai_call` | 一次调用的当前视图：UUID callId、SINGLE/MULTI、可空且唯一的 turnId、用户/当时部门 ID、采集版本、服务端登记时间、调度意图、生成状态、结果码、用量状态及可空 token、预留/计划扣除额度、结算策略版本、结算状态、确认时刻、版本与收尾租约。UUID 与内部递增 ID 分开，内部 ID 供分页。 |
| `kb_ai_call_event` | 追加事件：唯一 eventId、callId、事件类型、发生和入库时间、白名单事实、规范化载荷摘要。重复 ID+相同内容幂等，不同内容冲突；独立唯一的逻辑阶段键防止换 eventId 重复推进同一阶段。 |
| `kb_ai_collection_period` | 服务端记录的采集启停区间与协议版本，用于区分“没有调用”“未采集”“保留清理”。启停不重置首次覆盖时间。 |

调用视图更新和事件追加在短事务内共同提交，按 callId 行锁和状态版本串行。生成终态固定后，仅允许独立结算进展，不能改写生成事实。事件不能通过公共 API 修改；保留清理可整组删除本模块记录。

不建立到用户或会话的级联删除外键，不保存名称、正文、来源、令牌指纹、内部签名或执行凭据。多轮 turnId 仅是最小关联元数据，不能据此开放私有会话读取。

选择独立存储而不是把 AI 事件塞入 `sys_identity_audit`，是因为 AI 生命周期、用量聚合和保留例外不同；选择追加事件加投影视图，而不是直接查询多轮表与 Redis UNION，是为统一新采集口径且保留明确的不可恢复历史边界。

### 2. 用量和结算采用两条独立状态轴

生成状态为 RUNNING、COMPLETED、FAILED、CANCELLED、INTERRUPTED、REJECTED。固定结果码说明 NO_RESULTS、PLACEHOLDER、QUOTA_REJECTED、DEPENDENCY_UNAVAILABLE 等，不保存原始错误。

| 轴 | 规则 |
| --- | --- |
| 真实 usage | 最终确认的累计输入/输出为 KNOWN；有调度意图而无可靠最终统计为 UNKNOWN，token 为 null；无调度意图且生成已终结为 NOT_INVOKED，token 为零。执行中暂不把未完成统计当作最终 usage。 |
| 结算 | NOT_REQUIRED、RESERVED、PENDING、SETTLED、REVIEW。拒绝且确认未占用额度可为 NOT_REQUIRED；意图或执行结果不确定保留 REVIEW。 |
| 额度 | reservedTokens、plannedChargedTokens 和确认状态分开。对外的 settledChargedTokens 只来自已确认 SETTLED 的固定额度意图，其他状态该值为 null。 |
| 策略 | 使用 `SINGLE_EXISTING_V1`、`MULTI_EXISTING_V1` 标识沿用的计算规则。单轮 UNKNOWN 可按旧逻辑计划扣零，多轮 UNKNOWN 仍按原预留；两者真实 token 均为空。 |

单轮增加内部观测对象，跟踪是否写入模型调度意图、是否收到可靠累计 usage、正常/异常/取消收尾。保留现有 SSE 四类事件与旧适配器构造兼容；没有确认能力的旧模型事件不得仅因整数缺省为零而判为 KNOWN。完整累计统计确认和单次文本增量分别消费，不按字符推算 token。

沿用原单轮计费而不是将其替换为多轮保守扣预留，是为了把本变更保持为可追溯查询与采集增强；改变计费规则应另立变更。

### 3. 新增有版本的内部采集接口

内部路径采用 `/internal/ai-observability/register`、`/events`、`/renew` 和 `/status`，只处理白名单元数据，网关不公开转发。接口独立于会话开关，沿用 RequestSignature 的算法，使用新 secret、caller 和 nonce 域，校验方法、路径、原始 body、签名时间和 nonce 后再解析；严格拒绝未知字段及重复 JSON 键，原始 body 上限 32 KiB。

首次 register 同时需要 kb-ai 服务身份及当前用户会话；kb-app 重新确认启用用户、部门和强制改密状态，固定用户与调用部门。生成端在登记及配额领取中复用同一可信主体；领取前主体变化导致绑定不能核对时停止，不换用户或部门继续生成。后续事件必须绑定已登记的调用、执行代次与固定操作身份，可在原会话过期后收尾，但不能返回正文。内部 status 只返回最小采集确认状态。

事件摘要覆盖协议版本、调用和阶段身份、固定事实，不依赖 JSON 字段顺序。首次登记只接受短时间内的新意图，原登记时间参与绑定；相同 callId 的重试不能重新取当前时间伪装为新调用。事件接口不能隐式创建不存在的调用，32 KiB 限制不限制已登记调用在保留例外期间的合法固定收尾。

选择新鉴权域而非直接复用 ConversationProperties，是为了关闭多轮会话时仍能独立采集单轮，且不扩大原内部历史接口的豁免。

### 4. 单轮从登记到收尾贯穿同一身份

单轮每次实际接受的 HTTP 订阅生成一个 callId，不为原单轮公开接口新增请求重放承诺；客户端重新发起单轮请求仍属于新调用。内部网络重试必须使用原 callId 与事件身份。

流程：确认主体与参数 → register 持久化 → 记录配额领取意图及稳定关联 → 调用原 Redis 领取流程 → 固定领取结果 → 授权检索 → 在真实模型调用前持久化调度意图 → 生成/取消 → 固定生成终态与原规则的额度意图 → 记录原流程的结算确认。

无结果和占位也登记，但没有模型调度意图；明确配额拒绝以 REJECTED/NOT_INVOKED/NOT_REQUIRED 结束。领取响应不确定时不再次领取，不调度模型，记录 REVIEW；不能把超时当作拒绝或确认未占用。

正常终止事件发送前，等待有界的元数据收尾确认；未确认时安全结束，不将故障折算成空 usage。取消仅做有界收尾，不启动后台继续生成。元数据重试只访问采集接口，不重放已有 Redis RELEASE。单轮原 RELEASE 的已有有界重试策略本身不由本查询模块扩展；无法取得可核对结算凭据时记录 REVIEW，不按日志推断余额。

增加单轮观测租约与续期：仅用于确认生成端存活，不负责 Redis 扣费。租约超时后恢复器按已持久的调度/领取事实追加 INTERRUPTED 或 REVIEW；晚到终结不能改写生成终态。若进程在模型完成、最终 usage 持久化前崩溃，实际用量只能保留 UNKNOWN，这是明确的数据边界。

选择先登记而不是流结束时才 fire-and-forget 写一条日志，是为了进程崩溃后仍有可查询的最小事实；代价是启用后登记依赖不可用会阻止新模型调用。

### 5. 多轮通过既有事务记录事实

在已启用采集的 `TurnExecutionService.begin` 事务创建 callId=turnId 的调用视图；匹配重放复用既有记录。reserve、dispatch、终结、ack 以及结算调度器更新 SETTLED/REVIEW 时，在相同业务事务追加对应观测事件和更新投影。事件采用稳定逻辑阶段键，网络重试或重复调度不会增加调用计数。

生成终态、UsageSettlement、原固定 digest、部门、leaseId 和结算重试窗口仍由原流程负责。新模块只投影已有事实，不改原 digest、不从 Redis 重新生成结算、不延长原安全重试期。纯结算在用户过期/停用后仍可推进原意图与观测状态。是否继续采集已登记多轮以观测记录存在为准，关闭新采集开关不能截断已有调用的终结或确认事件。

与单轮共用规范化事件和视图写服务，但多轮优先使用 app 同事务写入，而不是让 AI 再向 app 重复提交 app 已持久化的事实。多轮原恢复器仍是生成状态权威，新的单轮恢复器不得抢占其执行资格。关闭或删除会话清理正文后，观测只保留原最小事实。

### 6. 查询采用独立权限和有界投影

| 接口 | 权限 | 结果 |
| --- | --- | --- |
| `GET /api/admin/ai/usage` | ai:usage:read | 调用级汇总、实际窗口、asOf、已知样本数、覆盖信息与保留策略 |
| `GET /api/admin/ai/usage/groups` | ai:usage:read | groupBy=day/department/user，稳定分组键续页及相同口径数值 |
| `GET /api/admin/ai/audits` | ai:audit:read | 追加事件安全列表、原窗口、hasMore、nextCursor |
| `GET /api/admin/ai/audits/{eventId}` | ai:audit:read | 白名单事件详情；合法 UUID 不存在返回 404 |

共用过滤为 userId、departmentId、mode、generationStatus、usageStatus、settlementStatus、from、to；审计另有 callId、eventType。limit 默认 20、1–100。时间缺省为服务器最近 7 天，单窗口最多 31 天。事件过滤使用事件写入时的事实，不拼接不断变化的当前视图伪装为过去状态；事件尚无该字段时不能命中相应状态筛选。

用量按 call.startedAt 分配窗口，各时间与状态在同一短只读快照内聚合；`COUNT(DISTINCT callId)` 或等价的一行一调用方案保证不因事件连接重复。KNOWN 合计不含 UNKNOWN；没有 KNOWN 时返回 null 与 knownCount=0。计划额度与 SETTLED 确认额度分别汇总，REVIEW/PENDING 单独计数。数据库精确聚合以 BigInteger 等无损整数读取；四个公共接口的内部 ID、计数、token、额度与耗时统一返回十进制字符串，缺失保持 null，不经 Long 溢出或浮点计算。内部单调用 DTO 仍使用经过范围校验的整数，旧 API 的数字协议保持不变。

分组分页按 UTC date、departmentId 或 userId 的稳定键升序续页，不按动态消耗排名。日组最多覆盖窗口涉及的 UTC 日；部门/用户按 limit 续页。分组每次读取有独立 asOf，明确不是跨页冻结快照，总览采用独立服务端汇总，不用浏览器加载的分页相加冒充全量总计。

审计按 `(occurredAt DESC, id DESC)` 分页。扩展独立版本游标，绑定规范化过滤、固定 from/to、首次 `max(id)` 上界及最后位置；限制 `id <= 上界`，迟到事件只会在刷新后的新查询出现。不能只依赖普通 sequence 的大小推断提交顺序：所有追加事件的写路径必须先取得调用行锁，再取得专用 PostgreSQL 事务级发布锁，取得发布锁后才分配事件内部递增 ID、插入事件并提交；其他写者不能在较小 ID 未提交时先发布较大 ID。锁内无网络或外部等待，回滚可留 ID 缺口但不得绕过统一写服务。首次读取在同一只读快照取得已提交上界和第一页，避免较小 ID 的迟提交事件混入续页。QueryCursor 当前不能承载该上界，新增独立游标类型，不改变旧查询的游标格式。保留清理可能使后续页减少，游标不提供对已清理事件的冻结保留。

索引至少覆盖调用登记时间及内部 ID、部门/用户与登记时间、未解决状态与租约，以及事件时间/ID、callId 与时间/ID。本次按实际 Mapper 谓词静态审阅索引，不连接数据库执行查询计划检查，不承诺全量计数或任意多条件索引。接口带查询超时和结果上限，503、参数错误、无权限与空结果可辨认，所有查询响应包含 no-store。

选择调用汇总和事件明细分开，是为了统计不随事件数量膨胀，并明确汇总窗口和事件窗口的不同。

### 7. 180 天策略只清理已解决的观测记录

有效保留期由 `kb.ai.observability.retention-days` 配置，默认 180，必须为正整数；部署实例使用相同有效策略，不一致时清理失败关闭。自动清理由 `cleanup-enabled` 控制，默认 true，首发核对或回退期间可独立关闭，不以停止新采集代替关闭清理。`retentionAnchorAt` 在生成终结且结算 SETTLED 或确认 NOT_REQUIRED 后取两者较晚时刻。执行中、RESERVED/PENDING/REVIEW 的 anchor 为空，永不按年龄直接删除。

清理调度器使用有界批次（默认 500），通过事务级锁防止多实例重复轮次。每批锁定调用并复核状态、anchor 与当前保留策略，再先删除所属事件、最后删除调用，事务失败整批回滚。状态推进和清理争用同一调用行锁；确认结算会在同事务更新 anchor，不能拿候选扫描时的旧状态删除。

仅删除本模块表。过期调用的事件重试不能创建记录；register 的原发生时间校验和事件接口“已有调用才可写入”规则共同阻止旧重试复活。首次登记重试超过新意图接收窗口须核对原记录，记录已清理则拒绝，不能更新时间创建。

保留策略适用于统计和审计，首期没有独立长期聚合档案；清理后普通历史不再进入合计。保留期外因未解决而保留的例外可在合法窗口内查询，但响应标记历史可能不完整。记录采集区间及全局清理进度等最小运营元数据，不保留已删除调用的明细替身。

选择统一保留期而非先删明细、永留聚合，是为了首期统计可回溯到同一保留范围的事实，也避免尚无业务授权的长期档案。

### 8. 页面复用现有生命周期，不扩大原审计入口

在 `App.tsx`、`admin/access.tsx`、`navigation.safeReturnPath` 注册两页和精确权限。复用会话 epoch、权限事实键、AbortController 及查询代次隔离，但 AI 查询有独立类型和状态；旧审计 hook 的专属协议不直接改为多数据源通用协议。

用量页包含已提交查询的总览、状态分布、覆盖说明和分组表；审计页包含事件列表及安全详情抽屉。默认手动刷新和显式续页。退出、切换账号、强制改密、后台和离开页面清空资料；恢复后先核对资格，按默认条件重新读取。403 只做一次资格核对，不因守卫重新挂载循环请求。

筛选只在内存保存，不进入地址、storage 或遥测。ID 和大整数使用现有无损 JSON 路径及十进制显示；null、0、未调用模型分别显示。统计日界固定 UTC，并明确标注。两页不补查用户、部门名称，不以目录故障阻断已确认资格。

### 9. 配置、启停和数据覆盖有明确运营语义

新增两侧一致的 `kb.ai.observability.enabled`，默认 false；启用要求独立的至少 32 UTF-8 字节 secret，生产拒绝开发密钥。采集关闭时管理查询仍可读已有保留数据，并返回 DISABLED；首次未启用的 coverageStartedAt 为空。停止新登记后仍允许可信服务完成已登记调用的固定收尾，不能关闭恢复和原业务结算。

内部协议默认版本 1；初始建议超时 5 秒、最多 3 次有界元数据重试、签名窗口 60 秒、nonce TTL 180 秒、新登记意图窗口 300 秒、单轮观测租约 180 秒且每 30 秒续期。上述时间值集中配置并验证相互约束，不延长既有多轮结算安全窗口。重试使用新 nonce、同一事件身份和原始固定载荷。

有效清理保留策略、覆盖区间和 asOf 来自 app。新记录只覆盖正式启用后的新协议调用；原 Redis 列表继续可供旧流程使用，但既不双计入报表，也不自动导入。尚未接模型或解析服务不会阻止用内存模型替身验证元数据流程。

### 10. 验证修复补充：清理界限、心跳和单轮终态

V22 增加仅保存时间的全局清理界限，界限取本批删除调用登记时间及所属事件发生时间的最大值，在同一删除事务中单调推进；查询起点不晚于该界限时保守提示历史可能不完整。延长保留期不能撤销已知缺口。升级时若已有采集区间而无法还原旧清理进度，以迁移时刻作为保守界限；未开始采集的空库保持空界限，不回填调用明细。

实例策略心跳由独立服务以 REQUIRES_NEW 短事务先行提交；区间同步在取得统一区间锁后复核全部有效心跳。冲突导致区间同步回滚时，活实例声明仍然可见，清理继续失败关闭；停止心跳后才按原90秒租约到期。清理也在区间锁内复核策略，不改变原调用锁和事件发布锁顺序。

单轮在真正领取前重新解析当前主体并比较登记绑定；明确主体拒绝或变化时不领取，不切换用户/部门继续。已确认 FINALIZED 后停止观测租约续期，仍可按原规则续期尚未收尾的配额；已在途的观测续期若在确认终态后被正常拒绝，不将成功收尾改为 SSE error。

## Risks / Trade-offs

- [启用后调用依赖 app 的持久登记] → 明确服务不可用行为，先部署后启用；登记未确认不调模型，不声称降级后仍有完整审计。
- [进程在最终 usage 保存前退出] → 已登记调度意图保留 UNKNOWN，恢复为 INTERRUPTED/REVIEW；不根据文本长度补造真实 token。
- [旧单轮 RELEASE 响应丢失或已有重试无法形成可靠凭据] → 观测记录 REVIEW，不由新模块重放金融副作用；SETTLED 只代表原流程确认的该调用固定额度意图，不代表全 Redis 账本对账。
- [追加事件与多轮事实写事务增加写入开销] → 严格白名单、小载荷、短事务、批量查询与必要索引；不在持锁事务中调用 Redis、HTTP 或模型。
- [事件发布锁使事件提交短暂串行] → 所有调用锁先于发布锁获取，锁内只分配事件 ID、写安全事件并提交；本次仅用存储替身验证调用顺序和分支，不声明已验证真实提交顺序或数据库锁行为。后续放宽此策略必须同时修订稳定事件上界契约。
- [异常记录长期不满足删除条件] → 单独提供 REVIEW/执行中数量和最老年龄指标；不为压缩容量越过已确认的保留例外，本期不引入人工改账接口。
- [汇总状态更新和清理使分页不构成永久快照] → 每次汇总返回 asOf；事件固定入库上界，清理后记录不可恢复；页面不做虚假全量统计。
- [旧权限目录不认识新增 code] → 迁移前排空旧 app，回退遵守目录兼容规则，不为上线忽略未知权限。
- [历史数据无法完整恢复] → 默认不回填，公开采集区间与保留范围；后续历史导入须单独定义来源、去重和验证边界。

## Migration Plan

本节仅描述交付给使用方的部署与回退步骤。本变更的开发和验收任务不执行部署、数据库迁移、端到端验证或外部环境联调。

1. 保持采集关闭，停止新聊天请求并排空需要升级的旧 app/AI；先备份并核对当前迁移版本、权限目录和既有多轮结算状态。
2. 发布新 app，执行新增观测表、索引和权限迁移；仅一次性授予已有 ROLE_ADMIN 两项新权限，空库继续走正式引导。验证旧管理审计范围保持不变。
3. 发布新 AI 与网关，配置两侧匹配的独立 secret、TLS 和协议版本，确保内部采集路径不公开；发布新前端并确认固定路由、API 错误状态和 no-store。
4. 停流期间统一启用两侧采集，确认全部承接聊天的实例支持新协议，再恢复新请求并记录覆盖起点。不得用新旧 AI 混部产生未声明覆盖缺口。
5. 验证正常、拒绝、无结果、取消、断连和结算待核查路径，确认用量/事件去重后再启用自动清理，首轮只核对候选和保护条件再执行有界删除。
6. 回退先停止新登记、排空或按原规则关闭在途生成，保留原结算投递及已登记观测收尾；停用清理并回退前端入口，已有表、数据、Flyway 历史和权限绑定保留。
7. 不认识新权限的旧 app 不能直接回退或混部。需保持兼容目录的版本，或在另行审查的权限迁移后回退；不自动删除新绑定、repair 历史或删除调用数据。

## Validation Strategy

- 验收范围：只执行离线、进程内单元/架构测试、无连接 Mapper 映射、类型检查、静态构建和 OpenSpec 结构校验；不执行集成测试、端到端测试或外部组件运行任务。
- 后端：使用固定时钟、内存状态、签名/nonce 和存储替身、模型流及进程内 HTTP 客户端替身，验证状态、去重、拒绝、UNKNOWN/零值、两种结算策略、恢复、安全投影和依赖调用顺序。不启动应用服务、容器、数据库、Redis、模型服务或监听端口。
- SQL 与事务边界：交付迁移和 Mapper，采用 DDL 静态审阅、无连接映射与存储替身验证。真实迁移、聚合 SQL、数据库约束、锁、回滚、提交顺序及清理竞态均不在本次执行范围，也不作为待完成验收任务；离线通过不能宣称这些真实行为已验证。
- 前端：类型检查、静态构建、模拟 DOM、内存请求、受控流和虚拟时间单元测试，覆盖权限分离、大整数、固定窗口、迟到响应、后台恢复和 403 有界核对，不启动真实浏览器或网关。
- 执行入口：后端与前端采用明确单元/架构测试白名单，不运行全量自动发现入口或混入外部依赖测试；记录实际执行范围和排除项。
- 文档：保留 API、配置、升级与回退说明的编写及人工审阅，不编写或运行针对 README、Markdown、说明文案、注释、示例的内容断言测试。

# Design

## Context

动机见 [proposal.md](proposal.md)。本设计依据当前实现的以下边界：

- `SearchController` 在既有 Sa-Token 和强制改密门禁后取得服务端 userId；`SearchService` 以 `NOT_SUPPORTED` 编排权限、控制读取、Embedding、召回、rerank。
- `PermissionService` 的主体句柄只能在一次调用栈内使用；`IdentityService.resolvePrincipal` 有自己的短只读事务。数据库故障会传播，已确定的停用/不存在主体会形成拒绝范围。
- `QueryRetrievalService` 当前使用固定 10 秒事务，取得 `EmbeddingControlService.lockShared` 后复核 profile/epoch，并调用真实混合 SQL。该共享锁必须持续到同一次数据库召回结束。
- app 的 Hikari 池为 10，远程查询 Embedding 与 rerank 使用阻塞式传输；Worker 也使用 `kb-common.embedding`，但拥有独立任务预算和批处理场景。
- `RetrievalClient` 当前复用 60 秒模型超时，忽略响应包装 code，统一吞错为 `List.of()`；空 HTTP body 可能直接空完成。多轮将空材料保存为 `NO_RESULTS/COMPLETED`，心跳流依赖明确终止事件停止。
- `TurnExecutionService.finish` 已允许未封存来源的轮次以 FAILED 关闭；模型未调度时现有 `UsageSettlement` 能产生 NOT_INVOKED 和零 token 结算。多轮的失败、取消、过期恢复、幂等和费用确认协议可以复用。
- 前端 `api.ts` 的 413/429 文案分别偏向文件和部门配额；`stream.ts` 当前丢弃 error 的消息与附加字段。`user-web-conversations` 已要求错误后核对持久轮次，无需新增持久历史结构。

## Goals / Non-Goals

**Goals:**

- 使截止时间和实际资源占用成为两个独立、可测试的生命周期，防止超时后的工作绕过容量限制。
- 通过搜索专用执行上下文同时限制权限读取、连接获取、控制锁、召回和外部服务；网络等待期间不持有数据库事务。
- 复用已有身份、向量一致性、轮次和结算协议，提供明确的兼容迁移路径。
- 使用可控时间、传输和数据库替身进行独立单元测试，验证受测组件的预算、取消及资源生命周期。

**Non-Goals:**

- 全集群每用户/每部门 QPS、分布式搜索额度、自动扩容、答案缓存及新的权限缓存。
- 改变 BM25/向量的召回算法、检索分页、分类筛选或 Worker 重建策略。
- 接入具体解析/Chat 模型供应商、构建全项目部署平台或全链路追踪系统。
- 保证已发出的 HTTP 请求一定取消供应商服务端的计算或费用；本次约束本地调用、资源和结果消费。
- 编写或执行集成、端到端测试，启动应用/监听服务，运行或连接 PostgreSQL、Redis、MinIO、容器及第三方模型服务。
- 针对 README、运维文档、Markdown、措辞、格式或文档示例的测试；文档任务以对应文件和章节交付为完成依据。

## Decisions

### D1. 配置分组、初值与兼容

下列时间和并发值已经在探索中确认。其余大小、预留和 Retry-After 是为实现限界选择的可配置工程初值，写入配置说明，不当作已有实测容量。

| 配置归属 | 建议键 | 默认值 |
| --- | --- | --- |
| app `kb.search.execution` | `total-timeout-ms` | 8000 |
| 同上 | `embedding-timeout-ms` | 2000 |
| 同上 | `retrieval-timeout-ms` | 3000 |
| 同上 | `rerank-timeout-ms` | 1500 |
| 同上 | `response-reserve-ms` | 500 |
| 同上 | `max-concurrent` / `max-concurrent-per-user` | 8 / 2 |
| 同上 | `retry-after-seconds` | 1 |
| app `kb.search.limits` | `max-query-codepoints` | 8000 |
| 同上 | `max-request-bytes` | 131072（128 KiB） |
| 同上 | `max-embedding-response-bytes` | 1048576（1 MiB） |
| 同上 | `max-rerank-response-bytes` | 262144（256 KiB） |
| 同上 | `max-rerank-request-bytes` | 2097152（2 MiB） |
| 同上 | `max-response-bytes` | 4194304（4 MiB） |
| AI `kb.ai.retrieval` | `timeout-ms` / `max-response-bytes` | 10000 / 4194304 |
| 网关搜索路由 | `response-timeout` | 10000 |
| Web 公开构建配置 | `VITE_SEARCH_MAX_QUERY_CODEPOINTS` | 8000 |

持续使用现有 rerank provider/model/凭据和 Embedding profile；其连接超时只是更外层的连接参数，查询的有效等待为连接配置、阶段上限和请求剩余时间的最小值。Worker 的 30 秒连接配置等不因搜索限界被全局缩短。

拒绝非正值、无响应预留、用户容量超过实例容量、阶段上限大于 `total - reserve`，并以溢出安全方式换算毫秒/纳秒。总阶段上限不必静态求和小于总预算，因为后续阶段动态缩短或降级。AI 的 topK 必须为 1–200，候选数按 `min(200, max(50, 4L * topK))` 计算；模型生成仍使用原生成超时配置。

输入查询非空白、无 NUL/孤立代理项，按 code point 计数。128 KiB 可以容纳默认 8000 个补充字符全部使用 JSON 转义的请求，但字节限界与字符限界仍独立。数量参数的现有默认值和 `topK > candidates` 行为保持兼容；未知请求字段继续不能参与身份、向量和执行配置。

**取舍：** 采用小范围配置对象与现有库；不引入通用韧性框架。单纯把网关改成 60 秒会扩大阻塞积压，不能解决预算和容量问题。

### D2. 搜索入口、执行器与共享截止时间

在 `kb-app/search` 增加搜索执行门面与普通领域编排的分工：

1. 搜索专用正文读取边界限制实际字节并校验输入，既有 HTTP 会话和强制改密门禁继续执行。应用执行预算从合法请求进入搜索门面时开始；请求上传、前置认证门禁和响应经网络送达不作为本次 8 秒承诺的一部分。
2. 门面以单调时钟生成总截止时间，取得当前可信 userId 的实例/用户名额，然后将完整领域编排交给固定容量、零队列的搜索执行器。直接内部搜索调用也经过该门面。
3. 请求上下文只持有可信 userId、截止时间、取消原因和资源登记器。权限句柄及角色事实在实际执行线程内构造和使用，不跨线程传递句柄、Servlet 上下文或数据库事务。
4. 领域编排读取当前权限及控制状态；无可见范围短路；生成查询向量；在短事务中复核 profile/epoch 后召回；可选重排；准备有界成功响应。
5. 门面仅等待剩余总预算。总期限、阶段致命超时、成功和客户端断连竞争一个响应终态。超时交付固定 503，取消注册资源并中断工作线程；迟到结果只能清理资源。

选择普通 Spring MVC 请求线程进行有界等待，实际检索工作在专用有界线程执行。这样可以继续使用现有认证/异常映射，不依赖 MVC 异步重派发时重新执行身份门禁。客户端断连在容器可检测时触发取消；检测不到时仍由 8 秒截止兜底。

成功对象在执行预算内使用受字节限界的 JSON 输出准备好，保持 `R<List<ChunkHit>>` 的实际 JSON 结构；HTTP 层发送已验证字节，避免在门面结束后发生无界序列化或返回半截成功 JSON。原 List 返回的内部兼容入口也必须执行相同限界，不能成为绕过路径。

**取舍：** 保留阻塞式 app 的技术栈；不把 app 改成 WebFlux，也不只在最外层套一个能超时却无法限制实际工作的 Future。

### D3. 时间分配与阶段终止

设总截止为 D，工作截止为 `W = D - responseReserve`。所有权限和控制数据库操作受 W 约束。

- Embedding 开始前，为召回保留 `retrieval-timeout-ms`：可分配时间为 `min(embeddingLimit, W - now - retrievalLimit)`。不为正时跳过 Embedding。
- 数据库召回阶段截止为 `min(W, now + retrievalLimit)`，包括连接获取、共享锁与 SQL。剩余时间少于 3 秒时使用实际剩余值，失败即终止搜索。
- rerank 使用 `min(rerankLimit, W - now)`。无正预算时直接采用已取得的授权候选。
- 响应准备使用总截止 D；仅剩响应预留时不开始新的可选调用。预算检查使用单调时钟，并在接受每次返回、开始下一阶段和提交最终成功前复核。

阶段时间限制覆盖整段工作，不只是 socket 无字节空闲时间。调度器只发出快速终止信号；可能阻塞的关闭或 JDBC cancel 在独立有界取消通道执行。任务数量由实际在途请求约束，取消或结束后删除对应定时任务。

可选阶段达到自身截止且请求仍有剩余时间时，取消该阶段并降级；总期限到达或用户取消时，不再走任何降级阶段。请求中断状态必须传播，不能被 `catch (RuntimeException)` 当作正常模型故障吞掉。

### D4. 两级准入与实际退出记账

`SearchAdmission` 在同一个原子临界区检查用户占用和实例占用。用户达到上限优先返回 429；否则实例满载返回 503。拒绝不创建执行任务，部分领取或任务提交失败整体归还。

实例上限约束的是尚未完全退出的搜索请求，而不是尚未返回响应的请求。一个执行上下文登记主工作及其外部阶段子工作，使用独立的真实退出计数；只有主编排退出且所有登记子工作在各自 `finally` 确认退出后才释放用户名额和实例名额。`Future.cancel(true)`、`isDone()` 或完成回调不得直接作为释放依据。

外部阻塞阶段使用另一组固定容量、零队列的执行线程，容量不超过实例搜索上限。Embedding 超时后即使暂未退出，主编排也可继续执行 BM25；未退出子工作仍挂在原请求上。外部线程容量已满时，可选阶段直接降级，不积累队列。取消通道和调度器也独立设有界容量；不能使用无界 cached pool 或为每次超时无限创建线程。

用户名额降至零后移除该用户计数，避免为所有历史用户保留条目。任务提交失败、完成与超时竞争、重复取消、服务停止均走单次释放状态机。服务停止拒绝新任务并取消已有工作；进程内状态只描述本实例，不能宣称全局公平额度。

**取舍：** 实例保护覆盖浏览器和 AI 直连，也便于按实例调整。新增 Redis 分布式搜索账本会扩大故障面，当前目标不需要它；已有部门 Chat 配额继续由原账本负责。

### D5. 数据库预算必须覆盖权限、控制与实际 SQL

不能只修改 `QueryRetrievalService` 的注解：权限解析和首次控制读取发生在它之前，连接获取也可能等待 5 秒。

- 在搜索执行线程安装请求范围的数据库预算上下文，结束时必定清理。通过搜索感知的 JDBC/DataSource 包装与 MyBatis 插件，把连接获取、正在执行的 Statement 和剩余预算登记到本次执行；非搜索调用不启用此上下文。
- 等待 Hikari 连接时受到主工作取消/中断约束；迟到取得的连接先检查期限并立即归还，不能继续 SQL。获取失败不能回退旧权限。
- 为权限与控制读取的每条语句设置剩余 query timeout，登记 Statement 以便期限到达时取消。秒级 JDBC 超时需向上取整且不能变成 0（无限）；更精确的绝对期限仍由阶段 watchdog 约束响应和取消。
- `QueryRetrievalService` 改用动态预算的短事务模板，事务内在同一连接设置局部 `statement_timeout` 和 `lock_timeout`，再取得现有 MANDATORY 共享锁，复核 profile/epoch，执行当前授权混合 SQL。
- 事务、共享锁以及查询连接必须在实际 SQL 结束/回滚后退出；所有 session 设置只作用于本事务或在归还前可靠恢复，不能污染下一位使用连接的请求。事务以外的权限语句也必须受取消登记器约束。
- 网络模型调用保持在事务外。权限失败、控制状态读取失败和召回失败属于核心故障；只有已可靠解析的空范围才可以产生成功空结果。

**取舍：** 采用请求局部预算，避免全局调小 Hikari 或整个应用的 SQL 超时；已有锁顺序和向量身份复核继续作为正确性约束。本变更通过内存事务、连接和 Statement 替身单测验证预算传递、取消登记及回收调用顺序，结论限定于这些进程内行为。

### D6. 外部传输限界和结果验证

查询 Embedding 与 rerank 采用可注入的传输接口，实际 HTTP 请求、响应流和阻塞解析登记到阶段工作。使用阶段剩余时间构造连接/请求上限，响应采用最多 `maxBytes + 1` 的有界读取；不能先 `body(Map.class)` 完整解析再检查大小。阶段超时关闭响应、取消请求并丢弃迟到值；错误响应只消费必要的有界元数据。

`kb-common.embedding` 增加兼容的、有显式调用预算/响应限界的查询调用重载或 options，保持纯 JDK 类型。`ProfileEmbeddingClient`、`RemoteProfileEmbeddingClient`、`RemoteEmbeddingTransport` 的查询路径显式消费该上下文；无法兑现预算的自定义实现须被外层有界执行保护，不能静默绕过。旧批量方法继续供 Worker 使用；时间、容量和响应大小不进入 profile 指纹。app 只装配 QUERY 角色的执行预算。

rerank 先有界编码本次出站请求，超出 2 MiB 直接返回本次原候选 topK。远程 JSON 使用有界、严格的结构解析，拒绝重复关键字段、多个根值和超深结构；允许与候选身份无关的额外供应商元数据，但不采纳其正文或来源。

有效 `results` 的条数必须为 `min(topK, actualCandidates)`；index 使用精确整数转换，拒绝字符串、小数形式、负数、溢出、越界和重复；relevance_score 要求数值且有限。缺项、空数组、额外结果、缺失分数或任意坏项都整体回退，不拼接部分重排与旧排序。合法结果分数降序、原下标升序；始终映射回原 `ChunkHit`。Embedding 继续使用已实现的模型、数量、维度、非零向量和有限数值校验。

将已知传输/预算/容量/协议失败映射成固定可选阶段失败类别，仅这些类别进入回退；取消信号和未知程序错误继续向上。未知配置在启动时拒绝，不通过宽泛异常捕获伪装成正常降级。

**取舍：** 整批回退更容易保持结果身份和解释性；供应商返回少于请求 top_n 也会触发回退，这一契约需在接入时核对。回退直接采用本次授权候选，不增加一次重试、额外本地重排或答案缓存。

### D7. AI 失败传播、终止与费用

`RetrievalClient` 的返回约定调整为：恰好发出一个合法材料列表，或者失败；不能无值完成。HTTP 200、JSON 成功 code=200 和数组 data 是成功前提；204、空 body、null、包装失败、超大响应和解码错误全部转换为内部 `RetrievalFailure`，不读取或转发远程 message。通过 `switchIfEmpty` 关闭空响应漏洞。

保留已有逐项引用身份校验：混合数组可保留合法项，但非空数组全部无效时为协议失败。单轮继续允许旧响应的未知 versionId；多轮如非空列表最终没有任何可用版本材料，则显式失败。AI 候选参数按照 D1 限界，检索使用独立 10 秒预算，无自动重试；订阅取消只触发既有取消处理。

- 单轮 `ChatService` 为检索失败创建带固定 `SEARCH_UNAVAILABLE` 的 `ChatEvent.Error`，消息为固定文案；保留旧单参数 Error 构造方式的源代码兼容。`ChatController` 和 `AiObservedChat` 两条路径均不再发送成功 Done；采集结果使用既有 FAILED，调用模型意图保持 false。
- 多轮在封存来源、追加回答和调度模型前传播检索错误；`MultiTurnChatService` 的既有 cleanup 尝试提交 FAILED，再用同一结算身份完成 NOT_INVOKED/零 token 结算。error Map 增加固定 code，不将错误文案放进助手正文。
- app 不可用导致 FAILED 无法确认时，流在现有 cleanup 上限后结束，数据库租约过期机制恢复为 INTERRUPTED；前端必须读取事实。已经 FAILED 的轮次即使费用确认失败也不改变生成状态。
- 用户取消、删除或已有终态竞争继续按原协议；相同请求标识重放只返回原轮次，不重复召回。成功降级后的有效材料可以正常调用模型，BM25 真正返回空数组则仍可保存原 NO_RESULTS。
- 费用按既有用量规则计算，不退款或重置请求次数窗口。检索阶段未调用 Chat 模型的事实不代表 Embedding/rerank 供应商一定没有收费；本次不把这两类调用加入 Chat token 账本。

**取舍：** 使用既有失败状态和费用协议，不新增数据库状态或迁移表。固定 SSE code 允许前端给出明确提示，同时避免显示任意远程错误内容。

### D8. 前端与 HTTP 兼容

搜索页增加 Unicode 校验和 code point 长度提示；后台可降低上限，实际 400/413 仍是最终结果。页面使用搜索专用错误映射：400 输入不符合要求、413 搜索请求过大、429 搜索过于频繁、503 检索暂不可用；不全局改写文件上传或部门 AI 配额文案。Retry-After 是重试建议，不保证下一次成功，也不启动自动请求循环。

`stream.ts` 只提取白名单中的 `SEARCH_UNAVAILABLE`，把可选 code 交给 `Assistant.tsx`；缺失/未知 code 使用原通用错误流程。固定错误提示与持久轮次核对并行保留，不能因收到 error 就在本地伪造 FAILED。会话切换、离页、身份变更清理提示，旧响应不能恢复。

搜索成功依然是现有 JSON 包装与分块结构，不增加强制客户端理解的成功字段；内部结构记录执行模式和降级原因供指标使用。网关将 `/api/search` 的 10 秒响应超时配置独立表达，并透传 app 的 HTTP 状态与 Retry-After；AI 流式路由继续依靠流自身生命周期，不套搜索 10 秒总时长。

### D9. 观测与验证

使用现有 Micrometer：

- `kb.search.requests`：SUCCESS、EMPTY、FAILED、REJECTED、CANCELLED；成功降级仍计为一次请求。
- `kb.search.stage.duration`：固定 AUTHORIZATION、CONTROL、EMBEDDING、RETRIEVAL、RERANK、RESPONSE 阶段及有限结果类别。
- `kb.search.degradation`：固定阶段及 TIME_BUDGET、TIMEOUT、CAPACITY、UPSTREAM、INVALID_RESPONSE、PAYLOAD_LIMIT、PROFILE_UNAVAILABLE 类别。
- `kb.search.inflight`、`kb.search.lingering`：实际占用及响应结束后仍执行的请求数。

日志只保留固定类别、阶段和状态；不附原始异常，不用用户、query、requestId、任意 profileId 做指标标签。

测试按受测组件分别组织为进程内单元测试，数据库、Redis、HTTP、模型及其他业务依赖一律使用 Mock/Stub 或内存实现。注入单调时钟和调度器，用受控 latch/future 模拟正常取消、忽略中断和迟到完成；用内存输入流和传输替身验证字节限界、分段读取和严格解析；用 JDBC/事务替身验证连接到达后复核、同连接超时设置、取消登记以及锁与回滚调用顺序。

控制器使用 standalone MockMvc 与业务依赖 Mock，网关使用路由对象、Mock ServerWebExchange 和下游响应 Stub，前端使用 Vitest/模拟 DOM 与会话/API 替身。各组件独立接受契约夹具，不组合真实业务组件进行联调，不启动监听端口、浏览器、应用或第三方服务。

测试命令显式列出允许的单元测试类或文件，禁止全量/通配执行带入既有集成测试；编译、类型检查和静态构建可以执行。文档只要求交付，不测试其内容、措辞、格式或示例，也不扫描源码、SQL、配置文本进行格式断言。验证记录只描述实际执行的单元测试和静态检查，不将替身结果视为真实数据库锁、驱动取消、跨服务或供应商行为的证明。

## Risks / Trade-offs

- [短预算更容易降级] → 使用独立阶段指标观测比例，按真实延迟调优；默认值表达初始策略，不宣称已达到性能目标。
- [取消不能强制终止第三方或驱动] → 实际退出前保留容量，限制工作线程和取消通道；持续挂起会让实例快速拒绝新检索，指标暴露该状态。
- [JDBC 秒级超时和网络取消存在精度差异] → 单调绝对截止负责响应，局部数据库超时与取消负责回收；本轮单测验证预算及取消/回收调用，实际驱动行为不纳入本轮验证结论。
- [多个实例会放大总请求数] → 明确容量是实例级，部署总容量按副本数计算；不以本次机制替代全局部门配额。
- [严格响应验证暴露历史松散返回] → 用固定输入输出夹具覆盖真实包装、旧单轮缺版本、空 body、坏项和 rerank 条数；升级说明列出契约变化。
- [前后端版本错位] → 新增错误码为可选字段，旧前端仍能结束流；部署顺序确保新 AI 先停止吞错，再启用 app 限制。
- [权限句柄或数据库预算串线程] → 仅传递可信 userId 和纯预算数据，线程内解析权限，所有上下文在 finally 清理并通过复用线程回归验证。

## Migration Plan

以下流程用于运行说明的交付；本变更的实施任务不启动服务或执行部署。

1. 提交代码时同步新增 `docs/search-resilience.md`，记录默认值、作用范围、错误语义、容量计算、指标及实际验证范围；更新 README 的检索和 AI 降级说明。
2. 先发布支持可选 SEARCH_UNAVAILABLE 的 Web，以及使用独立检索预算、成功包装校验和失败收尾的新 AI。旧 app 本来就返回成功 code 包装，因此可先兼容；各组件的独立单测分别使用旧/新协议夹具核对其输入输出。
3. 再发布 app 的有界执行、传输和准入，随后对齐网关搜索路由。默认 outer=10s、app=8s；修改总预算时同步调整调用方，保留至少默认的 2 秒外层余量。部署配置检查应核对这组关系，单个服务不能自行证明另一服务的实际配置。
4. 无数据库迁移。观察检索降级、拒绝、真实在途和 lingering，按实例容量与外部依赖时延调整配置；灰度期间不宣称所有旧实例也受新容量保护。
5. 回退优先恢复 app/网关配置及实现，新 AI 可继续消费旧 app 的合法响应。若 AI 也回退，则检索故障再次成为 NO_RESULTS，必须明确作为行为回退记录。已保存 FAILED、既有结算意图和历史不重写；Web 的可选错误码处理可保留。

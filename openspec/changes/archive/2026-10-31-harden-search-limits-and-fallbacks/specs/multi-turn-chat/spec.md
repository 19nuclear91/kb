# Spec Delta

## MODIFIED Requirements

### Requirement: 追问检索必须结合可用历史并保持授权召回

有合格历史时，系统 SHALL 用有界的历史主题与当前问题构造追问检索输入；无历史时使用当前问题。检索 SHALL 继续经调用者会话执行受权限保护的 POST 召回，不采用服务账号、客户端裸向量或旧授权范围。合法成功空结果 SHALL 保持固定无结果表现；检索拒绝、超时、不可用或协议损坏 MUST 显式失败，不用旧回答或全库检索绕过该结果。非空材料全部缺少可用版本身份时不得冒充真实空结果或推断当前版本。

#### Scenario: 含指代的追问
- **WHEN** 用户先询问任务租约，再提出“它过期后怎么办”且相关完整历史仍可用
- **THEN** 发送给检索的输入同时包含受预算控制的先前主题和当前问题
- **AND** 原问题作为本轮用户消息保存，检索输入不冒充用户原话

#### Scenario: 无合格历史或无结果
- **WHEN** 没有可用历史，或授权检索合法成功返回空结果
- **THEN** 前者只用当前问题检索，后者产生固定无结果回答且不调用模型
- **AND** 不靠历史正文回退为另一条未授权回答路径，不声称发现了不可见文档

#### Scenario: 检索服务故障
- **WHEN** 本轮授权检索超时、被容量限制拒绝、依赖不可用或响应损坏
- **THEN** 进入检索失败收尾，不声明 NO_RESULTS，不把故障文案追加为成功助手正文
- **AND** 不继续调用模型、不复用历史回答，不自动再次检索

#### Scenario: 所有材料缺少版本身份
- **WHEN** 非空召回材料均无法提供可用的固定版本身份
- **THEN** 本轮按检索协议不可用处理，不补成当前版本、不将材料交给模型，也不产生正常无结果回答

#### Scenario: 可选阶段已经合法降级
- **WHEN** app 因 Embedding 或 rerank 不可用完成受控降级，并返回合法的版本化材料
- **THEN** 多轮可以按既有预算和来源确认流程继续，不将允许的检索降级当作整个生成失败

### Requirement: 新旧流式协议必须具有明确兼容边界

既有 `POST /api/ai/chat` SHALL 保留单轮请求、占位兼容、引用及终止行为且不自动写入历史，但检索失败按新契约改为安全 error，不再输出成功无结果回答。新入口首次接受使用 SSE，返回会话/轮次标识响应头，事件继续使用 citation、delta、done、error；匹配重放使用 JSON 并由 Content-Type 明确区分。检索 error SHALL 附带固定 code=SEARCH_UNAVAILABLE，原消息字段仍可读取。SSE 来源仍是本轮实际新材料，不以继承依赖宣称逐句证据。新流与历史响应 MUST 禁止存储缓存。

#### Scenario: 旧调用方与新轮次首次接受
- **WHEN** 旧客户端调用原单轮接口，或新客户端首次成功提交会话轮次
- **THEN** 旧客户端继续消费原事件类型与字段，并按新规则接收检索 error；新客户端在流开始前取得 X-Conversation-Id、X-Turn-Id
- **AND** 新流持续输出既有四种事件，正常完成、错误和客户端取消均能有界结束

#### Scenario: 流开始前拒绝和重放
- **WHEN** 身份、归属、参数、预期序号或配额在 SSE 建立前拒绝，或者请求为匹配重放
- **THEN** 拒绝使用相应 HTTP 状态；重放返回 application/json 身份与状态
- **AND** 不通过第二个 SSE 订阅重启生成，不在错误或重放 JSON 中附带回答正文

#### Scenario: 两类单轮观测模式
- **WHEN** 单轮 AI 采集开启或关闭时发生检索故障
- **THEN** 两种路径都以安全 error 结束，不发送成功 done；开启采集时记录失败而非 COMPLETED/NO_RESULTS

#### Scenario: 前端识别检索错误
- **WHEN** 用户端消费带 SEARCH_UNAVAILABLE 的 error
- **THEN** 显示“检索暂不可用，请稍后重试”，结束本次消费并按已有协议核对持久状态
- **AND** 缺少或未知 code 时使用通用错误提示，不直接展示任意服务端 message

## ADDED Requirements

### Requirement: 检索失败必须复用既有终态和未调用模型结算

已创建但模型尚未调用的轮次发生检索故障时 SHALL 在有界收尾内尝试提交 FAILED，释放会话活动资格并按 NOT_INVOKED、真实 token 为零、chargedTokens 为零形成既有结算意图。错误不作为助手正文保存，不进入后续完整历史上下文。持久化或结算不可用时 MUST 保留既有待确认及过期恢复机制，不假称终态或额度释放已确认，不发送成功 done，也不得覆盖已经提交的其他合法终态。

#### Scenario: 检索失败且收尾成功
- **WHEN** 已领取配额的轮次检索失败，且 app 与结算依赖可用
- **THEN** 轮次保存为 FAILED，模型调度次数为零，NOT_INVOKED 与零 token 结算可被历史和审计核对
- **AND** 并发资格正常释放，既有请求次数窗口不因失败而额外重置

#### Scenario: app 同时不可用
- **WHEN** 检索失败后提交 FAILED 也无法在收尾期限内完成
- **THEN** SSE 仍有界结束为错误，已保存状态由后续读取与资格过期恢复核对，不在客户端伪造 FAILED 或继续生成

#### Scenario: 失败终态已保存但结算未确认
- **WHEN** FAILED 已提交，而同一结算意图投递暂时失败
- **THEN** 历史保留 FAILED，结算独立待确认并使用同一身份恢复，不重新检索或创建另一次扣费

#### Scenario: 取消与失败竞争
- **WHEN** 客户端取消和检索故障收尾同时争用轮次
- **THEN** 只保留先提交的合法终态，重复回调不能追加错误正文、改写终态或重复结算

### Requirement: 检索失败后的匹配重放不得重新生成

检索失败后的相同用户、会话、请求标识、原问题及预期序号的匹配重试 SHALL 遵循既有幂等协议，读取原轮次及当前状态，不再次检索、调用模型或领取配额。用户主动重新发送时 MUST 使用新标识和当前序号，并重新验证权限、检索容量及部门配额。

#### Scenario: 重放失败轮次
- **WHEN** 客户端对已因检索故障失败的轮次执行匹配重试
- **THEN** 返回同一轮次的 JSON 重放结果，不发起新的 SSE 或任何上游检索

#### Scenario: 用户主动重发
- **WHEN** 用户读取失败事实后主动以新请求标识和最新序号发送
- **THEN** 按新的请求重新判定当前资格与容量，原失败轮次及结算事实保留

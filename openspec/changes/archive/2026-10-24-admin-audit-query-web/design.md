# Design

## Context

动机见 [proposal.md](proposal.md)。行为契约见 [admin-web-audits](specs/admin-web-audits/spec.md) 和 [admin-web-access](specs/admin-web-access/spec.md)。本变更涉及权限、精确时间及异步请求生命周期，需要在编码前确定状态边界。

已核对的现状：

- `AuditQueryController` 已提供列表和 UUID 详情；`AuditQueryService` 逐请求判定 `audit:read`，默认服务端最近 7 天、最多 31 天，游标绑定筛选和微秒精度窗口。
- `AuditQueryViews.Page` 包含 `items/hasMore/nextCursor/from/to`；详情为 `metadata/changes/summaryAvailable`。`AuditSummaryProjector` 已执行后端字段白名单，查询范围不包含 AI Redis 与独立 Embedding 操作。
- `kb-web/src/admin/access.tsx` 已有管理权限上下文、页面守卫及菜单；`App.tsx`、`navigation.ts` 尚无审计路由和返回地址规则。
- `Session` 已提供认证、no-store、取消及会话 epoch 隔离；`api.ts` 的无损 JSON 解码把 ID 转为精确字符串，把超安全范围的普通整数保留为 bigint。
- 通用 `useCursorList` 只暴露记录和游标，丢弃 from/to；续页错误可保留已读记录。审计需要区分暂时故障与 403 的整页清理，并避免权限核对导致守卫重挂载后循环请求。
- 相邻管理页使用 Ant Design、内存请求替身和 jsdom 测试，当前没有真实浏览器验收证据。

## Goals / Non-Goals

**Goals:**

- 在现有管理页体系内实现可核对的审计查询状态，确保一次查询的筛选、时间窗口和游标始终一致。
- 让仅持有 `audit:read` 的用户独立完成排查，准确读取大整数、安全摘要与空主体。
- 将审计特有的拒绝恢复和窗口逻辑限制在新模块，保持其他管理页面的读取与写入行为。

**Non-Goals:**

- 后端查询协议、数据源汇总、身份目录关联和审计生产者完整性改造。
- 通用管理 Hook 重构、全局 JSON 解码规则调整和新增客户端依赖。
- 带筛选的页面深链接、导出、自动轮询或审计写操作。

## Decisions

### 1. 首版直接消费现有 API

列表和详情分别使用 `/api/admin/audits` 与 `/api/admin/audits/{eventId}`，复用现有 Session 认证传输与 `readJson` 的 R 解码。审计专用读取调用 `Session.send` 并关闭其前置 403 身份等待，收到 403 时立即向页面交付拒绝，错误体取消也不阻塞拒绝；页面清理后才触发一次资格核对。适配器在读取响应前后核对取消信号和 Session epoch。其他业务的 Session 默认行为保持原样。`audit-query` 主规格及 Java 代码不需要本次修改。页面说明采用“展示已记录的管理与登录事件，包含企业登录和绑定；不包含 AI 调用与独立向量重建记录；未查到记录不表示操作未发生”，不向用户呈现内部表名。

备选：统一汇总 AI 与 Embedding。该方案会改变后端数据源、游标与安全投影契约，超出本次前端页面范围；以后通过独立变更扩展。

### 2. 使用审计专用 API 与查询状态

计划文件边界：

| 文件 | 职责 |
| --- | --- |
| `kb-web/src/admin/auditApi.ts` | 筛选和响应类型、条件校验、URL 构造、列表与详情读取、安全结构投影 |
| `kb-web/src/admin/auditQuery.ts` | 已提交查询的代次、窗口、记录、游标、列表与详情互相隔离的请求、拒绝恢复 |
| `kb-web/src/admin/AuditsPage.tsx` | 草稿筛选、查询动作、表格、详情抽屉及状态展示 |
| `kb-web/src/admin/access.tsx` | 精确 `audit:read` 常量和管理导航条目 |
| `kb-web/src/App.tsx`、`kb-web/src/navigation.ts` | 受保护页面与精确的安全返回路径 |

专用查询 Hook 复用现有会话与权限上下文、取消模式和错误分类，不修改通用 Hook。列表与详情分别持有 AbortController、请求序号及查询代次；每次应用结果前核对 signal、序号、查询代次、会话 epoch 和当前资格。

备选：扩展 `useCursorList` 以携带任意页元数据及审计拒绝策略。这会扩大账号、角色等既有调用方的回归范围；本次保留为审计局部实现。

### 3. 表单草稿与已提交条件分离

常用区展示最近 7 天／自定义时间、结果和操作域；高级区展示操作、操作者 ID、目标类型与 ID、请求标识和本地登录用户名。操作域及类型提供已知值提示，同时允许合法未知原值；本地标签仅用于展示。

- 初次进入默认每次 20 条，支持切换为 50/100；改变条数重新开始查询。
- 空字符串代表未选择，构造请求时省略；非空文本保持精确匹配，首尾空白、控制字符或超长输入报错，不静默改写。
- 长度上限：操作域和操作 128 个 Unicode code point，目标类型 64，请求标识 256，用户名 128。ID 使用 `positiveId` 的字符串校验，不经过 Number；targetId 依赖 targetType。
- 默认最近 7 天首请求省略 from/to。自定义模式要求两端同时存在，这是前端交互约束；后端原有单边时间能力不变。
- 自定义日期先核对实际日期及本地时间，再转换为带时区请求时间；请求窗口必须递增且最多 31 天。
- 编辑草稿不发请求。提交相同合法筛选也新建查询代次；刷新沿用已提交条件而非未提交草稿，重置恢复默认表单与每次 20 条。
- 原查询在新输入校验失败时继续有效；一旦新查询被接受，则关闭详情、取消旧请求并清除旧结果。

备选：将筛选绑定地址栏或输入即检索。前者持久记录审计筛选，后者易把旧游标与新草稿混用；本次均采用显式提交。

### 4. 服务端窗口与游标构成一次查询

查询状态保存提交条件、请求代次、已确认记录、服务端原始 from/to、nextCursor、hasMore、加载和错误状态。时间显示可使用本地格式，网络状态始终保留返回的原始字符串，不通过 Date 往返重新生成微秒时间。

续页请求继续使用已提交的非时间条件、固定每次条数、服务端原始 from/to 与 nextCursor。首请求若有自定义窗口，则返回后的服务端规范化窗口为后续请求依据。API 适配器验证窗口合法，查询状态核对续页窗口与首窗口一致。

同一查询同时至多一个列表请求，使用同步互斥标记防止 React 状态更新前的双击。收到合法页后一次提交记录和新游标，按服务端顺序追加；事件以 eventId 标识，不按分数或显示时间重新排序。重复事件、非前进游标或不可信响应作为读取故障，不静默去重掩盖问题。

续页暂时失败保留已确认记录、原窗口及待重试游标；显式重试重新请求同一页，未确认的数据不进入列表。刷新重建整个查询：默认范围重新由服务端定界，自定义范围沿用已提交时间。页面只显示已加载数量、实际查询窗口和继续读取，不添加总数或跳页。

备选：每次续页重新以浏览器当前时间计算最近 7 天。这会改变游标签名，或把不同窗口结果混合，故不采用。

### 5. 安全 DTO 与精确值展示

`auditApi.ts` 从 unknown 响应构造页面需要的对象，不直接把服务端对象全量展开到组件。校验 metadata 必需字段、UUID、可空精确 ID、时间、分页字段和详情事件身份；详情变化值只接收字符串、布尔、合法 Long 整数或 null，额外顶层字段不进入展示模型。

沿用既有无损解码：ID 是字符串，before/after 的整数为 number 或 bigint。数值校验拒绝不安全 number、小数及超 Long 范围；展示统一转换为精确文本，禁止 Number(bigint) 或全对象 JSON.stringify。null 变更值显示“空值”，空字符串显示“空字符串”；false、0 均保留；null 操作者及目标显示“未记录”。

详情按 eventId 读取，保留安全元数据和 changes；summaryAvailable=false 时忽略变化内容并提示摘要不可用；true 且 changes 为空显示无可展示变更。打开另一事件时立即清理旧详情。字段标签和已知枚举可翻译，未知合法代码按原值文本显示，禁止 HTML 渲染和外部资源加载。

API 投影不承担替代后端审计白名单的职责；本次不复制整个审计生产者或扩大详情字段集。请求标识与目标 ID 可作为排查信息展示，不联查名称或生成跨业务页面的自动读取。

备选：直接展示原始 JSON。它既不适合字段前后值核对，也容易带入新增的非展示字段，因此采用明确 DTO 和表格。

### 6. 以当前资格隔离数据，拒绝后显式恢复

新增 `perm.auditRead = 'audit:read'`，通过现有 `AdminGuard` 与菜单精确判定。空间目录故障不影响已确认的审计资格；旧 `identity:audit:read`、角色名、前缀和写权限不能开放页面。

状态处理：

| 事件 | 处理 |
| --- | --- |
| 列表／详情 401 | 使用现有 Session 登录恢复，清理审计状态 |
| 列表／详情 403 | 立即清理结果、详情、窗口、游标及筛选，并至多自动核对一次权限 |
| 详情 404 | 清除该事件详情，显示不可访问，保留同身份下已确认列表 |
| 输入或游标 400 | 输入错误留在表单；失效游标停止续页，允许重新提交查询 |
| 网络、503、损坏成功响应 | 显示安全故障；续页保留已确认部分并允许手动重试 |
| 退出、身份变化、强制改密、后台、离开 | 取消请求并清空页面数据；恢复后先确认身份和资格，再从默认查询开始 |

403 拒绝标记以 Session 对象、epoch 及独立的 `permissionFactsKey` 为界，仅保留“审计读取已拒绝”的状态，不保留审计资料。该键只根据已确认的功能权限集合生成，不含空间目录及其加载状态；审计页面的挂载键同样使用该权限键。权限核对中的 loading 不解除拒绝，权限先返回而空间仍加载、目录清空／恢复或读取失败也不能触发审计自动重读。旧上下文未提供此键时只使用当前审计读取资格作为保守回退，不能使用混合空间目录的 factsKey。使用模块内 WeakMap 或等价的同生命周期状态，使守卫权限核对后重挂载不会自动重新查询；显式重试、身份代次或真正权限事实变化才能解除拒绝。详情 403 与列表 403 使用同一审计拒绝边界，不允许详情请求失败后列表继续加载。

临时故障不写入该拒绝标记；权限接口不可用时依赖既有守卫显示重新确认。后台恢复沿用现有 SessionProvider 的 epoch 更新，不新增另一套登录或恢复监听。

备选：只在组件内记录 403。这会在守卫重挂载时丢失拒绝状态；保留旧结果等待权限核对也不能满足立即清理要求。

### 7. 验证限定为隔离的进程内单元测试与静态检查

- `auditApi.test.ts`：替换传输依赖，单测精确筛选、空值省略、长度／ID／时间边界、未知合法代码、无损 ID 与变化值、响应字段和 UUID 核对、损坏响应。
- `auditQuery.test.tsx`：使用会话、权限与 API 替身单测固定微秒窗口、单飞续页、失败重试、草稿隔离、刷新代次、重复身份／游标拒绝、迟到响应及拒绝标记跨 Hook 重挂载保留。
- `audits.test.tsx`：替换查询 Hook、会话及权限依赖，只挂载被测页面，单测筛选输入、摘要三态、值展示、安全文本、状态反馈和依赖变化后的敏感状态清理。
- `audit-access.test.tsx`：使用上下文替身分别单测守卫与导航，以及安全返回路径纯函数；不组合 App／AppRoutes、真实 SessionProvider、AdminAccessProvider 与业务页面。
- 定向回归仅包含独立的 `navigation.test.tsx`、`session.test.ts`、`api.test.ts`；不执行 `admin/access.test.tsx`、`admin/operations-routing.test.tsx`、`routing.test.tsx` 等包含多模块组装的测试文件。
- 使用现有 Vitest 与 jsdom，按明确文件白名单运行单元测试，不启动应用、浏览器、HTTP 测试服务器、数据库、Redis、MinIO、Docker、模型或供应商服务；不编写或执行 README、说明文档、注释、规格及示例的内容断言测试。文档仅交付使用说明及实际检查记录。
- 类型检查与 Vite 静态构建使用本地开发工具；实施时记录实际执行文件、结果及未验证范围，不安排集成或端到端测试。

## Risks / Trade-offs

- [首次默认窗口依赖服务端时间，前端不能提前知道实际范围] → 首次加载期间显示范围待确认，成功后使用返回的实际窗口；自定义范围才由用户显式确定。
- [显示格式丢失微秒导致游标不匹配] → 时间原值与显示文本分开，专门使用六位小数窗口的行为测试。
- [权限核对卸载组件使 403 自动请求反复出现] → 拒绝标记超出单组件寿命，但限定于当前会话与权限事实；以重挂载测试验证。
- [默认隐私生命周期会在后台恢复后丢弃筛选] → 使用默认查询重新读取，页面说明该行为，避免恢复旧身份资料。
- [新增审计域可能暂时缺少中文标签] → 保留合法原始代码，搜索接受未知值，显示不依赖标签字典完整。
- [继续读取累积当前会话中的记录] → 只允许显式有界页请求，不自动预取；刷新、重置、离开和身份变化均释放记录。
- [进程内测试不能证明真实浏览器、数据库或审计完整性] → 运维说明区分本次自动化证据与部署环境验证，不以单测替代真实环境结论。

## Migration Plan

1. 实施时在 `kb-web` 内完成 API、状态、页面、入口与隔离单元测试，更新 `docs/admin-audit-web.md`、`kb-web/README.md` 和根 README 的入口说明。
2. 完成定向前端测试、类型检查与静态构建后，按现有静态托管流程部署；新页面使用已有 API、权限与 SPA 回退，不需要数据库迁移或后端升级步骤。
3. 部署人员按现有角色权限流程为需要的账号配置 `audit:read`，前端不自行授予或预设角色名。
4. 回退时恢复前一版前端静态产物，后端数据和权限绑定不受页面回退影响；无需回写或修补审计记录。

# Design

## Context

动机和范围见 [proposal.md](proposal.md)。本变更同时涉及后端能力投影、前端多组件交互以及不确定写入结果，需明确设计。

- `DocumentController.delete` 已接收无请求体的 `DELETE /api/documents/{documentId}`，成功返回 `R<Void>`。`DocumentManagementService.delete` 以当前 `edit` 过滤目标，在事务中取消任务、软删除父文档和取消审核，提交后尽力清理所有版本原件。本次不修改此业务流程，也不增加恢复能力。
- `DocumentCapabilitiesService` 先检查父文档 view，再独立计算 download/edit；目前投影只有 `documentId`、`canDownload`、`canUploadVersion`、`canRetry`。其契约明确限定字段，因此需修改主能力的增量规格，不能只在前端推导删除资格。
- `pages/Documents.tsx` 中 `DocumentDetail` 承载上传、重试、文件、审核、评论和收藏。写入锁分散在各组件，目前没有覆盖整个详情页的互斥机制。
- `Session` 已负责认证、请求取消和 epoch 隔离；`useReviewScope` 在隐藏及身份变化时卸载详情内容；`FilePreview` 在关闭或卸载时取消读取并释放 Blob URL。这些机制可以复用，但单独取消网络请求不证明服务端事务未执行。
- `useAdminWrite` 提供 `X-Request-Id` 绑定及重试，既有删除接口没有该回执协议，不能直接把其“按原标识重试”语义用于整文档删除。

## Goals / Non-Goals

**Goals:**

- 通过最小新增布尔字段表达当前删除资格，以既有 DELETE 执行业务删除。
- 为确认、提交、拒绝、核对和离开页面建立可测试的状态转换，不把当前资源事实误报为历史请求回执。
- 在详情页统一阻止冲突提交，复用现有组件的身份隔离与资源释放，保持其他页面原有写入语义。

**Non-Goals:**

- 不引入新的服务、前端运行时依赖、全局资源缓存或跨标签页广播。
- 不为这次 UI 补齐增加服务端删除状态查询、请求幂等记录、数据库迁移或管理后台权限入口。
- 不承诺前端锁能串行化其他用户、其他标签页或已在服务端执行的请求；这些请求仍由现有事务和授权规则处理。

## Decisions

### 1. canDelete 使用同一次能力解析中的 edit 结果

扩展 `DocumentCapabilities` 及 TypeScript `Capabilities`，在 `DocumentCapabilitiesService` 现有 edit 结果上增加 `canDelete`，不新增权限查询、不读取版本或文件。更新 record 参数说明及接口模型描述。

前端必须显式判断 `canDelete === true`。字段缺失、读取失败、错误类型及旧响应均不启用删除。父文档 view 门禁继续存在，因此本次用户界面可达条件为 view 加 edit；这不改变直接调用 DELETE 时原有的 edit 判定。

考虑过复用 `canUploadVersion`：它会把两个动作绑在同一客户端推断上，无法明确描述接口能力，因此选择显式字段。独立 delete 权限已由用户排除。

### 2. 确认绑定父文档，不绑定选中版本

按钮放在详情操作区，危险操作样式与上传、重试区分。打开弹窗先清除旧确认快照并重新读取详情及能力，成功后保存当前目标 ID 与用于展示的标题。标题作为 React 文本渲染；不推算隐藏版本数量。确认文本说明全部版本、未完成处理/审核及无法恢复，不承诺原件立即物理擦除。

确认期间能力失效、父文档不可访问、目标或身份变化会使本次确认失效；不能在旧确认窗口恢复后自动提交。没有当前发布版本、正在解析或审核不会额外阻止有资格的整文档删除。

只提供详情页入口，避免为列表逐行读取能力，也不从管理目录扩大可读范围。现有列表和收藏、搜索入口仍通过详情页到达此操作。

### 3. 详情页局部协调写入，删除请求使用独立状态

在文档详情子树建立一个可选的操作协调上下文，身份为 session/epoch/documentId。它以同步引用维护普通写入在途数、已知未确认标记和删除独占状态，界面 state 仅负责展示。普通写入开始时同步登记，结束时报告明确成功、明确拒绝或未确认；禁止只靠异步渲染后的 disabled 阻止同一事件周期的重复提交。

上传、重试、审核命令、评论写入和收藏写入接入该上下文。删除进入确认阶段即禁止新普通写入；已在途操作继续等待自身结果，结束前禁用删除提交，不能靠卸载组件把它们算作成功取消。等待期间用户可以取消尚未提交的删除确认或离开页面，不强制为本次变更改写所有既有写入的超时策略。若已知存在未确认写入，确认界面展示“先前操作可能已经执行”的一般提示，用户再次明确确认整文档删除后才提交，不复用旧确认点击。

没有此上下文的其他页面保持原行为。审核/评论的既有请求标识、未决绑定及显式重试规则不被全局替换；处于详情页删除独占阶段时，它们的新提交与重试都受相同门禁。确认期间保留未提交草稿；取消尚未提交的确认可以恢复普通交互。

DELETE 真正提交后关闭预览，暂停进度和其他详情读取，隐藏或卸载相关内容子树使旧回调失效；独立的删除控制区继续呈现提交或核对结果。用独立请求控制器和代次处理删除，不采用 `useAdminWrite` 的服务端幂等重试功能。

### 4. 按明确响应区分成功、拒绝与未确认

建议局部状态如下，状态名属于实现建议：

| 状态 | 可用操作 | 后续条件 |
| --- | --- | --- |
| idle | 打开确认 | 当前详情及 canDelete 就绪 |
| checking | 取消、返回 | 本轮详情与能力重读完成 |
| confirming | 确认、取消 | 资格有效且普通写入不在途 |
| submitting | 等待、离开页面 | 单次 DELETE 结果 |
| uncertain | 只读核对、返回列表 | 不自动重发 |
| verifying | 等待核对、返回列表 | 当前详情与能力结果 |
| rejected | 重新读取、返回列表 | 有效身份下核对当前资格 |
| unavailable | 返回列表、主动重读 | 不显示旧内容或成功 |
| confirmed | 清理并导航 | 仅来自当前 DELETE 合法成功响应 |

请求继续使用 Session 与安全 JSON 处理，不携带 versionId、请求体或虚构的删除回执参数。现有明确成功为 HTTP 200 的成功 R 封装；正文中断、格式异常或其他无法匹配既有成功契约的响应不得通过“响应已到达”判成功。网络错误、超时、408 及 5xx 归入未确认；已发出后当前作用域内的异常取消也不得报为确定失败。400/401/403/404/409 等明确拒绝按其 HTTP 事实处理，其中 401/403 继续委托既有身份处理，404 直接清理资源并显示不可访问。其余非成功且语义不能确认的情况保守归为未确认。

删除请求及核对读取采用有界等待（建议与现有身份读取一致，默认 15 秒）；这是客户端停止等待的界限，不是服务器回滚或执行终止的证明。组件卸载导致的取消由生命周期路径处理，旧回调不能产生新提示。

### 5. 核对是读取当前资源，不是查询删除回执

用户主动核对时，先撤销旧能力快照，用独立的新读取代次请求详情及 capabilities，只有两者都可靠成功才可以提供新的确认机会。

- 任一资源读取为 404：立即屏蔽旧内容，统一显示当前不可访问，不能推断删除、归档或撤权。
- 两者成功且 canDelete=true：说明当前仍可访问且原删除结果未确认；可提供“重新确认删除”操作，但必须开启新的确认流程、重读有效事实并由用户明确提交。
- 仍可查看但 canDelete=false：展示当前资料及原结果未确认提示，不允许再次删除。
- 网络或服务故障：保持未确认和写入禁用，支持下一次主动核对或离开，不进行无界后台轮询。

即使读到了 200，先前的请求也可能仍在服务端执行。新的用户确认是一个新的删除意图，不是获得了原请求失败的证据；本次不尝试实现客户端无法证明的 exactly-once 语义。等待或核对期间可返回列表，离开不取消已提交的服务端事务。

### 6. 成功清理与路由反馈分别处理

合法成功后先使当前文档操作代次失效，停止文件和轮询、清除本页版本/审核/评论/收藏状态，再使用路由 replace 返回 `/documents`。文档中心正常挂载并重新读取服务端列表，不依赖旧页缓存或乐观删除后的总数计算。

通过当前会话内的短期提示承接“文档已删除”，提示不携带标题或正文，不使用 localStorage、sessionStorage、URL 参数或持久路由历史保存删除事实。列表重读失败单独展示，不能改变已经确认的删除结果。

继续使用 `useReviewScope` 和 Session epoch。切换文档、隐藏、离开、退出、强制改密或换用户时取消本地请求并递增代次；旧成功响应不得导航，旧读响应不得恢复内容。恢复只确认当前身份与资源，不凭 404 重新构造旧成功通知。后台发生的真实删除会在后续受保护读取中体现，本次不增加跨页面全局缓存清理协议。

### 7. 验证聚焦行为和兼容性

- 后端覆盖 view/download/edit 组合、例外 edit、未发布父文档、权限变化、依赖故障和实际 JSON 新字段。保留删除服务的任务取消、审核取消、软删除和原件清理回归；不通过新增 SQL 或文本断言证明运行行为。
- 前端用现有 Vitest/Testing Library 对删除控制器、协调逻辑和确认组件做隔离单元测试，以 Mock 请求、上下文、生命周期信号、资源清理和导航回调及可控延迟响应覆盖确认刷新、重复提交、普通写入互斥、成功清理、未确认结果的 200/404/403/503 核对，以及身份/可见性变化。
- 单元测试覆盖大整数 ID、标题安全展示、canDelete 缺失、无当前发布版本、选中历史版本和旧响应不复活；不要求挂载真实子组件或完整页面进行联合回归。
- 执行后端和前端相关独立单元测试、类型检查和构建。测试依赖全部由 Mock 或 Stub 替代，不包含集成测试、需要启动 PG、Redis、MinIO、后端服务或浏览器 E2E 环境的任务，也不包含文档内容断言、人工文档核对或规格文档校验任务；保留说明文档更新。

## Risks / Trade-offs

- [读取 404 无法确定删除结果] → 使用统一不可访问提示，保留服务端回执能力缺失这一边界；不添加存在性探测接口。
- [读取 200 时旧删除请求仍可能执行] → 保留未确认语义，禁止自动重发，后续删除必须重新确认。
- [只给删除按钮加锁无法覆盖子组件] → 以详情页可选协调上下文覆盖所有新写入和显式重试，记录在途状态；对协调门禁逻辑做隔离单元测试。
- [隐藏或导航取消了浏览器请求但服务器可能提交] → 失效旧回调，恢复只读核对，不显示“已取消删除”或伪造成功。
- [软删除不等于可恢复、原件清理也可能失败] → 确认说明不提供恢复或物理擦除承诺，原有存储对账继续承担清理补偿。
- [仅 edit 无 view 的用户仍没有此入口] → 保持既有最小披露规则，不把详情页当成新的管理删除接口。
- [能力字段的滚动发布兼容] → 新前端对缺失字段失败关闭，旧前端忽略新字段；同步更新 DTO 构造点与测试夹具。

## Migration Plan

1. 先发布新增 canDelete 投影的 kb-app；数据库、权限数据和既有删除客户端不需要迁移。
2. 发布 kb-web 静态资源，确认新能力成功读取后才允许操作；新前端暂时遇到旧 app 时禁用删除。
3. 对有 view/edit、只有 view、缺失能力字段和响应丢失的场景完成定向验证，并记录实际验证范围。
4. 回退前端即可移除入口；保留额外后端字段兼容旧前端。若回退后端，新前端会禁用删除。版本回退不能恢复已经删除的文档，不提供业务撤销承诺。

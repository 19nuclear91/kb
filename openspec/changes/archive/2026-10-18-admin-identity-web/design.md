# Design

## Context

动机和范围见 [proposal.md](proposal.md)。本设计基于现有实现：

- `kb-web/src/App.tsx`、`navigation.ts` 已有普通用户路由；`Session` 统一发送 satoken、处理 401/403，并用 epoch 隔离旧身份请求，`SessionProvider` 在恢复前台时重新确认身份。
- `IdentityManagementController` 提供用户和部门生命周期；`RoleManagementController` 提供角色及单项权限变更。两者同时映射 `/api/admin/identity` 和旧 `/api/identity`。
- 用户搜索及目标角色绑定返回 `items/hasMore/nextCursor`；部门、完整角色及权限目录仍是数组。用户搜索的部门条件只匹配主部门，没有全局总数。
- 用户/部门的部分写操作接受 version；角色接口没有版本字段，权限修改一次只接受一个 permission/granted。
- `/api/auth/permissions` 提供本人当前权限；用户、部门、角色、密码、密级、角色分配权限互不蕴含。部门目录与角色候选没有面向写入者的独立最小候选接口。
- `api.ts` 的失败消费目前取消响应体，仅生成 HTTP 状态错误。后端 `IdentityException` 有稳定大类，但最后管理员、角色引用、部门非空和编码冲突都可表现为通用 CONFLICT；全局异常处理返回 `R.fail(message)`，公开分类已丢失。
- 既有前端测试使用受控响应、模拟 DOM 和禁止真实 fetch 的测试环境；后端具备独立 MockMvc、服务替身及架构测试。

## Goals / Non-Goals

**Goals:**

- 在同一应用中形成按当前资格隔离的管理导航、数据读取和写入体验。
- 使用已有接口精确表达分页、单项提交、版本与请求标识，不扩大读取范围或伪造原子批量能力。
- 为有限身份管理写入增加兼容错误投影，允许前后端独立回退。
- 将首期验证保持在进程内可重现的行为测试、类型检查和静态构建范围。

**Non-Goals:**

- 改动服务端授权、幂等、事务、最后管理员不变量、密码政策或数据库模型。
- 引入权限缓存、统一管理员布尔值、候选读取的隐式扩权或新的身份管理权限。
- 新增独立前端工程、全局审计、外部绑定、账号资料通用编辑、用户/部门删除、批量写接口或生产部署执行任务。

## Decisions

### 1. 在既有应用内组织管理区

增加 `src/admin` 管理模块，按权限上下文、API/DTO、提交状态和三个页面组织文件，继续使用已有 `Session`、安全 JSON 编解码、布局及反馈组件。三个路由放在已认证布局中；导航增加按资格显示的管理分组，合法登录返回地址只增补三个精确站内路径，不放宽为任意 `/admin/**`。

| 路由 | 布局 | 首期动作 |
| --- | --- | --- |
| `/admin/users` | 筛选区、用户表格、目标详情抽屉、独立操作弹窗 | 创建、部门/状态/密码/密级调整、单项角色分配/解除 |
| `/admin/departments` | 部门树、节点详情、操作弹窗 | 新建、改名、移动、启停 |
| `/admin/roles` | 角色目录、详情、按用途分组的权限项 | 新建、改名、删除、单项授权/撤权 |

沿用现有中文界面和组件库，不新增全局状态或路由依赖。独立 `kb-admin` 会重复登录和部署；一个无边界的管理大页面会耦合三类读取权限，因此均不采用。

### 2. 权限上下文与会话 epoch 对齐

管理权限状态独立于 me：`loading / ready / unavailable`，ready 中的空列表代表确实无权限。上下文以当前 session epoch 为界，仅在身份 ready 后读取 `/api/auth/permissions`；本人权限读取失败只阻止管理能力，不把普通页面身份改成无效。

进入管理路由、会话重新确认及管理 403 后核对权限。账号角色和角色权限变更成功后使权限及相关管理数据失效并重读；me 核对仍复用 Session 的有界 403 流程，不根据消息推测强制改密。失去读取资格时立即关闭相关表单、停止请求并清空页面；有资格但暂时不可确认时显示重试。

页面读取和操作资格分开：

| 行为 | 当前页面所需资格之外的条件 |
| --- | --- |
| 账号搜索、详情、绑定角色摘要 | `identity:user:read` |
| 新建账号、调整主部门 | `identity:user:write`；部门候选需 `identity:dept:read` |
| 账号启停 | `identity:user:write` |
| 重置密码 | `identity:user:password` |
| 调整他人用户密级 | `identity:clearance:write`；目标不是本人 |
| 新增用户角色绑定 | `identity:role:assign`；完整候选需 `identity:role:read` |
| 解除已读取的用户角色绑定 | `identity:role:assign` |
| 部门浏览与写入 | 分别为 `identity:dept:read`、`identity:dept:write` |
| 角色浏览与写入 | 分别为 `identity:role:read`、`identity:role:write` |

表中写操作均还须当前页面的读取资格；这是可视管理界面的前提，不改变后端写接口可被独立授权的事实。缺少候选资格时保留局部说明，展示摘要已经提供的 ID；不请求完整目录、不提供裸 ID 输入。这样复用现有权限模型，无需新增最小候选接口或替用户扩权。

### 3. 按实际接口建模，区分数组与分页

统一使用 `/api/admin/identity`，不新增别名调用。管理专用 DTO 增补 version，避免把普通 me 的 Identity 类型误当完整可写摘要。用户、部门、角色 ID 在浏览器内使用精确字符串身份；回传 ID 和 version 按接口数值要求经安全编解码输出，不能直接把 ID 字符串原样放入数字字段。

| 业务 | 入口 | 关键消费约束 |
| --- | --- | --- |
| 用户检索 | `GET /users/search` | q、departmentId、enabled、limit/cursor；改变条件清游标，限制请求输入；无 total |
| 用户详情 | `GET /users/{userId}` | 身份摘要和版本，缺部门读取权时仅展示已有 departmentId |
| 已绑定角色 | `GET /users/{userId}/roles` | 分页，读取后续页；不扩展角色功能权限 |
| 创建用户 | `POST /users` | username/displayName/departmentId/clearanceLevel/initialPassword |
| 调整部门或启停 | `PATCH /users/{userId}/department`、`/enabled` | 独立请求，带 version，不夹带 clearanceLevel |
| 重置密码 | `PATCH /users/{userId}/password` | newPassword，不套用用户版本字段 |
| 调整密级 | `PATCH /users/{userId}/clearance` | clearanceLevel/version；字典来自 `/api/auth/security-levels` |
| 分配或解除角色 | `POST /users/{userId}/roles`、`DELETE /users/{userId}/roles/{roleId}` | 一项一请求，DELETE 解除不存在绑定时 404 不能伪装成功 |
| 部门目录和详情 | `GET /departments`、`/departments/{departmentId}` | 数组构树，保留停用节点和根节点 |
| 部门生命周期 | `POST /departments`；`PATCH /departments/{departmentId}/name`、`/parent`、`/enabled` | 创建 code/name/parentId；后三项带 version，根父节点用 null |
| 角色目录和详情 | `GET /roles`、`/roles/{roleId}` | 目录数组与独立详情，不虚构分页或成员数 |
| 权限目录 | `GET /permissions` | 返回全部 code/description；分组只影响展示 |
| 角色生命周期 | `POST /roles`；`PATCH /roles/{roleId}`；`DELETE /roles/{roleId}` | 创建空权限；改名不改 code；删除无引用；没有 version |
| 单项角色权限 | `PUT /roles/{roleId}/permissions` | permission/granted，一次只改一项，没有 version |

除 `/api/auth/**` 外，表中路径均相对 `/api/admin/identity`。用户检索调用既有 GET，q 仅进入该 API 请求，不写页面地址、持久状态或诊断；密码始终只在写请求体中传输。

### 4. 共用写操作状态，明确提交与刷新分别成功

管理表单共用提交状态：草稿、提交中、已确认、结果不确定、明确拒绝及提交成功但刷新失败。一次逻辑操作生成一个请求标识，统一通过 `X-Request-Id` 传递；请求体有可选 requestId 时不重复放入，避免两处不一致。绑定记录包含方法、目标、动作、精确提交值和必要版本，不只绑定表单是否打开。

提交中锁定表单与重复触发。网络失败保留内存中的原绑定；仅允许用户明确选择匹配重试或重新读取，不自动补发。更改内容、目标或基于新版本确认操作时使用新标识；结果不确定时明确开始新操作应提示旧提交仍可能已执行，不把重开表单当作取消服务端写入。已有后端不承诺校验任意同标识内容，因此客户端必须维持绑定，服务端幂等语义本次保持原样。

版本冲突后保留可核对的非敏感意图，读取最新事实，再由用户确认新提交。写入已收到成功但列表/树刷新失败时，保留成功回执并只重试读取。身份变化、关窗和离页清理密码及待提交状态，晚到回执不能修改新目标。

新建及密码重置表单提供两次密码输入，仅检查必填和一致性，强度由既有服务端政策判定，不硬编码 8 位或增加字符类别要求。新建与角色分配分为两个明确动作，密码不出现在回执或复制功能中。

### 5. 组织树和角色权限沿用当前粒度

部门树由 parentId 构造；移动使用独立目标选择弹窗，排除本节点、后代和停用目标，根部门对应 null。客户端候选过滤提升可用性，服务端仍负责最终层级、依赖和版本判定；不采用自动提交的拖拽移动。所有部门变更成功后重读整树和当前节点，以免后代路径显示失真。

角色权限按服务端目录分组，授予/撤销均经明确确认，按单项 PUT 提交。同一角色存在未确认的写入时锁住其他修改；失败或结果不确定时停止后续操作并提供核对，不形成后台写队列。角色成员和 ACL 引用数量没有查询契约，本页仅解释删除约束，不推测数量或加载越权明细。界面的串行只约束本页，角色接口仍没有跨管理员的版本检测承诺。

批量勾选后统一保存需要新原子接口及冲突模型，不属于首期；角色目录和部门目录先沿用既有数组，规模扩大时另行设计分页与树懒加载。

### 6. 通过有限来源原因增加管理错误投影

保持公共 `R`、全局异常处理方法签名和旧身份别名响应。为 `IdentityException` 增加可选的类型化原因元数据或等效的兼容表示，保留现有构造方式、errorCode/httpStatus 和领域判断。新增原因由部门非空、角色引用、管理不变量及编码冲突的实际检查点提供；不修改它们原有类别、HTTP 状态或事务边界。

在 app 中增加仅作用于两个身份管理控制器的错误适配器，按方法与精确路由模板白名单选择新投影。白名单即上表所有写入口，排除两个控制器的读取、外部身份接口和全部 `/api/identity` 别名；未命中时交回既有处理。处理器只适配已识别领域异常，不以原始 DataAccess/远端异常生成业务原因。

新响应示例：

```json
{"code":500,"message":"角色仍有引用，请先处理绑定或授权。","data":null,"reasonCode":"ROLE_IN_USE"}
```

| 原因 | HTTP | 页面处理 |
| --- | --- | --- |
| INVALID_VERSION | 409 | 提示重新读取并确认新版本 |
| DEPARTMENT_NOT_EMPTY | 409 | 提示先处理启用成员或子部门 |
| ROLE_IN_USE | 409 | 提示先处理用户绑定或资源 ACL 引用，不提供强制删除 |
| LAST_MANAGER_REQUIRED | 409 | 说明需要保留其他合格管理员 |
| IDENTIFIER_CONFLICT | 409 | 在当前创建表单提示用户名或编码已存在 |
| INVALID_HIERARCHY / INVALID_PARENT / CONFLICT | 409 | 提示层级或当前状态冲突，读取后重新确认 |
| INVALID_REQUEST | 400 | 提示输入不符合要求；由表单定位已有客户端校验项 |
| FORBIDDEN / DISABLED / PASSWORD_CHANGE_REQUIRED | 403 | 保持现有 me 核对，重新确认权限或进入改密流程 |
| NOT_FOUND | 404 | 清理失效目标并允许重新读取 |
| UNAUTHORIZED | 401 | 继续由 Session 清理本地会话 |

message 从有限分类映射固定文本，data=null；不携带输入、对象字段、数量或异常正文。无可用细分时保留通用分类或原响应。前端只在白名单管理写请求失败时读取最多 8 KiB 的 JSON 错误体，要求 reasonCode、HTTP 和 code=500/data=null 形状匹配；未知值、超限、非 JSON 和旧后端都回退当前 HTTP 提示。不得根据 message 匹配原因，普通搜索、文档、会话及其他 API 保持原消费行为。

### 7. 以独立行为测试和静态构建验收

前端继续 Vitest、受控 Promise/流和模拟 DOM；对权限组合、分页、版本冲突、结果不确定、身份/目标切换、敏感输入清理及逐项权限写入做内存单元测试。后端使用服务/Mapper 替身与 standaloneSetup MockMvc，验证新增原因的来源、精确路由白名单、错误脱敏和旧入口兼容；ArchUnit 只检查类依赖，不启动应用。

运行前端 typecheck、全部前端单元测试和 build；后端只定向运行任务白名单中的内存业务用例与架构检查，禁止全量 Maven 测试。既有 `RoleManagementControllerTest` 混有 `everyRoleEndpointHasOperationAndResponses` 文档断言，不能按整类运行，只选择任务清单列出的四个业务方法。

执行范围排除集成测试、端到端测试、完整 Spring 应用或 HTTP 服务启动、监听端口，以及连接数据库、Redis、MinIO、容器、嵌入式数据库、真实浏览器和供应商服务的任务。不新增或执行 README、操作说明、配置示例、Javadoc、OpenAPI 文档注解的内容断言；文档只交付并人工核对，文档/规格校验不作为实施测试任务。此处验收只证明上述离线业务行为与静态构建结果。

## Risks / Trade-offs

- [权限组合可能不完整] → 按具体读取依赖降级并说明原因，不隐式开放目录；部署时可按职责显式配置权限组合。
- [他人修改权限会使界面暂时滞后] → 路由、恢复、403 和相关成功写入后重读；所有请求仍由服务端按当前事实判定，不提供浏览器实时推送保证。
- [同一账号或角色被其他管理员修改] → 用户/部门版本冲突需重新确认；角色沿用服务端已有粒度并重新读取，不声称获得新增版本保护。
- [旧提交结果不确定时用户又发起新动作] → 显式保留不确定状态和原请求绑定，避免自动重试；查询只能证明当前事实，不能伪造旧请求的原子撤回。
- [目录数组在大组织中体积较大] → 首期遵循既有接口、不产生全量用户查询；目录分页和树懒加载作为独立后续变更。
- [异常适配影响旧入口] → 控制器范围、方法及路由模板共同限定，覆盖旧别名与普通业务回归；不修改公共 R。

## Migration Plan

1. 实现阶段先发布兼容的后端可选错误投影，无 DDL 或权限目录变更。
2. 再发布同一 `kb-web` 静态产物，继续沿用现有同源 `/api/**` 和页面回退约定；更新三个管理路径的说明。
3. 新前端可以先连接旧后端，仅失去细分提示；旧前端可以连接新后端，继续使用原状态和字段。
4. 回退时恢复旧静态产物即可撤下管理区，后端可保留或独立回退；不删除账号、部门、角色、审计或任何已提交业务数据，不重放写操作。

以上为交付和回退说明，本提案不执行部署或外部链路验证。实现完成时记录实际执行的内存单元测试、架构检查、类型检查和静态构建结果。

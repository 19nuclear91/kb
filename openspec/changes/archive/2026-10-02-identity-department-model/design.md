# Design

## Context

当前 `kb-app` 已通过 `sys_user.dept_id`、`sys_dept.path`、角色关联表和 `PermissionService` 计算有效主体；`AuthService`
再把当前会话转换为 `QuotaPrincipal`，`kb-ai` 只通过内部接口读取该主体。现有模型缺少外部身份绑定、管理写路径、部门生命周期状态、并发版本和变更审计。详见
proposal.md 的 Why；本设计落实 `identity-department` 规格。

## Goals / Non-Goals

**Goals:**

- 让内部用户 ID 成为权限、配额和审计共同使用的稳定主键，并把外部认证 subject 映射到该主键。
- 在 PostgreSQL 中安全维护无环部门树、物化路径、用户主部门和启停状态。
- 通过一个业务服务边界提供受保护的查询和写操作，保证权限解析、配额主体和管理接口读取同一份事实。
- 让每次成功的身份/部门变更与不可变审计摘要在同一事务中提交，并支持请求幂等和并发冲突检测。
- 通过增量迁移保留现有用户、部门、角色、ACL 和开发种子数据的标识及语义。

**Non-Goals:**

- 本变更不接入具体 SSO/OIDC 厂商、不实现登录回调页面，也不替换 Sa-Token 会话机制。
- 本变更不改变空间/文档 ACL、部门授权向下生效、密级过滤或配额 Lua 账本的业务规则。
- 首期不支持一个用户同时拥有多个主部门、不做部门级显式 deny、不提供硬删除身份或部门。

## Decisions

### 1. 保留内部主键，新增外部身份映射

继续使用现有用户 ID 作为所有授权、配额和审计的内部主键，保留 `sys_user.dept_id` 作为唯一主部门来源。新增外部身份映射表，按规范化的
`provider` + `subject` 建立唯一约束，并反向索引用户；外部 subject 只用于服务端查找，不通过管理 API
回显，也不写入审计摘要。这样可以兼容当前以数字用户 ID 建立的开发会话，同时允许后续 SSO 将不同供应商的 subject 绑定到同一内部用户。

考虑过直接把 provider 和 subject 放进 `sys_user`，但一个用户可能先后或同时拥有多个认证源，且认证绑定生命周期与用户资料不同，因此采用独立映射表。

### 2. 用版本化物化路径维护部门树

在现有部门记录上补充稳定编码、启停状态和乐观锁版本；继续维护物化路径以支持祖先链查询。创建、重命名、移动和停用统一进入身份/部门服务：事务内锁定待变更节点及其相关祖先/后代，先检查父节点存在、启用状态和环，再更新节点及后代路径。移动失败或版本不匹配时整笔事务回滚，避免出现半棵树的新旧路径混合。

考虑过运行时递归 CTE 代替路径，但现有权限查询已经依赖路径且部门授权需要快速反查祖先，继续使用路径能减少热路径改造；代价由写操作锁和路径更新承担。

### 3. 用软停用和服务层引用校验保护归属

用户和部门均采用启停状态，不删除仍被 ACL、角色、文档或审计引用的记录。用户只能归属到启用部门；停用部门前必须没有启用子部门和主部门用户，或先在同一事务中完成显式迁移。
`PermissionService` 和配额主体解析每次都检查用户与主部门状态，管理端不能通过请求体或身份头覆盖解析结果。

### 4. 由身份/部门服务集中承载管理写路径

在 `kb-app` 的 auth 模块增加身份、部门查询和管理写服务及受保护接口。写接口接收目标实体的版本/更新时间条件，失败时返回可区分的不存在、停用、冲突和禁止错误；读取接口只返回管理者有权看到的摘要。现有
`AuthService.quotaPrincipal` 和 `PermissionService.resolve` 复用同一个服务端主体解析逻辑，`QuotaContextController`
的响应契约保持兼容，`kb-ai` 不直接连接业务库。

管理权限沿用服务端角色/权限判定，首期由有效的系统管理角色控制；不把客户端声明的角色、部门或密级当作授权依据。

### 5. 事务内追加审计并以请求标识幂等

新增 append-only 身份审计表，保存事件 ID、请求 ID、操作者内部用户 ID、目标类型/ID、操作、时间和脱敏前后摘要，并对请求
ID（在同一操作域内）建立唯一约束。成功变更与审计写入同一数据库事务；重复请求命中唯一约束时返回原操作结果或等价幂等结果。审计摘要不保存会话
token、完整外部 subject、密码或业务正文。失败校验不产生成功事件，数据库错误整体回滚。

考虑过把审计只写 Redis，但身份事实的审计必须在业务库中可恢复、可查询，且不能依赖 AI 服务或缓存可用性。

### 6. 采用向后兼容的数据库迁移顺序

新增 Flyway 迁移先创建外部身份映射和审计表，再为现有用户/部门补齐默认编码、启用状态和版本值，最后添加非空/唯一/外键约束与索引。历史用户
ID、部门 ID、角色关联、ACL 和 `dept_id` 不重编号；开发种子继续可重复执行。迁移完成后，旧的数字用户会话仍走原有解析路径，SSO
映射作为新增路径接入。

## Risks / Trade-offs

- [Risk] 移动大部门树会锁定并更新大量后代路径，影响管理写延迟。→ 对树写操作设置超时和受控批量上限，记录耗时指标；权限热路径继续使用索引化路径读取。
- [Risk] 物化路径更新与并发管理操作可能产生锁竞争。→ 使用固定锁顺序、版本条件和事务回滚，并为冲突返回可重试错误。
- [Risk] 外部身份绑定错误会把会话指向错误用户。→ provider/subject 唯一约束、仅允许高权限绑定、绑定变更写审计，认证回调仍由后续
  SSO 适配层负责校验。
- [Risk] 审计摘要长期增长。→ 只保存必要字段和摘要，建立时间/目标索引并把保留与归档策略作为运维配置；不把正文写进审计。
- [Risk] 现有开发种子缺少外部身份数据。→ 迁移不强行虚构生产 subject；保留数字开发登录，并在测试中显式覆盖映射绑定路径。

## Migration Plan

1. 增加数据库迁移和领域模型，创建外部身份映射、身份审计表及部门/用户状态、编码、版本字段。
2. 为现有部门和用户回填稳定默认值并验证唯一性、外键和路径完整性；保持 `sys_user.dept_id` 与既有 ACL 不变。
3. 发布身份/部门服务的只读主体解析改造，确认现有检索与 AI 配额调用结果不变。
4. 发布受保护的管理写接口、并发校验和事务审计；先在开发环境启用管理操作，再开放给生产管理员。
5. 为选定 SSO 提供方创建外部身份绑定数据并灰度验证；出现问题时停用新写接口，保留旧会话解析，数据库迁移按 Flyway 的备份恢复流程回滚。

## Open Questions

无。供应商 SSO 选择和审计保留期限不影响本变更定义的内部模型与接口契约，可在后续适配和运维变更中确定。

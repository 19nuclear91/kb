# Design

## Context

当前 Worker 使用 PostgreSQL 的 `kb_parse_task` 作为持久队列：领取时递增 `attempts`，通过 `lease_until` 回收失联任务，失败时写回
`pending`，由巡检把达到上限的任务标为 `failed`。`TaskFailureAlert` 只有日志实现，Actuator 虽暴露 `metrics`
端点但没有解析域指标；业务应用的文档重试会把同一任务的尝试次数和错误清零。相关现状见 `ParseTaskRunner`、`ParseTaskMapper`、
`ChunkPublisher` 和 `DocumentManagementService`。

本设计必须兼容已有的 `pending/running/succeeded/failed` 状态、同版本幂等发布和基于 `ROLE_ADMIN`
的管理授权，同时让崩溃恢复、死信处置和外部观测具有可追溯的数据库事实。

## Goals / Non-Goals

**Goals:**

- 让租约恢复、可重试失败、永久失败和死信处置形成可收敛的状态路径。
- 使用指数退避和失败分类避免暂时性依赖故障快速耗尽尝试次数。
- 保留执行周期、失败摘要、死信处置和重放历史，并保证重放请求幂等。
- 为用户级重试和管理员全局死信操作提供一致的权限、审计和脱敏边界。
- 以低基数 Micrometer 指标和持久化结构化事件支持外部监控系统。

**Non-Goals:**

- 不把 PostgreSQL 队列迁移到 RabbitMQ、Kafka 或其他外部消息系统。
- 不在 Worker 内实现具体的邮件、短信或告警平台客户端；`TaskFailureAlert` 仍是可替换适配边界。
- 不改变文档解析器、切块器、embedding 模型或检索排序语义。
- 不为历史解析结果推断缺失的来源位置或重建旧的失败堆栈。

## Decisions

### 1. 以附加死信记录保持任务状态兼容

保留 `kb_parse_task.status` 的现有四个值，避免旧 Worker、旧客户端和回滚版本无法识别新增枚举。通过下一版 Flyway 迁移增加任务恢复字段：

- `next_attempt_at`：下一次允许领取的时间，空值表示立即可领取；
- `failure_class` 和 `failure_code`：稳定的 `PERMANENT`、`RETRYABLE`、`UNKNOWN` 分类及有限长度代码；
- `execution_generation`：每次人工重放递增，区分同一 `version_id` 的不同执行周期；
- 必要的失败时间和脱敏摘要字段，避免把完整堆栈写入业务表。

新增 `kb_parse_task_dead_letter` 保存进入死信的执行周期、任务和版本、尝试次数、分类、代码、受限原因摘要、进入时间、处置状态、操作者、重放请求标识和处置原因。新增
`kb_parse_task_event` 作为追加式事件历史，记录领取、退避、租约失守、重试、死信、重放和成功等关键转移。死信表便于查询当前未处置项，事件表保留完整时间线。

选择附加记录而不是直接新增 `dead_lettered` 任务状态，是为了兼容旧状态检查和安全回滚。业务上仍把有未解决死信记录的失败任务视为
`dead-lettered`；文档版本使用现有 `failed` 索引状态，不会误报为可检索。

### 2. 领取条件和退避保证恢复收敛

任务领取 SQL 在 `pending` 分支增加 `next_attempt_at <= now()` 条件；运行中租约过期仍可被 `FOR UPDATE SKIP LOCKED`
回收。领取时继续递增 `attempts`，因为进程崩溃也必须消耗一个执行周期，不能靠失败写回计数。

可重试失败使用指数退避：默认基准 30 秒、每次加倍、上限 15 分钟，并加入约 ±20% 的抖动；这些值由 Worker
配置覆盖。永久错误跳过退避直接写入死信。未知错误按可重试处理并受任务的 `max_attempts` 限制。每次状态变更、版本状态更新和事件/死信记录在同一数据库事务内完成。

非最终失败将文档版本恢复为明确的待重试状态，避免 `index_status=parsing` 长期悬挂。达到上限或永久失败时，任务保留 `failed`
，文档版本置为 `failed`，并在同一事务中创建唯一的死信记录。租约失守只生成恢复事件，失去租约的 Worker 不得写失败状态。

### 3. 在 Worker 边界集中进行失败分类

新增失败分类器，将确定性输入问题和解析器错误映射为 `PERMANENT`，对象存储/HTTP 超时、限流、embedding 暂时性失败和数据库暂时不可用映射为
`RETRYABLE`；无法识别的异常映射为 `UNKNOWN` 并按可重试处理。`LeaseLostException`
作为控制流单独处理，不生成失败事件。分类器同时产生稳定代码和脱敏摘要，告警、指标、任务表和死信表共用这套值。

### 4. 用新的执行周期实现用户重试和管理员重放

现有文档级重试保留 `edit` 权限边界，但改为在事务内关闭当前未解决死信、递增 `execution_generation`
、清零当前周期的尝试字段并重新排队，同时保留旧死信和事件历史。管理员 API 位于 `/api/admin/parse`，复用
`IdentityManagementAuthorizer` 的 `ROLE_ADMIN` 检查，支持分页查询未处置死信、按分类/时间筛选和提交带原因的重放。

管理员重放和死信处置要求请求标识；在事件表上建立请求标识和操作类型的唯一约束，使超时重试最多创建一个新执行周期。响应只返回任务、版本、状态、分类、尝试次数和受限错误摘要，不返回对象
key、文件正文或完整堆栈。管理写操作沿用身份模块的追加审计边界，记录操作者、目标、请求标识、时间和脱敏原因。

### 5. 用持久事件和适配器保证告警不丢不重

死信转移、最终失败巡检、租约失守异常、队列老化和告警发送失败先写入结构化事件/告警投递记录，再由轻量调度器调用
`TaskFailureAlert`。投递记录使用事件类型、任务、执行周期和告警窗口组成去重键；发送失败保留待投递状态并增加失败指标。默认实现继续写结构化日志，生产环境可替换为
webhook 或 Alertmanager 适配器。

告警在事务提交后由投递器发送，避免业务事务回滚后出现伪造告警。巡检发现耗尽任务时复用同一死信转移路径，因此进程崩溃导致的最终失败与直接异常失败使用同一告警契约。

### 6. 通过低基数 Micrometer 指标暴露运行健康

Worker 注入 `MeterRegistry`，记录任务领取、成功、重试、死信、租约失守、告警投递失败计数和任务处理耗时分布。定时数据库查询提供待处理深度、未解决死信深度和最老待处理任务年龄
gauge。标签只使用状态、结果和失败分类等有限集合，不使用任务 ID、版本 ID、对象路径或用户输入。继续使用现有 Actuator `metrics`
端点，不绑定 Prometheus 或其他通知依赖；阈值规则由外部监控系统配置。

### 7. 以增量迁移和可回滚顺序发布

新增 Flyway 迁移先创建可空字段、历史表、索引和请求去重约束；为历史任务填充 `execution_generation=0` 和可立即领取的
`next_attempt_at`，不为历史失败自动发送告警。旧的 `failed` 任务可由一次性巡检补写标记为 legacy 死信，保留原错误摘要。

先部署兼容新字段但仍能读取旧任务的 Worker 和 App，再启用管理员 API、事件投递和指标告警规则。回滚代码时保留迁移产生的附加表和字段，旧
Worker 继续按原四种状态领取任务；禁止回滚脚本删除历史或约束，避免丢失处置证据。

## Risks / Trade-offs

- [Risk] 每次失败增加事件和死信写入，数据库写放大 → 只记录受限摘要和关键状态转移，并为事件/死信按任务、状态和时间建立索引。
- [Risk] 失败分类错误会让永久错误反复重试或暂时错误过早死信 → 未知异常默认可重试，分类代码可观测，管理员可在死信中重放。
- [Risk] 指标 gauge 的周期查询给数据库增加负载 → 使用索引覆盖的聚合查询和可配置采样周期，避免逐任务查询。
- [Risk] 告警投递器自身故障造成通知延迟 → 投递记录持久化、失败可重试，并单独暴露告警投递失败指标。
- [Risk] 历史 `failed` 任务缺少完整执行时间线 → 以 legacy 标识补齐可查询死信摘要，不伪造不存在的尝试细节。

## Migration Plan

1. 部署追加字段、事件表、死信表、索引和请求去重约束的 Flyway 迁移。
2. 发布兼容 Worker：失败分类、退避、死信事务、事件记录、告警投递和指标先在日志/Actuator 中运行。
3. 发布 App：用户重试改为新执行周期，增加管理员死信查询/重放和审计；旧文档接口继续返回兼容的任务状态。
4. 为旧的终态任务运行一次 legacy 对账，补齐可操作的死信摘要但抑制迁移告警。
5. 在外部监控中配置队列年龄、死信深度、租约失守率和告警投递失败阈值，逐步启用通知。
6. 回滚时先停止新重放入口和告警规则，再回退应用代码；保留数据库迁移和历史数据，旧 Worker 继续处理 `pending/running` 任务。

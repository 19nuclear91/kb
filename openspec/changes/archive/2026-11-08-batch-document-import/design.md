# Design

## Context

动机与已确认产品范围见 `proposal.md`。本设计涉及 app、前端、网关、数据库迁移和对象对账，满足独立设计文档的创建条件。

当前实现事实：

- `DocumentUploadService.upload` 校验文件与空间 edit，计算 SHA-256，使用随机 `documents/` 对象键写入存储，然后调用 `DocumentWriteService.create`。后者同事务创建文档、版本和解析任务；当前没有上传请求绑定或持久回执。
- 当前上传路径对写库异常立即尽力删除对象。这种处理不能直接用于批量幂等路径：数据库提交回执丢失时，异常不证明事务没有提交。
- `DocumentWriteMapper.insertVersion` 从实际空间读取发布策略；`content_hash` 是普通索引，相同名称、内容允许对应不同文档。
- `UploadDialog.vue` 每次持有一个 File；`Session` 在身份变化、隐藏和恢复时取消请求并使旧回调失效。私有草稿不存入浏览器持久存储。
- `StorageReconciliationMapper.xml` 的清理引用只来自未删除文档的版本；宽限期不能替代在途上传的持久引用保护。
- gateway 的 dev/prod 业务路由没有 `/api/document-imports`，现有业务响应等待为 10 秒。新增路径必须有实际路由和认证回归。
- 普通解析已具备持久队列、租约、重试及发布门禁；缺少第三方解析器时新文件保持排队。批量受理不应依赖解析器就绪。

## Goals / Non-Goals

**Goals:**

- 用持久项身份保证每项至多创建一份文档，跨请求、实例和登录保留可核对事实。
- 对象网络操作位于事务外；结果提交、失效恢复与清理保护具有明确的原子边界。
- 浏览器队列恢复只依赖当前身份、任务读取和重新选择的匹配文件。
- 用进程内离线竞争及故障注入测试覆盖关键控制流，明确 Mock、内存替身和模拟 DOM 所能提供的验证证据。

**Non-Goals:**

- 不将整个批次做成跨文件大事务，不新增解析队列、消息中间件或服务端读取用户磁盘的能力。
- 不以名字或内容摘要进行全库查重、秒传、文档合并或自动版本更新。
- 不引入分片续传、浏览器持久文件缓存、管理员跨用户任务中心或自动清除已导入文档。

## Decisions

### 1. 独立导入协议，复用底层文档创建

新增 `com.zhishiku.kb.app.document.imports`，按 web / model / service / mapper 组织。批次创建提交 JSON 清单，文件逐项发送 multipart；每个文件仍进入既有文档、版本和解析任务模型。

通过事务服务复用 `DocumentWriteService.create` 或抽取其同事务写入协作者，使文档创建与项回执保存使用同一连接、同一事务。批量路径自行协调存储和执行代次，不直接调用现有包含补偿删除的 `upload()`。抽取文件校验、文件名规范化与摘要计算时，保留现有单文件入口行为及测试。

取舍：前端循环旧接口不能提供幂等与恢复；一次发送全部文件会扩大请求体、失败重传和事务边界。清单加逐项文件能保留部分成功并限制内存与网络占用。

### 2. 固定清单与文件匹配

创建请求包括 `spaceId`、字典内 `securityLevel` 和有序 `items`。每项包括客户端生成的 `itemKey`、规范化 `fileName`、`title`、`sizeBytes`、`sha256`；空白标题在绑定前规范化为文件名。条目身份不取文件名或摘要。

前端逐文件计算 SHA-256，最多同时计算一个文件，使用可终止的 Worker 与 Web Crypto；按已取得的单文件上限控制单次读入，避免同时把整个批次载入内存。服务器重新按实际字节核验大小、摘要和文件格式，不信任浏览器 MIME、扩展名或摘要声明。

本地显然无效的文件显示原因，用户移除或修正后才能提交清单，不静默漏项。服务端创建阶段整体验证清单结构和容量，实际内容无效在对应项上传时独立失败。恢复时匹配规范化文件名、大小和 SHA-256；同名同大小但内容不同不能替代原项。多份完全相同文件可对应不同 itemKey，页面由用户明确选择要恢复的项，不按摘要自动合并。

取舍：只有名称与大小不足以确认原文件；在上传后才首次绑定摘要，会使首次响应丢失后的换文件无法可靠判定。提前冻结摘要增加一次客户端读取，但能给出稳定的恢复合同。摘要不是读取、下载或秒传凭证。

### 3. 持久模型与状态

新增下列三张表，实际迁移号在实施时使用当前最新版本之后的可用编号：

| 表 | 关键内容与约束 |
| --- | --- |
| `kb_document_import` | id、owner_user_id、create_request_id、manifest_digest、space_id、security_level、item_count、total_bytes、创建时间；`(owner_user_id, create_request_id)` 唯一 |
| `kb_document_import_item` | id、import_id、item_key、ordinal、固定文件名/标题/大小/摘要、状态、revision、当前 attempt_id、document_id/version_id/parse_task_id、固定失败代码；`(import_id, item_key)` 与 `(import_id, ordinal)` 唯一 |
| `kb_document_import_attempt` | id、item_id、request_id、请求绑定摘要、执行代次、服务端生成的唯一 object_key、状态、lease_until、认证代次、起止时间及固定诊断；`(item_id, request_id)` 与 object_key 唯一 |

文件项状态：

```text
PENDING ----> PROCESSING ----> ACCEPTED
                  |
                  v
                FAILED ----> PROCESSING
```

- `ACCEPTED` 为不可逆的上传受理终态，记录固定三元组；文档后续删除、搬迁、解析失败均不能把它变回可上传。
- `FAILED` 只表示已确认没有创建文档且本次执行资格已撤销。恢复使用用户新发起的尝试和最新 revision；不可重试的内容错误需另建正确清单。
- 网络端的“待确认”是客户端认知，不能由异常直接写成数据库 FAILED。数据库本身不可达时保留最后的 PROCESSING，待可信重读或恢复事务判定。
- 尝试状态为 ACTIVE、ACCEPTED、INVALIDATED。ACTIVE 即使超过租约时间，也必须在锁内持久化失效后才允许释放对象保护。
- 批次状态由项聚合：存在 PENDING/PROCESSING 为 OPEN；全 ACCEPTED 为 COMPLETED；全为终态且有成功有失败为 PARTIAL_FAILED；全 FAILED 为 FAILED。失败项主动恢复可回到 OPEN。“完成”仅表示文件受理阶段结束。

首期保留任务、项和请求绑定记录，不增加定时删除。此为设计默认，保证跨登录查询和旧请求去重；日后增加保留期必须同时定义幂等墓碑与过期响应，不能单独删回执。

### 4. HTTP 接口与错误语义

全部接口采用当前会话，响应 `Cache-Control: no-store`，沿用 R 包装与精确 64 位身份。JSON 拒绝未知字段、重复键、非法 Unicode、溢出和尾随内容，错误不回显文件内容或对象键。

| 接口 | 用途 |
| --- | --- |
| `GET /api/document-imports/capabilities` | 返回当前容量与格式限制；可上传空间和密级仍用既有候选接口 |
| `POST /api/document-imports` | `X-Request-Id` 绑定当前用户与规范化完整清单；创建批次及全部项，返回固定批次身份 |
| `POST /api/document-imports/resolve` | 只读按本人 create requestId 核对创建结果；没有记录不证明旧请求永远不会提交 |
| `GET /api/document-imports` | 本人任务游标分页，按 id 倒序 |
| `GET /api/document-imports/{importId}` | 批次摘要、同次读取的四类计数、当前可继续上传资格 |
| `GET /api/document-imports/{importId}/items` | 按 ordinal 正序游标分页，返回受理状态及允许披露的原清单字段 |
| `GET /api/document-imports/{importId}/items/{itemId}` | 核对单项 revision、固定回执或失败状态 |
| `POST /api/document-imports/{importId}/items/{itemId}/file` | 一个 file、expectedRevision 和 `X-Request-Id`；核验文件匹配后处理本项，明确成功返回固定受理回执 |

请求标识复用项目既有 1–256 code point、去首尾空白、拒绝控制字符的绑定约定，前端生成随机 UUID。相同创建标识、相同规范化清单返回原批次；同标识不同内容 409。同一上传尝试标识绑定项、expectedRevision 与固定文件描述；旧请求不得因项已失败自动开启新尝试。

已 ACCEPTED 的匹配项返回原受理三元组，即使 expectedRevision 已旧；相同项的新主动尝试同样不能再创建文档。仍须校验归属、当前写资格及上传内容匹配。失效旧尝试返回冲突并要求读取，新的主动尝试必须使用新 requestId 和最新 revision。

- 400：清单、标识、版本或文件描述非法；创建未通过时无部分批次。
- 401/403：当前身份或上传资格被拒，浏览器暂停该批次后续发送。
- 404：任务/项不存在或不属于本人，统一处理。
- 409：绑定内容不符、项正被处理、旧执行或 revision 冲突；重读后由用户决定下一步。
- 413/415：文件大小或内容格式拒绝；已合法绑定执行的项保存对应固定失败事实。
- 429：实例/用户上传容量不足；没有领取新执行，前端使用导入专用提示，不复用“部门 AI 额度不足”。
- 503 或损坏/丢失响应：结果需核对，不能凭 HTTP 状态认定事务回滚。

客户端在任何不确定响应后仅发有界读取；读取确认 ACCEPTED 才记成功，确认 FAILED/PENDING 且可上传后由用户主动重试。创建结果未知时保留原 key，主动匹配重试只使用同一清单；刷新后通过本人任务列表找到已持久记录，不自动新建替代批次。

### 5. 项级受理、崩溃恢复与存储协调

每项经过下列边界：

1. 在 multipart 解析前对新增文件路径进行身份与实例/用户实际在途准入；容量不足不创建执行。容器临时文件和入站体大小仍受显式限制。
2. 先核对实际文件名、大小和摘要与固定清单一致，再进入短事务检查本人归属、当前 edit/身份和 revision。已 ACCEPTED 的项只返回原回执；否则锁项并绑定尝试，领取执行代次、记录新唯一 object_key 与租约，项变为 PROCESSING。相同标识在途只返回冲突，不再次写存储。文件匹配检查只对已完成归属与当前上传资格预检的项执行。
3. 事务外核验实际文件大小、摘要与格式，再写该尝试独有对象键。新增面向导入的有界存储写入入口，使用现有凭据与桶、显式 SDK 调用超时；不改变旧存储调用的默认语义。检查本次截止与取消，实际工作未退出前保留本地容量。
4. 最终短事务锁项及实际目标空间，清理请求内 ORM 查询缓存并重新解析身份/认证代次、主部门、强制改密、空间未归档与 edit。验证同一 ACTIVE 尝试、代次和未到截止，再按实际空间策略创建文档、版本和解析任务，保存项三元组及 ACCEPTED 回执、终结尝试。全部同事务提交，失败无部分回执。
5. 获得确定提交结果后返回。提交是否成功不可确认时，不直接删除对象、不新建执行、不把项改为 FAILED；查询或恢复流程从持久事实收敛。

内容格式或存储调用在最终提交开始前确定失败时，使用独立短事务锁项并核对当前尝试，原子撤销资格及保存 FAILED；原件有无落桶仍可未知，由对账回收。失败记录事务自身也未确认时保持待核对。已经进入最终提交但未取得确定结果的异常不能复用此失败分支；必须先读取并锁定持久事实，不能覆盖可能已提交的回执。

恢复调度独立于解析器和当前用户在线情况：按上限扫描到期 ACTIVE，短事务锁对应项并重读。若已受理则保留原结果；仍是该到期执行时原子改为 INVALIDATED、项 FAILED、递增 revision。它只结束旧执行资格，不自动重新上传或创建文档。读状态本身不制造新执行。

续传为重新上传完整的匹配文件；新尝试使用新对象键。旧请求即使继续完成存储写入，也不能通过代次及状态门禁；它的晚到失败不能覆盖新尝试。对象存在或 SDK 的成功返回不能单独触发后台“自动完成导入”。

取舍：每次尝试独有键增加少量失败残留，但避免迟到旧 PUT 覆盖已受理原件。恢复依赖数据库资格而不是进程是否仍活着，可跨实例工作。

### 6. 对账保护与提交竞争

清理保护集合扩展为：现有未删除文档的全部版本对象键，或状态仍为 ACTIVE 的导入尝试对象键。到期 ACTIVE 在恢复事务真正提交 INVALIDATED 前继续受保护，不能直接用 `lease_until > now()` 定义清理资格。

最终提交与恢复使用同一项锁：前者在一个事务把 ACTIVE 保护转换为存活版本引用，后者永久撤销旧执行提交资格。一次数据库查询看到转换前或转换后的保护，不存在中间空隙。清理候选的 object_key 永不重新分配给其他尝试；其状态一旦 INVALIDATED 就不能恢复 ACTIVE。这样删除前复核之后也不会重新取得该键的合法导入提交资格。

扫描和删除前复核都使用同一保护集合；集合为空拒绝删除等既有规则保留。失败及失效对象在现有宽限期后进入候选，SDK 迟到写入导致对象再次出现时，由后续扫描回收。

缺失对象检查只抽样已建立的存活版本，不将 ACTIVE 且尚未 PUT 的对象算作丢失原件。导入 ACCEPTED 回执本身不构成永远保护：文档已删除且无 ACTIVE 尝试时，其原件按现有规则清理。

### 7. 任务所有权与内容资格

任务只属于提交者，没有管理员代查入口；用户/部门启用、认证代次、强制改密仍按现有协议检查。任务属于本人不等于仍有上传或文档阅读资格。

读取投影分两层：

- 本人最小历史：批次/项 ID、序号、创建时间、受理状态/计数、固定失败代码及已受理三元组。即使原空间 edit 撤销，仍可核对自己的受理事实，`canContinue=false`；不返回对象键、摘要、原始错误或新的文档资料。
- 原提交清单：只有本人仍具备原空间上传资格且空间未归档时，返回其原始文件名、提交标题、大小、摘要、spaceId、securityLevel 供匹配。无资格时省略这些字段，依赖故障返回 503，不能以旧快照补齐。

原清单表示本人曾提交的意图，不跟随文档后续改名或搬迁。当前文档详情、处理状态、审核与文件入口按固定文档/版本通过既有受保护接口另取；没有 view 时只显示“已受理，当前无法查看处理状态”。任务查询不批量联表暴露新版标题、审核意见或解析原始错误。

每次上传与匹配写重放仍需要本人归属及当前 edit；读取本人最小回执是独立的只读核对，不借写重放绕过资格。前端见身份/空间拒绝立即停止后续准入；已在途请求也在提交前重核。

### 8. 前端结构与生命周期

新增 `src/imports/`，复用 Session、`decodeJson/encodeJson`、`positiveId`、共享 UI 和自管 lazyPage。路由建议 `/imports` 与 `/imports/:importId`，文档中心新增批量上传入口，主导航增加“我的导入任务”。

文档中心入口先进入 `/imports` 再选择文件；创建清单成功后在同一已挂载页面展示活动任务和上传队列，不先切换路由再依赖已释放的 File。历史任务详情页复用任务内容组件；主动切页遵守清理规则，再进入后重新选择尚未上传的文件。

队列是纯 TS 状态核心，Vue 只提供响应式桥接。每次队列执行绑定 session epoch、批次及本地 generation；文件引用、摘要 Worker、AbortController 和请求绑定仅存内存，不写 localStorage、sessionStorage 或 IndexedDB。

- 用户提交一次明确的“开始上传”可以调度本次已选清单，默认两个并行项；普通单项确定失败后继续其余待发送项。
- “暂停后续上传”停止新发送，已发请求继续核对；它不删除文档，也不要求服务端把整个批次置为永久取消。恢复由用户明确发起。
- 页面隐藏、离开、退出、身份进入核对或换号时停止调度，取消本地等待和摘要工作，清理私有显示与 File 引用；服务器事实可能继续变化。回来先核对身份、任务和项，再重新选文件并主动继续。
- 后台或隐藏页面不轮询。可见页面对 PROCESSING/待确认项作有界读取，默认每 3 秒一次、连续失败 3 次后停止；单次主动核对最多持续 3 分钟，到限保留待确认并提供手动刷新。恢复调度在服务端独立执行。
- 服务端计数 pending/processing/accepted/failed 来自同一读取快照且总和等于项数；“本页回执待确认 X 项”独立呈现，不混入服务端计数或伪造运行中。
- 默认只显示阶段状态，不编造网络字节或解析百分比；同名项始终显示序号和文件身份，以 itemId 定位。

页面恢复不依赖存储旧 File 的浏览器特性。上传专项读取需要校验响应身份、revision、有限枚举和回执字段，避免把损坏 HTTP 200 当作成功；错误使用导入上下文文案。

### 9. 容量、超时与保留默认值

以下是实现初值，属于本设计的可配置默认建议，不是用户已确认的业务上限或吞吐承诺：

| 参数 | 初值与约束 |
| --- | --- |
| 单批文件数 | 100，可配置 1–500 |
| 单批声明总字节 | 1 GiB，可配置有界正整数，累加使用 checked long |
| 单文件上限 | 沿用 `kb.storage.max-upload-bytes`，当前默认 50 MiB；能力响应与 multipart 限额一致 |
| 清单 JSON | 1 MiB，读取过程中限界；文件名按现有安全策略，标题按现有文档写入约束 |
| 列表/项分页 | 默认 20，范围 1–100；游标绑定本人、批次及排序 |
| 浏览器并发 | 2；摘要计算并发 1 |
| app 文件处理实际在途 | 每实例 8、每用户每实例 2，先准入、无等待队列，429 不自动重试 |
| 尝试执行预算/租约 | 默认 120 秒，从持久领取开始；数据库时间核对资格，不续租，不延长旧尝试 |
| 导入存储调用 | 默认 60 秒且不超过尝试剩余预算，连接/完整调用均限时 |
| 网关响应等待 | 独立导入路由 150 秒；前端单项等待 180 秒 |
| 恢复扫描 | 每 30 秒，单轮最多 100 项，竞争领取有界 |
| 任务记录 | 首期不自动清理；对账只处理可清理对象，不删除请求绑定 |

应用的新配置使用 `kb.document-import`，非法配置拒绝启动；能力接口只输出公开限额。网关等待不是请求体传输总期限，部署说明分别描述反向代理/Servlet 入站超时、磁盘临时文件限额与响应等待的作用。容量覆盖新增上传路径的实际执行退出，不因向客户端交付超时错误立即释放仍在工作的槽位。多实例总容量受部署实例数影响。

## Risks / Trade-offs

- [服务器提交结果未知时误删原件] → 不在批量异常分支直接补偿删除，持久资格与对账决定可清理性。
- [租约过期但最终事务尚未提交] → ACTIVE 保护不按时钟直接消失，恢复与提交争用同一项锁。
- [迟到旧请求污染新执行] → 尝试代次、固定回执、唯一对象键及终态不可逆共同限制。
- [批量查询成为内容权限旁路] → 本人最小受理历史与原清单/当前文档的读取资格分别校验。
- [浏览器刷新无法恢复 File] → 重新选择完整文件并按摘要匹配，明确人工继续，不宣称字节级续传。
- [文件摘要计算及多份 multipart 放大内存/临时磁盘] → 单文件有界读取、摘要单并发、上传准入与临时文件限制。
- [离线替身无法证明真实环境行为] → 报告明确限定进程内证据范围，不据此声称真实事务、网络取消或部署已验收。
- [长期保留任务表持续增长] → 首期依靠有界批次及分页，监测容量；后续保留期变更必须保留幂等语义，不能静默淘汰绑定。

## Migration Plan

以下为部署与回退顺序说明，不属于本变更测试执行任务。

1. 交付创建导入表、唯一约束和查询/恢复索引的增量迁移，不改写已有文档版本或旧请求记录；实施阶段以离线 Mapper 映射测试及人工迁移审阅核对。
2. 发布前在全部 app 实例暂停对象对账删除；旧 app 的清理查询不了解 ACTIVE 导入对象，不能与新上传同时执行删除。
3. 由 app 执行迁移，升级全部 app（新接口、恢复调度和对账保护），核对所有实例版本后恢复原删除配置。恢复调度启用不依赖解析器或 AI 开关。
4. 发布 gateway 的 dev/prod 导入路由，再发布前端任务入口。错误 404/405 表示当前接口不可用，不循环调用旧单文件接口补做。
5. 回退先隐藏新入口并停止新导入上传，排空或持久失效在途尝试；保留所有表、回执、文档和对象。若回退至旧 app，必须持续关闭对象对账删除，直到重新部署理解导入引用的版本；历史任务暂不可查询不能引导自动重建批次。

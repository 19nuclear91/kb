# Proposal

## Why

现有 `kb-eval` 已能基于标注和有序结果计算检索质量，但缺少把真实授权搜索响应转换成评测输入的工具。补齐采集环节后，可以在相同用例、语料和权限条件下比较不同部署配置的最终检索效果，并保留可复核的采集来源与失败边界。

## What Changes

- 新增独立 Java 21 CLI 模块 `kb-eval-collector`，读取数据集、查询用例与采集配置，通过现有 `POST /api/search` 采集最终有序结果。
- 用 `caseId` 绑定查询、筛选及身份别名，并要求与人工标注完整一一对应。会话令牌从环境变量读取，采集前通过 `/api/auth/me` 核对预期内部用户，不自动登录或创建账号。
- 默认串行采集，显式记录候选数及 topK，限制连接等待、整次请求、输入与响应大小；不自动重试、跟随重定向或更换身份。
- 严格校验成功包装、筛选协议头和分块身份；保留返回数组顺序及同版本不同分块，不补版本、不静默去重。合法空结果与请求失败分开处理。
- 全部用例成功后向新目录发布兼容 `kb-eval` 的 `run.json`、`results.jsonl` 以及独立的 `collection.json`；标记 `sourceType=RECORDED`，不输出查询、文档正文、标题或令牌。
- 首个失败终止运行并返回非零退出码，不发布成功运行清单，不把部分结果或失败包装成正常空结果。仅通过进程内协议组件、传输替身和已有评测读取器兼容测试验证采集行为；不安排启动服务或外部组件的集成测试，也不编写文档内容断言测试。
- 提供合成输入示例及 PowerShell 采集、比较和质量门禁用法，注明实际服务验证范围。
- 首版仅记录最终交付结果，不新增检索后端接口或算法切换参数，不采集 BM25、向量、RRF、rerank 各阶段结果；采集元数据明确算法执行与降级状态无法由现有响应核实。

## Capabilities

### New Capabilities

- `retrieval-result-collection`：授权搜索最终结果的批量采集、身份与用例绑定、有界请求、严格转换、来源记录及完整输出发布。

### Modified Capabilities

无。`retrieval-evaluation` 的离线边界、输入格式、指标及门禁语义不变；复用现有认证、组合筛选和检索保密契约。

## Impact

- 实现阶段新增 `kb-eval-collector/` 并在根 `pom.xml` 注册；使用 JDK HTTP 客户端、父 POM 管理的 Jackson 及现有 JUnit/AssertJ 测试风格，不启动 Spring 应用，不依赖业务应用内部实现。
- 线上仅调用既有 `/api/auth/me` 和 `/api/search`；采集受当前用户权限和服务端容量限制，搜索可能按部署配置调用 Embedding 与 rerank。无数据库迁移、检索 SQL 或线上响应格式变更。
- `kb-eval` 不增加网络访问能力；采集器通过文件协议与其连接。新增测试读取现有评测输入校验能力，验证成功输出可被原工具直接消费。
- 实现阶段新增 `docs/retrieval-result-collection.md`、合成示例，并更新 README 与现有评测文档中的采集入口。采集只提供客户端观测事实，不证明语料或 ACL 已冻结，也不替代实际检索质量与权限验收。

# Design

## Context

动机与确认范围见 `proposal.md`。本设计同时满足 `worker-embedding-resilience` 新规格及两份业务规格增量。

当前与方案直接相关的实现：

| 位置 | 当前行为 | 设计约束 |
| --- | --- | --- |
| `EmbeddingProfilesConfiguration` | 将 `RestClient` 调用作为远程 transport，直接读取完整 Map | Worker 需要独立的有界传输 |
| `RemoteProfileEmbeddingClient` | 公共向量校验、文本转换、按条数分批；支持可选 `CallBudget` | 公共扩展须保留 app 查询侧兼容性 |
| `DefaultParsePipeline` | 无预算参数地生成全部向量，完成后检查租约 | 预算与停止信号必须传入每个子批 |
| `ParseTaskRunner` | 单线程执行器，`Future.get` 超时后取消；默认执行器队列无界 | 逻辑终结与实际退出需要分别跟踪 |
| `EmbeddingRebuildRunner` | 独立线程生成，调度续租；失租只设置标志 | 需共享业务槽位并将失租传入执行 |
| `EmbeddingBatchReader/Committer` | 读取与提交分别在短事务中验证执行资格 | 生成预算不能替代提交时的数据库围栏 |
| `EmbeddingReadinessScheduler/EmbeddingProbe` | 按 profile 同步探测，结束后写就绪事实 | Worker 需要独立探测执行身份与截止 |
| `FailureClassifier/EmbeddingRetryPolicy` | 普通解析未知错误可重试，重建协议错误不可重试；408 分类不同 | 用明确的模型故障类型消除两条路径的差异 |

普通解析已有 `claimToken/epoch/profile`，重建已有 run/item token；数据库资格与本地停止标志是不同事实。维护失效允许其他合格实例继续工作，本实例仍须等待旧工作实际退出后归还容量。

## Goals / Non-Goals

**Goals:**

- 建立可组合的执行截止、实际资源占用和取消契约，覆盖默认装配及所有 Worker 生产调用入口。
- 将 HTTP 子批限制与数据库提交单元分离，保持既有向量身份、原文、分块 ID 和失败恢复事实。
- 使每一种停止原因具有确定的后续动作，并可用受控时钟、响应流和执行屏障验证竞争。

**Non-Goals:**

- 接入第三方解析供应商、更换模型或调整分块及向量语义。
- 增加集群级模型配额、提高业务并发、建立 HTTP 子批持久检查点。
- 重写 app 查询限界、增加公开管理接口、修改既有主规格或自动归档。
- 承诺供应商取消计算、避免所有重复计费或强制终止任意不响应取消的 JVM 工作。

## Decisions

### 1. Worker 专属执行层与公共向量协议分工

Worker 增加统一的执行协调、预算、有界编码和 HTTP 传输组件。公共模块继续拥有 profile、文本转换、向量结果校验及必要的纯 JDK 扩展点；不引入 Worker 的数据库、Spring 或任务状态到公共模块。

```text
Parse scheduler ---+
                   +--> Business slot --> Claim --> Generate --> Commit/Recover
Rebuild scheduler -+                             |
                                                 v
Probe scheduler ------> Probe slot --------> Bounded embedding transport
                                                 |
                                                 v
                                          Configured supplier

Deadline scheduler --------------------> Stop signal
Bounded cancellation workers ----------> Cancel / close / confirm exit
```

- 为公共远程客户端增加可选的分批策略，保留现有构造方式及 app 的条数分批策略；Worker 注入双限制策略。
- 复用 `CallBudget` 的剩余时间、取消登记和响应上限契约，Worker 执行对象在内部关联用途及本次身份。必要的接口扩展保留既有实现兼容。
- Worker 的远程 transport 要求明确的有效执行预算；不允许无预算默认方法继续访问网络。三条生产入口全部改为通过统一执行层调用。
- Worker 探测调度维护自己的异步执行及结果交付状态，复用公共探测文本和就绪记录类型；app 的现有探测路径保持原调用方式。
- 未注册为生产 Bean 的旧单客户端不重新引入装配；保留的兼容入口须能证明不会绕过已注册 Worker transport。

选择理由：查询和后台生成具有不同预算与恢复语义，Worker 组件不能直接依赖包含搜索专用异常的 `kb-app` 传输。将全部搜索执行框架搬入 common 会扩大改动；仅在旧 lambda 前后检查时间又无法限制正文读取。

### 2. 运行配置与限额校验

新增配置统一放在 `kb.worker.embedding` 下，由 Worker 绑定，不加入 `EmbeddingProfile`、fingerprint 或数据库模型定义。

| 配置 | 默认值 | 约束 |
| --- | ---: | --- |
| `kb.worker.embedding.max-request-bytes` | 1048576 | 正整数，最大 16777216 |
| `kb.worker.embedding.max-response-bytes` | 4194304 | 正整数，最大 67108864 |
| `kb.worker.embedding.max-json-depth` | 64 | 整数 1–128 |
| `kb.worker.embedding.rebuild-generation-timeout-seconds` | 300 | 整数 1–3600 |
| `kb.worker.embedding.probe-timeout-seconds` | 10 | 整数 1–60 |

这些最大值是实现层配置护栏；默认值来自本次确认，均不代表已校准的供应商性能。小数、负数、零、超范围、单位换算溢出及错误类型不能截断或静默取默认值；配置诊断不附原始绑定异常或秘密。

普通解析继续读取 `kb.worker.task-timeout-seconds`，默认 900。HTTP 条数仍使用 profile 的 `connection.batch-size`；单次连接配置超时继续生效，并被本次剩余预算进一步收紧。业务和探测槽位在本次设计中各固定为一，不提供放大并发的配置。

选择理由：连接和执行限额是运行资源参数，放入 profile 会导致不必要的模型身份变化。独立 Worker 配置也避免将后台默认值应用到 app 的在线查询。

### 3. 双限制分批：完整预检、按需有界编码

先固定本次 profile 与输入快照，执行既有文档文本转换，然后完成以下处理：

1. 使用与最终发送一致的 JSON 编码规则，计算固定字段及包络开销、每条文本的实际 UTF-8 转义开销；全部输入至少完成一次单条可容纳性预检。
2. 任一单条加包络仍超限，在首个 HTTP 请求前失败。预检本身消耗父预算，并定期响应停止信号。
3. 按原顺序形成同时满足条数及字节限额的最大连续子批，记录输入范围；只保留有界编码缓冲及批次范围，不预先构造所有请求的大字节数组。
4. 发送前再次用同一编码器在字节上限内生成完整请求，验证长度与计划一致。前缀、转义、逗号、模型名和维度均计入预算。
5. 每个响应的 index 在本子批内完整校验，再映射回整次输入位置。全部子批成功后才交付一个完整结果。

空输入不发送请求；合法边界允许等于限额。单条超限不裁剪文本，响应失败不触发递归拆小重发。原文、向量维度、转换版本与数据库提交边界不因分批改变。

选择理由：按字符数估算会漏掉 UTF-8 与 JSON 转义；收到失败后试探性拆分会扩大外部调用。完整单条预检能够提前发现末尾大项，同时避免缓存全部请求的额外内存峰值。

### 4. 隔离且可终止的 HTTP 传输

使用 JDK 21 HTTP 客户端及项目已有 Jackson 能力，在 Worker 组装隔离客户端，不复用注入的带观测／默认头 builder。每个通道持有独立、有限的客户端资源，在一个通道取消时不终止另一个通道的合法调用。

- 每次子批只有一次传输尝试。关闭自动重定向；Worker 在任何 JDK HTTP 客户端初始化前设置禁止自动连接重试及非幂等自动重试的进程策略。策略由 Worker 早期启动配置负责，不在 common 静态初始化中修改；其对 Worker 内其他 JDK HTTP 使用者的影响需在运维说明中明确。
- 接收响应头时先判断状态。非 200 使用立即取消的接收分支，不聚合、消费或记录错误正文；不要用会完整排空正文的替换型 body handler。
- HTTP 200 采用有界正文读取，声明长度超过上限时提前拒绝；无长度头按实际字节限制，最多作一个越限字节的探测。关闭自动内容解压，对非 identity 内容编码按协议错误处理，避免传输与解码字节口径分离。
- 成功内容按 UTF-8 JSON 处理，拒绝重复属性、超深结构、尾随根值及不完整输入；附加字段仍经过相同结构与载荷约束。
- HTTP 子截止在本次编码开始前确定，覆盖请求编码、连接、等待、读取和 JSON 校验；计数预检另计入父执行预算。响应处理和最终向量校验结束后再次检查父截止。
- 取消登记覆盖响应到达前的发送句柄与到达后的正文资源。登记与停止交错时，迟到注册的资源立即收到本执行的停止信号。
- 取消只发信号；实际关闭在有限取消工作通道进行。必要时关闭该通道的客户端并确认本地终止，确认前不构建替代客户端绕过原占用。
- 本地响应流、请求工作及取消动作退出后，才算本地调用退出；远端是否停止计算属于供应商边界。

选择理由：继续直接 `.body(Map)` 无法覆盖读取前限界；复用注入客户端可能附带内部追踪和凭据。使用已有 JDK/Jackson 能力可避免为本次增加厂商 SDK，但必须明确处理 JDK 重试初始化和取消完成语义。

### 5. 逻辑结果、计算停止与数据库资格分离

每次执行拥有独立标识、用途、单调截止、一次性逻辑结果以及实际工作计数。用于正常交接或停止的状态与槽位的释放状态分别管理。

```text
Logical:  RUNNING --> SUCCEEDED
              |
              +----> STOP_REQUESTED

Actual:   ADMITTED --> CLAIMING --> WORKING --> SETTLING --> EXITED
                                       |
                                       +--> STOPPING ----+

Capacity: held ------------------------------------------> released
```

- `TIMEOUT` 停止本地计算，但不等价于数据库资格已失效；若原 token/epoch 仍合法，仍应记录一次可重试失败。
- `LEASE_LOST` 或 `LEASE_UNKNOWN` 停止本地输出与新请求，任何业务写回仍由数据库围栏决定；不得因为本地停止标志被设置就绕过围栏或伪造新的失败。
- 维护延期由既有维护事务幂等失效和补偿；网络取消不再退还 attempts，也不复制维护事件。
- 正常生成只有在截止前、停止信号未生效时才能原子交接至提交阶段。交接关闭生成计时器的有效状态，已取出的旧回调不得影响提交或其他执行。
- 提交阶段保留原数据库短事务及资格核对，生成截止不用于倒推撤销已经合法交接的事务结果。
- 失败收尾只允许一次，以原身份执行；若收尾故障或资格已失效，由持久租约／巡检恢复。所有已经安排的收尾仍计入本地实际工作。

选择理由：单个 `leaseHeld` 布尔值同时表达超时、取消与持久资格会把真实超时吞成失租。仅依赖 `Future.cancel/isDone` 则会过早释放容量；必须以执行体及资源处理的退出通知记账。

### 6. 领取前准入与固定执行资源

两类业务 Runner 通过同一个执行协调器竞争业务槽位；探测使用另一个槽位。采用有限执行线程及零等待队列，调度只做非阻塞准入与任务交付。

- 已准入工作进入对应执行通道后，才执行数据库 claim，避免执行器拒绝发生在任务已经领取之后。
- 普通解析实际领取上限收紧为一；较大的 `kb.worker.batch-size` 不再使多份任务提前进入本地等待。重建仍可一次领取多个 item，但它们属于一个原子批次。
- 空领取或领取异常在实际调用退出后释放槽位；事务结果未知时不主动改写猜测的目标，继续依赖数据库租约恢复。
- 业务槽位包含领取、生成、提交／失败收尾以及本次取消动作。完成生成不直接释放槽位。
- 心跳保持独立，结果绑定原执行身份。续租异常与返回 false 都使本地执行停止；逻辑停止后不靠持续续租维持无效生成。
- 截止线程只执行短小的状态转换与取消派发，不执行阻塞关闭或数据库收尾。业务和探测各最多一个待执行／执行中的取消动作，重复信号合并；取消线程及底层客户端辅助任务具有固定上限。
- 应用关闭首先拒绝新准入，再停止两个通道的当前执行并关闭资源。底层不退出时保持槽位占用和诊断，不使用强制线程终止或替代线程制造已恢复假象。

选择理由：仅在领取后限制 HTTP 并发会消耗无效 attempts 和租约。让探测共用唯一业务槽位会使长文档处理期间的就绪事实过期；独立探测槽位保留观测进展，同时总资源仍有界。

### 7. 三条路径的截止起点与结果交付

| 路径 | 父截止起点 | 成功交接 | 终结后的资源规则 |
| --- | --- | --- | --- |
| 普通解析 | 流水线开始 | 完整解析与向量结果交给原发布门禁 | 旧生成计时器失效；业务槽位继续覆盖发布或恢复 |
| 重建 | 生成阶段开始，先于读取分块 | 全部子批及结果校验完成后交给原批次提交 | 提交仍验证 run/item token、epoch、profile 与正文 |
| 探测 | 本次 profile 探测开始 | 截止前完成校验后选定本次 ready 结果 | 写入结果及本地工作退出后才能开始下一 profile |

每次 HTTP 上限为 `min(connection.timeoutSeconds, parentRemaining)`，所有换算和比较使用单调时钟；墙钟仅用于已有数据库记录与展示。

探测超时可以先选定失败，但失败持久化和实际网络退出须分别跟踪。单实例同 profile 不并发写多次探测结果；迟到响应不能再次写入 ready。写入失败时不延长旧事实，沿用原记录过期机制；槽位仍占用时后续轮询直接跳过，不将未执行的 profile 伪记为成功。上一调用真正退出后才继续下一 profile，每个 profile 取得新预算。

选择理由：重建租约可以持续续期，不能代表生成截止；探测必须保证失败选择不被迟到成功覆盖。用新的预算起点包住每个 HTTP 而没有父截止，会使拆批重新获得无限时间。

### 8. 错误类型与既有业务契约映射

新增不持有供应商正文、URI 或原始异常 message 的模型故障值，包含有限 reason 与可重试属性。仅对已识别的外部依赖故障转换；程序错误保持原有未知错误处理，不伪装为合法供应商响应。

| 内部原因 | 自动任务重试 | 普通解析 | 重建 |
| --- | --- | --- | --- |
| `TIMEOUT`、`NETWORK`、`UPSTREAM_RETRYABLE`（408/429/5xx） | 有界 | RETRYABLE，沿原退避 | `MODEL_UNAVAILABLE`，沿原退避 |
| `REQUEST_LIMIT`、`RESPONSE_LIMIT`、`INVALID_RESPONSE` | 否 | PERMANENT，固定原因与摘要，立即死信 | `INVALID_RESPONSE`，立即 BLOCKED |
| `AUTH_REJECTED`、`HTTP_REJECTED` | 否 | PERMANENT，固定原因与摘要，立即死信 | `MODEL_UNAVAILABLE`，不可重试并 BLOCKED |
| `LEASE_LOST`、`LEASE_UNKNOWN` | 不产生新的模型重试 | 资格围栏／原租约恢复 | 资格围栏／原租约恢复 |
| `SHUTDOWN` | 不立即重发 | 停止新调用，沿持久资格恢复 | 停止新调用，沿持久资格恢复 |

重建公开错误码沿用现有粗分类，Worker 日志与低基数指标提供上述细分原因，避免扩展前端或公开管理数据结构。普通解析使用受控 Embedding 失败码和固定摘要，不能通过通用 `summarize(error.getMessage())` 把远端正文带回数据库。

传输层不自动重试。任务重试会重做尚未提交的完整文档或重建领取批次，可能重复调用此前成功但未提交的 HTTP 子批；已有成功重建批次保持不变。

选择理由：保留既有管理契约，同时让运维能区分配置限额、协议错误和临时依赖故障。将所有异常统一重试会对确定性超限产生重复调用；将全部网络异常永久化又会破坏既有恢复能力。

### 9. 观测与回归验证

增加 Worker 专属低基数指标，至少包含：

- 逻辑调用结果及耗时，固定用途 `PARSE/REBUILD/PROBE`。
- 固定原因的超时、载荷超限、协议与状态故障。
- 每通道实际占用以及逻辑结束后仍占用的数量；空闲时显式为零。

逻辑停止使用 `kb.worker.embedding.execution.stops{purpose,reason}` 在一次性结果选定时递增，标签预注册，内存观测不经过可能阻塞的取消队列；空领取和已成功交接的执行不计入停止。完整 Embedding 调用的 `calls`／`call.duration` 继续在调用返回时计量，两种口径独立，重复停止及实际退出不重复记录逻辑停止。

指标、日志及固定摘要不记录输入、供应商正文、密钥或 endpoint；不使用 taskId、docId、用户或任意 profile 作为标签。现有数据库队列与重建快照指标继续表达持久事实，不用新的本地占用指标替代它们。

验证使用真实编码器与向量校验器、受控传输／响应流、可控单调时钟、执行屏障及内存指标注册表。主要证据：

1. 请求与响应恰好上限／超出一字节，UTF-8、转义与前缀，末尾单条超限且零发送，跨子批下标映射。
2. 无长度头、错误长度、深度、重复属性、尾随 JSON、未知字段、非 200 正文零消费及无传输层重放。
3. 绝对截止覆盖慢响应与结果解析，拆批不重置，迟到响应不变成功，正常交接后旧计时器不影响提交。
4. 忽略中断、阻塞关闭、取消登记竞争、重复终结与恰好一次释放；旧工作退出前数据库 claim 为零。
5. 普通解析与重建共用槽位，探测独立；失租与续租异常停止下一子批，失败写回不越过 token/epoch。
6. 临时／永久错误分类、部分 HTTP 成功不部分提交、维护不新增失败或重复补偿、成功重建批次不重做。
7. 探测超时的迟到成功不复活记录，槽位忙时不积压，写入失败不延长旧成功记录。
8. app 查询预算、公共构造兼容、profile 指纹及供应商上下文隔离回归。

离线组件证据不代替真实 JDK 网络终止、数据库并发或供应商兼容验收；发布记录须区分各自验证范围。JDK 重试初始化及客户端生命周期需要专门验证，不能仅以 mock 调用次数证明真实网络没有重放。

## Risks / Trade-offs

- **底层不响应取消会占住通道** → 通过独立截止和取消通道降低发生概率，保留 lingering 观测并由运维处理实例；其他实例仍可按数据库资格接管。
- **整批预检与 JSON 校验增加 CPU 工作** → 采用逐项有界计数与按需编码，避免反复全量序列化和存储全部请求。
- **新限额可能阻断此前可完成的任务** → 发布前核对供应商样例与原 batch-size；受控调整 Worker 限额后人工重放或恢复。
- **生成预算不等于数据库事务总预算** → 保留独立短事务和身份围栏；在交接点关闭生成计时器，避免用网络截止推断事务回滚。
- **JDK HTTP 重试开关具有进程作用域** → 仅在 Worker 的早期启动阶段设置并记录兼容边界，公共模块不修改全局属性。
- **固定一业务槽位可能降低维护切换时本机吞吐** → 与既有串行目标保持一致，资格失效后仍允许其他实例推进；不以提高并发掩盖未退出工作。

## Migration Plan

1. 发布前核对新增默认限额、配置护栏、HTTP 200／UTF-8 JSON／identity 内容编码及上游协议。配置只作用于 Worker，不回填或重标向量身份。
2. 构建包含公共兼容扩展的新 Worker，先在受控环境运行限界、取消、恢复和探测验证，再逐实例停止领取、处理在途工作并替换二进制。
3. 新实例启动后观察双通道实际占用、探测新鲜度、固定错误原因及数据库持久状态；旧 Worker 尚在运行时不能宣称所有实例已有新限界。
4. 因新永久分类进入死信或 BLOCKED 的工作，在修正配置／服务后走原人工重放或恢复接口；保持全部原文与成功重建进度。
5. 回退使用原 Worker 二进制与匹配配置，保留数据库任务、死信、重建和向量身份。回退会恢复旧限界行为，不能抹去此前产生的失败事实或自动重发已确认终态任务。

本变更按现有表结构和粗粒度重建错误码交付，不需要数据库迁移。目标供应商的实际延迟与响应体分布可在部署时继续校准，不影响本次已确认的行为契约。

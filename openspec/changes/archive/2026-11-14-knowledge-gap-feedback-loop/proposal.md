# Proposal

知识缺口闭环。本文记录已确认的业务边界及本变更的首期范围。最初规划阶段只交付设计、增量规格和任务；其后用户已另行授权实施，并于 2026-11-14 授权同步七份主规格及归档。47/47 项实施任务完成，见 [tasks.md](tasks.md)；实际离线证据、核验与归档记录见 [verification.md](verification.md)，逐场景映射见 [traceability.md](traceability.md)。归档不将规划文字当作完成证明，也不代表已部署或真实环境验证通过。

## Why

立项时，搜索、私有问答、文档审核与站内通知已有基础，但用户提出“没找到所需内容”或“回答不准确”后，尚无持续追踪受理、分派、知识修订与本人确认的业务闭环。落实[开发路线图 F-01](../../../../docs/development-roadmap.md)的首期范围，可以将用户反馈转化为可追踪的知识维护需求，同时避免将检索故障等同于知识缺失，或借反馈开放私人会话。

## What Changes

### 已确认的四项决定

1. **统一受理、人工分派**：由统一知识运营团队受理问题，再人工指派负责人；首期不采用各知识空间独立受理的模式。
2. **最小必要分享**：只持久保存用户明确确认分享的问题描述，不自动附带、复制或后台保存模型回答、完整聊天记录及引用正文。搜索词或原提问可作为提交表单的预填建议，必须经用户修改或确认后才作为问题描述提交；不能把系统派生的受限回答改标为用户输入以绕过来源屏蔽。
3. **提问者确认解决**：处理人提交方案后进入待确认，由原提问者确认“已解决”；处理人不能代替确认，不做超时自动解决。资料发布、方案提交与问题解决是不同事实。
4. **受控处理人池**：只能分派给显式获得处理资格的有效人员，而非任意启用员工；资格沿用现有角色权限机制精确判定，不按管理员或部门负责人等名称自动放行。问题单资格不替代文档阅读、编辑、下载和审核资格。

### 补充确认的边界

1. **最小参与范围**：问题描述和处理记录仅对原提问者、当前仍有处理资格的负责人及持有独立读取资格的受理人员开放；改派后旧负责人不因历史参与保留访问权，除非仍以其他合格身份获得访问。
2. **两类解决方案**：允许纯文字说明，不强制关联文档；文档型关联固定已发布版本，提交时处理人和提问者均须可读，后续撤权时隐藏关联资料，不自动替换最新版。
3. **简单终态**：提问者可撤回未结束问题，合格受理人员可带原因关闭未结束问题；停用提问者的问题可关闭但不能冒充已解决。已解决、已关闭和已撤回均不重开。
4. **保留业务记录**：首期保留已提交描述、处理说明和历史，不提供正文删除接口或自动清理；提交与撤回时明确告知“撤回停止处理，不等于删除”。保留不扩大当前可见范围。

### 首期范围

- 提供搜索、已保存问答轮次的主动反馈入口，以及不依赖 AI 会话开关的独立知识需求入口；提交前说明哪些描述将被保存、分享。
- 建立持久问题单、本人问题列表、统一受理队列及被指派问题视图，支持人工受理、分派和处理过程追踪；不自动收集每次失败或公开全部问题。
- 支持纯文字说明或关联固定已发布版本的解决方案，沿用现有上传、审核和发布流程补充资料；不另建审核流程，不自动重跑原问题或改写历史回答。
- 提供提问者确认与“仍未解决”的退回处理，以及与解决分开的撤回和带原因关闭。
- 为分派、提交方案及退回等节点提供受控站内提醒；依据已提交事实去重派生，通知不携带问题描述或文档正文快照，打开目标和未读数使用一致的当前可见范围。

### 本轮收敛的设计取舍

- 首期每单至多一名当前负责人，由受理人员改派；处理人可退回受理，原方案保留但不能作为新的待确认方案。人员停用或失去处理资格不自动重新授权或改写历史，由受理队列接管。
- 受理读取、分派、处理与关闭分别使用独立资格；方案及补充说明按同一问题单范围分享，无隐藏的内部评论。详情与关联资料分别鉴权。
- 不保存搜索/会话 ID、原答案及引用快照；入口只携带用户确认后的描述和非敏感来源类型。删除原会话不影响独立提交的业务记录。
- API、状态机、限额、幂等和通知兼容方案分别落在增量规格与设计中；取舍与替代方案见 [design.md](design.md)，实施和验证步骤见 [tasks.md](tasks.md)。

### 首期非目标

不做自动指派、相似问题自动合并、全员公开问题广场、附件、复杂 SLA 与升级机制、外部 IM 内容推送、AI 自动生成或发布修订、终态重开、私人会话分享和正文自动清理。这些是首期边界，不表示永久排除。

## Capabilities

以下能力与本变更下的增量规格一一对应，不直接修改主规格。

### New Capabilities

- `knowledge-gaps`：知识问题单的归属、受控分享、统一受理与合格人员分派、解决方案、提问者确认，以及相关可见性、流转与一致性规则。
- `user-web-knowledge-gaps`：普通用户主动提交、本人问题追踪与确认，以及合格处理人员访问被指派问题的受保护交互。
- `admin-web-knowledge-gaps`：统一受理队列、受控处理人选择、分派与协调处理界面；沿用已有管理页面资格和异步状态隔离。

### Modified Capabilities

- `functional-authorization`：定义问题单读取、分派、处理和关闭四项独立精确资格、最小处理人候选边界、撤权及一次性初始化规则，不开放完整身份管理目录。
- `admin-web-access`：为统一受理入口补充导航、资格核对及合法登录返回规则，维持资源懒加载、身份隔离和不自动重放写入的边界。
- `user-notifications`：扩展可信问题单事件、收件人规则和非文档型站内目标；列表、未读数及目标读取按问题单当前可见性复核，保留已有审核与评论通知语义。
- `user-web-notifications`：扩展问题单通知类型及目标白名单，按当前资格打开问题单，不将已读当作处理完成或确认解决。

## Impact

- **后端**：主要涉及 `kb-app` 的新增问题单业务、持久化迁移、受控查询/写入、权限目录、最小处理人候选和站内通知衔接。现有身份查询与最小投影模式可参考，但不因分派需求额外授予 `identity:user:read`。
- **前端与入口**：涉及 `kb-web` 搜索/问答反馈入口、问题单页面、统一受理界面、导航与通知目标；`kb-gateway` 需核对新增业务路径及认证拒绝等响应的 `no-store` 边界。具体 API 和路由在后续规格中确定。
- **既有约束**：继续遵守 `conversation-history` 的私人会话归属与来源屏蔽、`search-query-confidentiality` 的传输/日志保密、`document-review` 的固定版本与合法发布规则；本提案不改变它们，不新增管理员读取他人会话的能力，也不赋予问题单访问文档的持续授权。
- **兼容与验证**：当前协作事实和通知目标绑定文档版本及审核/评论，不能仅增加类型名称便接入问题单；须在设计中明确事件、目标、查询和前端协议的兼容方案，以及权限目录升级顺序。后续应覆盖越权、改派/撤权、确认与退回竞争、幂等及通知故障，不将通知派生成功或文档发布视为问题解决。
- **交付边界**：最初“只规划、不改代码/README”的限制适用于规划阶段；用户后续已明确发起实施，因此本阶段交付本项目代码、API/运维/使用说明及离线验证，不新增外部服务或执行实际部署。主规格同步、归档、提交和推送仍须另行请求；不以离线通过宣称真实环境验收完成。

# Design

## Context

动机和范围见 [proposal.md](proposal.md)。本变更涉及新的内容模型、跨资源授权、审核一致性、检索及协调发布，满足生成设计产物的条件。

已核对的现有实现：

- `document/service/ReviewApprovalService` 在短事务中锁定 Embedding 控制状态、文件版本和审核轮次，通过即发布；它与文件索引完整性绑定，不能直接承担人工答案卡发布。
- `document/service/PublishedDocumentQueryService` 与 `PublishedDocumentMapper.xml` 支持按当前主体查询可信固定发布版本、列出当前发布候选；`reference()` 允许历史发布版本，因此卡片送审及展示还要独立核对 `current_version_id`。
- `document/applicability` 以固定版本保存可更正的日期，缺行视为适用期修订 0；更正锁定版本行并推进修订，原值即使改回也不能复用旧修订号。
- `document/stewardship` 的业务日期、周期、月末截取及责任人资格模式可作为行为参照；卡片的独立资格和“来源更新暂停”规则须另行实现。
- `search/mapper/SearchMapper.xml` 使用 ParadeDB 文本检索，现有结果是文件分块；`kb-web/src/search/SearchWorkspace.vue` 固定文档筛选及增强搜索协议。
- `Permission` 为固定功能目录；`SpaceWriteService.delete` 已检查文档引用，归档及删除通过分类树状态行协调空间写入。
- 仓库 Java 历史包以 `document/service`、`space/web` 等布局为主。新增文件的落位采用当前分层规范，见 D12；不复制新的功能聚合目录。

## Goals / Non-Goals

**Goals:**

- 把不可变审定内容、当前可用性和责任人复审分开，任何“确认仍准确”都不能绕过来源变化所需的审核。
- 以当前数据库事实完成卡片及全部来源访问，保证列表、搜索、详情和写入使用同一语义；失效不依赖通知或批处理时效。
- 让新业务在现有部署及权限体系内可独立启用、核对与回退，保存完整修订、审核和命令记录。

**Non-Goals:**

- 通用工作流引擎、卡片向量化、AI 生成或引用、逐句证据判断及自动认定适用岗位。
- 新资源级例外 ACL、独立卡片密级、内容搬迁、发布版硬删除或任意恢复旧版本。卡片范围由所属空间和全部来源当前 ACL/密级共同限定。
- 改变来源文档的日期、审核或检索行为；来源文档仍可按原规则检索，卡片适用期门禁只作用于新资源。

## Decisions

### D1. 独立卡片模型与三个状态维度

不创建虚拟文件、不向 `kb_document_version` 或 `kb_doc_chunk` 注入卡片。文件审核依赖解析与向量状态，硬套会导致人工编辑必须等待无关服务，也会让既有 AI/评测消费者收到错误引用身份。

卡片分为：

1. **内容及审核事实**：稳定卡片、不可变修订、活动草稿分支、精确审核轮次和当前批准修订。
2. **本次展示判定**：来源、授权与适用日期的实时结果。管理端可显示固定原因，普通不可用目标统一 404。
3. **周期复审**：责任人及 3/6/12/24 月周期、最近确认和到期日。逾期提示不等同于答案失效。

一个卡片至多一条活动草稿分支及一个活动审核。每次保存插入新修订，更新分支指针；发布后该分支关闭，之后修改另开分支。分支全部贡献者保留，用于禁止编辑后换送审人规避自审。已通过的卡片修订只可被新批准修订取代，不能原地修改。

```text
Draft branch --> IN_REVIEW --> APPROVED --> published revision
      ^              |
      +-- REJECTED --+
      +-- WITHDRAWN -+

published revision + current source facts + access + dates
                            |
                            v
                     display eligibility

responsible user + confirmation + cycle --> review reminder
```

审核中的草稿冻结。驳回和撤回只结束轮次，原分支可继续保存及再送审；批准后草稿指针清空，发布指针单调前进。单纯建立草稿不下线仍合格的旧版。

### D2. 持久模型与约束

使用现有 PostgreSQL，通过 app 的下一空闲 Flyway 版本交付。当前最高 V43；实施时再次核对编号，不提前假定独占 V44。

| 表 | 职责与关键约束 |
| --- | --- |
| `kb_answer_card` | id、固定 space_id、card_version、published_revision_id、active_branch_id；空间外键 RESTRICT；发布指针必须引用本卡片的已批准修订 |
| `kb_answer_card_branch` | card_id、分支号、latest_revision_id、closed；同卡片只允许一条未关闭分支，分支号递增 |
| `kb_answer_card_revision` | card_id、branch_id、revision_no、问题、问法、答案、适用范围和日期；不可修改或删除；以全局 id 为文本索引 key |
| `kb_answer_card_source` | 修订、来源文档/版本、applicability_version 及服务端读取的日期声明快照；按修订/文档唯一，来源复合归属外键，不复制原文或标题 |
| `kb_answer_card_contributor` | 分支及实际编辑者，创建分支、复制发布版和后续保存均追加；不可移除 |
| `kb_answer_card_review` | 分支/精确修订/轮次、送审者、决定人、状态、时间、驳回原因；每卡片至多一个 IN_REVIEW，终态不可重写 |
| `kb_answer_card_stewardship` | 每卡一行、责任人、周期、首次指定日、最近确认日及其发布修订、stewardship_version；首次指定日保持不变 |
| `kb_answer_card_confirmation` | 不可变确认人、日期、发布修订与前后复审版本；配置变更的历史由独立审计与回执记录 |
| `kb_answer_card_command` | 操作域、原请求标识、操作者、卡片/分支/轮次、预期版本、规范化输入摘要版本和摘要、无正文回执；append-only |

使用复合外键及唯一约束保证卡片/修订/分支归属，不仅依赖控制器检查。源关联 0–10 份允许草稿保存，送审/批准以数据库事实核验至少一份；跨行完整性由发布命令及必要约束触发器保护。建立不可变修订/来源/贡献者/确认/回执保护，不为限制公开读而删除历史。

索引包括空间+卡片 ID、未关闭分支、活动审核、来源文档/版本、责任人+到期日、命令域+请求标识及卡片文本索引。新表和每个持久字段都交付业务注释；关系、状态值和时间单位与实体中文 Javadoc 一致。新写入不回填现有文档、会话或知识问题为卡片。

### D3. 功能资格与资源资格明确相交

| 用途 | 功能资格 | 资源条件 |
| --- | --- | --- |
| 普通浏览/搜索/详情 | 有效会话 | 卡片空间 view；全部来源固定版本当前可读；满足展示条件 |
| 创建/保存/送审/本人撤回 | `answer:card:write` | 空间 view+edit；待读取/修改修订全部来源可读；撤回另限送审者 |
| 审核清单/正文/批准/驳回 | `answer:card:review` | 空间 view+review；全部来源可读；决定另排除分支贡献者和送审者 |
| 维护历史/暂停版正文 | write 或 review 对应分支资格 | 空间范围与每个修订的全部固定来源访问，不要求来源仍为当前版 |
| 准确性确认 | `answer:card:write` | 当前合格责任人、空间 view+edit、全部来源可读、当前可展示、无活动草稿 |
| 最小管理查询/责任人配置 | 现有空间 manage 或 `space:manage-all` | 只读身份/状态投影，目标候选须具维护及来源访问；空间归档时不配置 |

来源的 view 允许现有文档例外；卡片自身只用空间 view，不增加卡片例外，也不将来源例外提升为空间资格。没有独立卡片密级字段，任一来源当前密级不足都会挡住整份派生答案。业务人工补充的适用范围仍在卡片所属空间与来源交集内展示。

授权由当前可信用户的 `PermissionService.PrincipalHandle` 解析；同请求可复用，不跨请求缓存。功能门禁先于目标及回执查询，目标范围核对先于冲突详情。管理最小投影单独查询，不先读取正文再在序列化时删字段。源不可读时维护正文也不可读；管理者可重新安排具备资格的人员，但不能凭管理权限恢复源派生正文。

### D4. 固定来源同时绑定版本与日期修订

来源关联存 `{documentId, versionId, applicabilityVersion}`，日期快照由服务器取得，仅用于审核对照；缺少日期行使用 revision=0 及 UNDECLARED。保存时使用客户端明确选中的三元组核对当前值，不能把损坏或陈旧选择补成新值。

候选复用已发布文档访问谓词及候选能力；新增批量来源投影用于同一事务取得当前指针、发布证据、日期修订、状态与当前主体可读性。**不能只调用允许历史版本的 `reference()` 就认定来源仍有效**。最大 10 份来源，避免 N+1 网络请求；不通过 HTTP 调用本应用或读取文件。

编辑者明确确认新来源后插入新内容修订。送审及批准固定同一组来源；期间任何来源版本或日期修订变化均拒绝批准，送审者撤回后重新核对并保存。日期值改回原值仍因修订号推进而需要新审核。来源标题、标签、分类更新不改变此绑定，不触发内容重审。

未生效的当前发布来源可参与未来生效卡片的审核；已过期来源不能用于新批准。计算全部已声明时间区间与卡片区间的交集，拒绝已经无当前或未来适用日期的组合。未声明界限只表示未知，不被补成“已确认长期有效”。

### D5. 当前展示在读取时计算

普通展示的数据库条件为：

```text
approved current card revision exists
AND card space is active and viewer has space view
AND source set is non-empty
AND every source is currently readable and has trusted publication evidence
AND every source version equals its document current published version
AND every source applicability revision equals the saved revision
AND card and all sources are within any declared effective dates
```

使用反存在条件检查“存在不合格来源”，并单独要求来源非空，防止空集合真值放行。卡片查询、搜索和详情引用同一共享 Mapper 谓词，支持主体别名绑定但不允许客户端选择 SQL 片段。业务层日期规则使用离线边界单测，SQL 与业务规则的一致性通过人工审阅核对；真实 SQL 执行及等价性不在本变更验证范围，不用 SQL 文本存在性断言或替身结果冒充实际运行证明。

普通读取采用有界 read-only REPEATABLE READ 事务；在创建该快照后一次读取数据库时间，全部投影使用相同 evaluatedAt/asOfDate。源事实、授权及日期属于本次快照；响应不是之后操作的许可，不能承诺撤回已经交付的正文。每次新请求重核，避免定时任务或永久权限缓存带来的失效窗口。

管理端对已授权内容可以展示 `SOURCE_CHANGED`、`NOT_YET_EFFECTIVE`、`EXPIRED` 等原因集合；缺来源访问只给通用不可用，不泄露源身份。普通 404 不含原因。历史批准保留，展示状态不写回审核状态、不生成伪维护审计。

来源恢复授权或取消归档后可按当前事实恢复可见；来源版本/日期修订不匹配则仍不可见。卡片自身日期已经过期时，延长日期必须改稿再审核；来源日期延长会推进其修订，不能自动恢复旧卡片。来源被永久删除而无法按规则恢复时，旧修订不可通过管理入口读取，可基于独立可读依据另建卡片。

### D6. 短事务、锁顺序与幂等

写入使用有界 READ_COMMITTED 事务，事务最长 10 秒，锁及语句等待不超过 3 秒，不含外部网络调用。前置参数与当前功能范围核对后，使用事务 advisory lock 串行同一操作域+请求标识；摘要绑定操作者、目标、全部预期版本及规范化载荷。

锁顺序固定为：

1. 请求绑定锁。
2. 预读本次涉及的卡片及来源空间提示，按空间 ID 升序获取现有分类树状态行共享锁，协调空间归档、删除与搬迁；最多涉及当前发布、活动草稿和新提交三组各十份来源。
3. 按文档 ID 升序对来源文档行取得共享锁，再按版本 ID 升序锁定对应版本行。`DocumentReviewMapper` 的正式发布先锁文档再锁版本；适用期更正锁版本，因此此路径不会以空日期行绕过首次声明竞争。
4. 卡片行、活动分支、审核及复审设置依次锁定；锁后重新读取卡片版本、实际来源集合及空间归属，任一与预读提示不符则冲突回滚，不边持锁边追踪新资源。
5. 用锁后新读的主体、权限、日期与来源事实完成最终资格判定，按预期版本进行状态转移，在同一事务保存修订/决定/发布指针、审计和回执。

无来源创建只需要目标空间协调锁；带来源创建须按上述顺序锁定并核验来源，不能因尚未存在卡片行跳过来源一致性。责任人管理同样锁卡片及相关来源后重核候选资格。源文档更新路径不反向锁卡片，不增加全库失效写入，避免循环锁依赖及来源发布时的扇出。新增读取不得取得 Embedding 控制锁；向量维护不阻碍卡片文本发布。

卡片命令完成授权和原意图匹配后，先处理已提交回执再检查“本轮仍活动”之类仅适用于新执行的状态，避免合法批准重放因已批准而被错误拒绝。重放必须使用原请求记录涉及的修订与分支资格核对，不能拿后来新草稿来替代原操作目标。身份和 ACL 按最终授权语句可见事实决定；之后并发收缩由下一次请求重核，不把批准回执当持续访问许可。

数据库约束防御重复活动分支、轮次和跨卡片指针；序列冲突、锁超时和事务失败不自动换请求标识重试。比较更新失败返回安全冲突，不确认部分发布。建卡与空间删除同时依赖空间协调锁和外键 RESTRICT，删除预检查包括全部卡片引用。

### D7. 责任人及周期复审

首发前要求管理员指定一个合格责任人及周期。责任人资格基于当前发布修订，无发布版时基于最新草稿；送审、批准还检查其能访问候选全部来源。已有发布版不会因为新草稿的来源变化自动改变旧版责任范围。

首次指定日为数据库业务日期；以后改派不重置。周期 3/6/12/24 月，沿用现有月末截取及提前 30 天算法；不引入新的时区或定时状态表。复审日期在投影时计算，可为索引查询使用受约束派生列，但不能形成与规则不一致的第二份权威状态。

责任人确认绑定 cardVersion、publishedRevisionId 与 stewardshipVersion；需要无活动草稿且当前仍能普通展示。确认追加不可变事实并更新最近确认日；发布、草稿保存、改派或日期更正不自动确认。改派和确认均锁卡片，先重核当前资格再报告版本冲突。责任人失格只导致需重新指定及本人无法确认，不单独撤下其他人可读的有效卡片。

初次指定及后续管理入口支持最小用户候选，不需要完整身份目录。显示名仅用于当前有权管理上下文，原责任人失格原因不披露。首期不清空已有责任人；未配置的初始草稿不能发布。

### D8. 卡片文本搜索与页面条件

在卡片修订表上建立独立 ParadeDB 索引，使用现有已选用的 `pdb.jieba` 和固定字段表达式；标准问题与常见问法形成 question_text，答案为 answer_text。归一化问题/问法用于精确相等组，采用 NFC、strip 和 Locale.ROOT 小写，不删除标点或进行语义纠错。

三组按精确问题、问题文本命中、仅答案文本命中排序，组内使用文本相关性再按 cardId 稳定打破并列。每组先应用 D5 及 spaceId，再限制有界候选，最终合并按卡片去重截取 limit。禁止先从所有修订取 topN 再过滤，也不把审核意见、适用范围或源文档全文放入卡片索引。字段 SQL 和排序为服务端固定，查询文本参数化。

文本索引随修订插入而更新，发布指针与批准原子切换即可改变合格集合，草稿和旧版即使存在索引记录也不能召回。数据库索引失败使相应写事务失败；搜索依赖失败返回 503，不回退到任意全表扫描或 AI。

考虑过直接合并原搜索结果或增加向量召回；首期采用独立结果协议，因为现有消费者依赖真实文档分块身份，卡片的日期/审核门禁也与文档不同。新搜索使用独立容量，默认实例 8、每用户 2，总期限 5 秒、语句最多 3 秒、编码后响应最多 256 KiB。准入在业务查询前，完成/取消/失败均释放占用；调小配置可以，扩大任何协议硬上限须另改规格。请求正文为 16 KiB，其他卡片业务为 128 KiB。

知识搜索页新增独立卡片表单和结果区域；用户可点击将文档区域原问题预填，再明确提交。该区域只支持自己的问题及空间条件，不继承文档的分类、标签、文件类型、时间或增强建议。结果保留已提交条件，查询失败不显示旧结果冒充当前成功。卡片浏览提供有界分页，搜索本身最多二十条不分页。

### D9. API 与页面约定

所有新业务响应使用 `R<具名类型>`，正确的 HTTP 状态及 `Cache-Control: no-store`，成功响应声明 `X-Answer-Card-Version: 1`；搜索对 query 使用独立更小正文上限。身份与版本使用规范十进制字符串，代码内部为 long；禁止 float、指数形式、前导零和越界。日期保持 ISO 日历字符串，时间为带时区时间。

| 入口 | 主要用途 |
| --- | --- |
| `GET /api/answer-cards` | 当前可展示卡片浏览，仅 spaceId/limit/cursor |
| `POST /api/answer-cards/search` | 独立卡片文本查询 |
| `GET /api/answer-cards/{id}/revisions/{revisionId}` | 固定选中修订的普通详情，必须仍为当前可展示版 |
| `POST /api/answer-cards` | 在固定空间创建卡片和第一草稿修订 |
| `PUT /api/answer-cards/{id}/draft` | 保存完整草稿载荷，存在分支则推进，不存在则创建新版分支 |
| `GET /api/answer-cards/workspace` | 按 editable/reviewable/mine/attention 及有界游标列出工作项 |
| `GET /api/answer-cards/{id}/workspace` | 当前合格人员读取有权内容、状态及动作资格 |
| `GET /api/answer-cards/{id}/history` | 有界修订与审核事实，逐修订核验全部来源；不公开普通历史入口 |
| `POST /api/answer-cards/source-options` | 以 spaceId、名称和有界游标查询本人可读当前发布来源 |
| `POST /api/answer-cards/{id}/reviews` | 绑定分支/精确修订送审 |
| `POST /api/answer-cards/{id}/reviews/{reviewId}/approve` | 独立批准并原子发布 |
| 同上末段 `reject` / `withdraw` | 原轮次驳回或送审者撤回 |
| `GET /api/answer-cards/management` | 以当前可管理 spaceId 查询最小管理清单 |
| `GET /api/answer-cards/{id}/stewardship` | 最小管理投影 |
| `POST /api/answer-cards/{id}/stewardship/candidates` | 当前合格责任人候选 |
| `PUT /api/answer-cards/{id}/stewardship` | 指定、改派或调整周期 |
| `POST /api/answer-cards/{id}/stewardship/confirm` | 当前责任人确认已发布修订仍准确 |
| `POST /api/answer-cards/commands/query` | 核对本人原命令绑定，不返回原始载荷 |

精确请求 DTO 在实施中按这些职责拆分；创建以外的写入携带 expectedCardVersion，分支/轮次/复审操作另携带相应身份及 expectedVersion。每次新写入递增 cardVersion；复审配置和确认同时递增独立 stewardshipVersion。创建不接受客户端 owner、发布状态、贡献者或审核人，首次 cardVersion 从 0 开始。源选择传三元组，日期快照从数据库取得。字段缺省与 null 的语义在 DTO/OpenAPI 中明确，禁止未知字段或动态无说明 Map。

普通列表和工作区使用 limit 默认 20/最大 100，候选同范围；游标绑定当前用户、用途、过滤与最后位置，最长 4096 字符。查询不返回全量 total。来源列表最多十份；详情一次至多一个答案修订。工作区不内嵌全部历史正文或任意版本数组。

前端路由为 `/answer-cards`、`/answer-cards/{id}/revisions/{revisionId}`、`/answer-cards/workspace`、`/answer-cards/{id}/workspace`、`/answer-cards/management`。固定路由优先于 ID 参数；管理选择空间通过已有最小管理空间查询，业务入口不借用全局文档管理目录。角色/主体管理页仅增新权限标签，不另设卡片管理权限目录。

### D10. 未知结果、会话隔离与兼容

客户端每个工作区保存一次原意图及请求标识、精确载荷、目标/版本和身份代次，仅在当前会话的内存状态中保持。响应未知时冻结冲突写入口，允许主动核对或原绑定重试；NOT_FOUND 不证明原调用未提交。关闭弹窗和局部组件卸载不清掉工作区待核对状态；完全刷新、退出或换号则清理内存，下次先读取持久事实，不自动重放。

已提交命令回执只包含 ID、版本、状态及提交时间，无问题/答案/来源清单。核对必须是本人，继续核验动作及原资源访问；创建未知用原空间上下文核验。显式放弃后先重读新事实，新的独立意图使用新标识和新预期版本，迟到结果仍绑定旧世代。

前端延续 Session 的 epoch/request-generation 模式；401/403/404、目标变化及用户切换时清理对应私有状态，查询取消后迟到响应不能重填。搜索详情固定命中修订，陈旧结果不能无提示替换为另一答案。来源文件入口只指向原版本；下载仍独立授权。

网关转发新路径到 app，补早期大小限制和拒绝响应 no-store，不固定补成功协议头。旧后端/损坏协议显示功能不可用，不回退原搜索或创建占位答案。页面懒加载、SafeText、退出可用及包体隔离沿用既有模式。

### D11. 审计与可运维边界

成功动作按 audit-query 增量的八个操作域写入 `sys_identity_audit`。新增目标 answer-card 及固定安全摘要映射；原全局审计仍独立要求 audit:read。摘要只含规定身份、状态、版本、日期及字段变化标记，不保存答案、原问题、源身份清单或原因文本。卡片私有历史与全局审计分别鉴权。

来源更正、日期跨日和搜索读取不触发卡片状态写入，故不生成伪卡片维护事件。管理排障依赖卡片固定来源绑定、当前事实、真实审核和原来源事件。首期无新的后台调度、站内通知类型或外部投递。

### D12. 代码落位与职责

已查看 app 的 document、space、search、authorization 同类 Controller/Service/Mapper、资源 XML 及前端 search 结构。新增卡片 Java 文件以技术层作为外层，业务子目录只在层内出现：

| 路径（相对 app Java 根 `com/zhishiku/kb/app`） | 职责 |
| --- | --- |
| `controller/answercard` | 普通读取、工作流、管理、命令核对控制器及严格输入处理 |
| `service/answercard` | 有实际边界的命令、读取、搜索及资格服务接口 |
| `service/impl/answercard` | 对应业务实现；状态、来源及日期判定服务，不塞进通用工具包 |
| `mapper/answercard` | 持久化和当前授权投影 |
| `domain/answercard`、`domain/req/answercard`、`domain/dto/answercard`、`domain/vo/answercard` | 实际需要的持久实体、请求、内部投影与对外视图 |
| `enums/answercard`、`config` | 状态枚举及有界执行配置 |

Mapper XML 放 `resources/mapper/answercard`，测试按对应 Java 包放置。只为实际职责建立类和接口，不创建空壳层；不新增 `app/answercard` 聚合 Controller、配置、模型和服务，也不为本变更搬迁既有 document 等历史包。

现有类的必要修改限 Permission/AuditScope/审计白名单、SpaceWriteService/SpaceMapper 引用检查、可复用来源与日期访问边界。新增类默认统一构造器注入；已有类沿用其注入方式。对外类及字段有 Schema，Controller 具有中文 Tag/Operation/Parameter 与准确包装响应；持久实体同时保留中文 Javadoc。

前端新增 `src/answerCards` 的 API、类型、状态与组件，`src/pages` 放页面壳，扩展 routing/navigation 和搜索区域；gateway/common 只承载路径及协议限制，不承载业务数据查询。AI、Worker 与评测 CLI 不新增卡片调用。

- 状态与权限：用进程内服务及内存仓储覆盖发布版/草稿并存、分支贡献者自审、无审核人、受控交错、幂等重放、角色/空间/任一来源收缩、管理员最小投影及责任人竞争的服务层处理。
- 来源与日期：用固定来源投影及可控时钟覆盖新版本、更正后恢复原值、从无声明 revision=0 到首次声明、未来生效、日期交集、午夜、截止当天/次日、复审第 30/31 天及月末。

## Risks / Trade-offs

- [来源任一修订变化都暂停] → 即使只改措辞或日期更正也需要复核；保留固定对照及处理清单，符合用户选择的严格标准答案语义。
- [来源交集缩小读者范围] → 多源卡片可能只对少数人可见；编辑和审核界面明确来源集合，不能通过隐藏链接扩大正文范围。
- [独立搜索条件增加一次提交] → 通过主动预填原问题减少输入，始终展示卡片自己的条件，避免误承诺文件类型或术语建议已应用。
- [文本相关性不等于问题等价] → 显示原问题与适用范围，用户选择具体卡片；首期不做问答自动命中直返。
- [查询需实时检查多个来源] → 来源最多十份，共享 SQL 谓词和索引、有界容量与超时；本变更不测量真实执行计划或容量收益，离线结果不证明生产性能。
- [历史与草稿长期保留] → 不提供硬删除或空间级联清理；记录规模与保留需求后续单独评估，不在本期扩展自动清理。
- [全局目录增加新权限] → 发布前排空旧 app，回退保留新目录识别能力和所有数据，不忽略未知权限。

## Migration Plan

本节只作为迁移和发布说明交付，描述实际启用时的顺序；本变更不执行数据库迁移、部署、联调或外部组件验收，也不要求这些操作先完成才能结束当前任务。

1. 实施时确认下一迁移版本，交付新表/约束/索引/中文元数据注释及两项权限的一次性初始化；新库正式引导使用完整目录，其他角色不自动授权。
2. 在说明中记录 ParadeDB 扩展兼容要求、迁移顺序及未验证边界，通过人工审阅核对迁移与设计。卡片本身不依赖解析器，但选择依据前须已有可信发布文档。
3. 发布前排空不认识新功能权限的 app；app 单点迁移并全部升级后，发布 gateway 新路径保护，再发布前端哈希资产及页面。普通文档搜索和 AI 不需要协调修改来源协议。
4. 实际启用时配置专门维护/审核人员的功能资格及空间范围，按正常业务流程创建卡片、指定责任人、送审和批准；此处不安排真实业务链路测试任务。
5. 止损先回退或移除前端新入口并关闭新业务访问，保留识别新权限及空间引用保护的 app 版本；保留卡片数据、不可变历史、权限绑定和索引，不执行反迁移、不以恢复旧版卡片绕过当前来源条件。
6. 交付记录分别说明代码、离线结果与真实环境未验证边界；迁移和发布说明不代表上述部署操作已执行。

# admin-web-parse-deadletters Specification

## Purpose

为具有解析运维资格的用户提供可筛选、可分页和可核对单条重放结果的死信管理页面，使故障事实、执行周期与重新入队结果清晰区分，并避免查询审计膨胀、重复提交和跨身份数据残留。

## Requirements

### Requirement: 死信管理页面必须按独立功能权限开放

用户端 SHALL 在 `/admin/parse/dead-letters` 提供死信管理页面，读取要求当前 `parse:deadletter:read`，重放额外要求 `parse:deadletter:replay`。角色名称、文档 edit、空间 manage 或其他运维权限 MUST 不代替上述资格。无读取资格时 MUST 不请求列表，有读取资格而无重放资格时 SHALL 提供只读浏览。

#### Scenario: 独立死信读取资格
- **WHEN** 用户持有死信读取权限而没有身份目录读取或文档正文权限
- **THEN** 可浏览脱敏死信列表，页面不额外请求用户、角色、部门或文档正文补充名称

#### Scenario: 只有重放权限
- **WHEN** 用户仅持有死信重放权限并直接打开页面
- **THEN** 显示无读取资格，不加载列表或提供手填死信 ID 的操作表单

### Requirement: 筛选与分页必须遵守死信接口契约

页面 SHALL 支持 OPEN、REPLAYED、RESOLVED 状态和 PERMANENT、RETRYABLE、UNKNOWN 分类，以及可选带时区的起止时间。默认状态 SHALL 为 OPEN、页码为 1、每页 20 条；全部状态或分类通过省略对应条件表达。时间采用含起点、不含终点，双边存在时起点必须早于终点。更换条件或每页数量 MUST 回到第一页并停止旧读取。

#### Scenario: 改变筛选条件
- **WHEN** 用户从第 3 页切换分类或时间范围
- **THEN** 页面从新条件的第 1 页读取，不将旧页响应混入新结果
- **AND** 空结果与读取失败分别展示

#### Scenario: 无效时间或分页
- **WHEN** 时间范围反向、相等或时间无法解析，或者分页参数超出接口范围
- **THEN** 页面在请求前提示校验失败，不提交被静默修正的条件

#### Scenario: 超大总数
- **WHEN** total 超出 JavaScript 安全整数范围
- **THEN** 总数保持精确文本，分页控件不得因转换为不精确数值而跳到错误页面

### Requirement: 死信读取必须具有明确刷新与审计行为

列表 SHALL 在首次进入、提交筛选、翻页、用户刷新及已确认重放后读取，不进行定时自动轮询。每次实际查询 MUST 携带新的 X-Request-Id，沿用服务端查询审计。读取故障 SHALL 显示可重试状态，不清空为成功的空列表，也不无限自动重试。

#### Scenario: 停留在死信页面
- **WHEN** 用户未改变条件且未执行刷新或操作
- **THEN** 页面不因计时器重复读取和产生周期性查询审计

#### Scenario: 确认重放后刷新当前页
- **WHEN** 单条重放取得合法成功回执
- **THEN** 页面按当前筛选重新读取，并在页码已超出剩余数据范围时进行一次有界回退
- **AND** 不把返回的旧死信记录当成新执行周期的任务进度

### Requirement: 摘要展示不得扩展正文访问范围

列表及详情抽屉 SHALL 只展示接口提供的死信 ID、任务 ID、版本 ID、执行周期、尝试次数、分类、代码、脱敏摘要和进入/处置时间，所有文本按纯文本呈现。抽屉 SHALL 使用已加载的列表记录；不按版本 ID 推测文档路径，不读取正文、存储对象或完整堆栈。筛选、摘要和原因 MUST 不进入地址栏、持久存储或遥测。

#### Scenario: 摘要包含标记文本
- **WHEN** 服务端摘要包含 HTML、脚本标记或链接文本
- **THEN** 页面仅显示文本，不执行标记或自动加载外部内容

#### Scenario: 尚未处置记录
- **WHEN** 死信 status 为 OPEN 且 resolvedAt 为空
- **THEN** 抽屉明确显示未处置，不伪造处置人、原因或不存在的详情字段

### Requirement: 单条重放必须确认原目标并准确说明受理结果

页面 SHALL 仅对当前列表中的 OPEN 死信，在读取和重放资格完整时开放单条重放。确认界面必须列出死信、任务及版本身份，并要求去除首尾空白后 1–2000 个 Unicode code point 的原因。提交使用精确死信 ID 和请求标识；成功只说明原死信已重放、新执行周期已入队，不承诺故障已修复或文档已可检索。

#### Scenario: 依赖恢复后重放
- **WHEN** 用户确认某 OPEN 死信并填写合法原因，服务端返回与目标匹配的重放回执
- **THEN** 显示重新入队结果，保留原失败事实并刷新列表
- **AND** 说明任务仍受当前 Embedding 维护及正常领取规则约束

#### Scenario: 已处置或并发变化
- **WHEN** 重放返回 404 或 409
- **THEN** 页面显示安全提示并重新读取列表，不自动换请求标识补发，也不将拒绝显示成成功

### Requirement: 不确定重放结果必须保留原请求绑定

重放 SHALL 在内存绑定目标、规范化原因和请求标识，提交中及结果不确定时冻结该逻辑提交，不允许自动重传或切换目标后复用标识。网络、5xx 或成功回执不可用时 SHALL 提供原内容重试、重新读取核对及放弃核对；列表中记录消失 MUST 不被单独解释为本次重放成功。

#### Scenario: 响应丢失后的匹配重试
- **WHEN** 首次重放可能已提交成功，用户选择按原内容重试
- **THEN** 使用同一死信、原因和请求标识，只有与目标匹配的合法成功回执才确认成功
- **AND** 不因列表已过滤掉 REPLAYED 记录而宣称失败

#### Scenario: 请求内容改变
- **WHEN** 用户放弃旧结果核对并重新确认另一目标或原因
- **THEN** 新提交使用新请求标识，同时明确放弃核对不会撤销已经发送的旧请求

### Requirement: 死信页面必须隔离身份变化并安全处理响应

死信 ID、任务 ID、版本 ID、执行周期和总数 MUST 保持精确。页面 SHALL 使用现有会话发送请求并保留成功 R 封装；失败只消费安全 HTTP 提示，不解析身份管理专用 reasonCode 或展示任意服务器 message。权限失效、强制改密、退出、身份切换、目标切换及卸载时 MUST 清理相关数据、弹窗、绑定并隔离迟到响应。

#### Scenario: 请求途中撤权
- **WHEN** 列表或重放返回 403，随后重新确认当前权限不再具备读取资格
- **THEN** 页面清除列表和打开的表单，停止请求并显示无资格，不以旧权限继续展示

#### Scenario: 另一条死信的迟到响应
- **WHEN** 用户关闭死信 A 的抽屉后查看死信 B，而 A 的响应随后到达
- **THEN** A 的回执或错误不写入 B 的抽屉或提交状态

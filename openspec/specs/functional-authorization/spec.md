# functional-authorization Specification

## Purpose

定义操作管理面所需的功能资格：有哪些功能权限、角色行如何被创建与销毁、角色与权限如何绑定，以及资格判定的精确语义。与资源授权（空间
ACL、文档例外、密级）相互独立——后者决定"能看见哪些内容"，本能力决定"能执行哪些管理动作"。

## Requirements

### Requirement: 功能权限目录必须由服务端代码定义

系统 SHALL 以服务端代码中的固定目录作为功能权限 code 的唯一权威来源；持久化层只存储角色与权限的绑定关系，MUST NOT
承担定义新权限的职责。启动时若发现持久化的绑定引用了目录之外的 code，系统 MUST 启动失败而非忽略该行。

#### Scenario: 绑定引用目录外的权限

- **WHEN** 持久化的角色权限绑定中出现服务端目录里不存在的权限 code
- **THEN** 系统启动失败并指出该 code
- **AND** 不得静默忽略该行后以不完整的权限视图继续运行

#### Scenario: 仅在持久化层新增权限

- **WHEN** 运维直接在持久化层插入一条目录外的权限 code 并绑定给角色
- **THEN** 该 code 不产生任何功能资格
- **AND** 系统在下一次启动时按上一条拒绝启动

#### Scenario: 查询权限目录

- **WHEN** 具备角色读取资格的操作者查询功能权限目录
- **THEN** 返回服务端目录中全部权限的 code 与用途说明
- **AND** 返回内容与判定时使用的目录是同一份

### Requirement: 功能资格判定必须逐权限精确匹配

系统 SHALL 让每个受保护操作声明其所需的单个功能权限，并以精确匹配判定操作者是否持有该权限。判定 MUST NOT
支持通配、前缀展开或层级继承；操作者未持有所需权限时 MUST 被拒绝。操作者的权限集为其全部角色所绑定权限的并集。

#### Scenario: 持有一项权限不蕴含另一项

- **WHEN** 操作者持有某管理权限但未持有另一管理权限，并提交后者保护的操作
- **THEN** 系统返回禁止错误
- **AND** 数据与审计记录均不发生改变

#### Scenario: 通配形式的权限 code 不被展开

- **WHEN** 某角色被绑定了形如前缀通配的权限 code
- **THEN** 该绑定不使持有者获得任何以该前缀开头的具体权限
- **AND** 该 code 按目录外 code 处理

#### Scenario: 多角色权限并集

- **WHEN** 操作者的两个角色分别绑定了不同的权限
- **THEN** 其资格为两者的并集
- **AND** 解除其中一个角色后，只失去该角色独有的那部分权限

#### Scenario: 客户端自行声明权限

- **WHEN** 请求携带自称的权限或资格声明
- **THEN** 判定只按服务端持久的角色与权限绑定得出
- **AND** 该声明不得使不具备资格的操作者通过判定

### Requirement: 角色的权限集必须可查询

系统 SHALL 允许具备角色读取资格的操作者查询任一角色当前绑定的权限集合；该视图 MUST 与判定时使用的事实同源，不得来自缓存快照或客户端声明。

#### Scenario: 查询角色权限集

- **WHEN** 具备角色读取资格的操作者查询某角色
- **THEN** 返回该角色当前绑定的全部权限 code

#### Scenario: 无资格操作者查询

- **WHEN** 已登录但不具备角色读取资格的操作者查询角色权限集
- **THEN** 系统返回禁止错误

### Requirement: 角色行创建必须受保护、幂等且可审计

系统 SHALL 仅允许具备角色写入资格的操作者创建角色行。创建 MUST 指定全局唯一的 code 与显示名；code 冲突 MUST
返回可识别的冲突错误且不产生角色。创建 MUST 带请求标识幂等并留下审计。新建角色的初始权限集 MUST 为空。

#### Scenario: 成功创建角色

- **WHEN** 具备角色写入资格的操作者提交唯一的 code 与显示名
- **THEN** 系统创建该角色行并返回其标识、code 与显示名
- **AND** 该角色的权限集为空，尚不授予任何资格

#### Scenario: code 冲突

- **WHEN** 创建请求使用的 code 已存在
- **THEN** 系统返回冲突错误且不产生新角色
- **AND** 既有角色的 code、显示名与权限集均保持不变

#### Scenario: 未授权操作者

- **WHEN** 已登录但不具备角色写入资格的操作者提交创建
- **THEN** 系统返回禁止错误，数据与审计均不发生改变

#### Scenario: 创建请求重试

- **WHEN** 同一请求标识的创建请求被重复提交
- **THEN** 系统最多创建一个角色行并至多保留一条对应审计事件

### Requirement: 角色 code 创建后不可变

系统 MUST 拒绝任何修改既有角色 code 的请求；角色的显示名 SHALL 可以修改。code
是资格判定与授权主体引用共同依赖的稳定标识，允许改写它等同于允许在不产生任何角色分配记录的前提下批量改变既有持有者的资格。

#### Scenario: 修改显示名

- **WHEN** 具备角色写入资格的操作者修改某角色的显示名
- **THEN** 显示名更新并留下审计
- **AND** 该角色的 code、权限集与持有者均不发生改变

#### Scenario: 尝试修改 code

- **WHEN** 请求中携带与既有值不同的 code
- **THEN** 系统拒绝该请求并说明 code 不可变
- **AND** 角色的任何字段均不发生改变

#### Scenario: 借改名夹带资格变更

- **WHEN** 操作者试图通过把某角色的 code 改写为另一个承载更高资格的 code 来提升其持有者
- **THEN** 请求被拒绝
- **AND** 该角色全部持有者的资格保持不变

### Requirement: 角色删除必须为硬删除且要求无任何引用

系统 SHALL 以硬删除实现角色销毁，且仅在该角色**双侧无引用**时受理：既没有任何用户绑定该角色，也没有任何以该角色为主体的空间或文档授权记录。任一侧非空
MUST 返回冲突错误，并说明需要先撤销哪一类引用。系统 MUST NOT 以级联方式代为清除这些引用。

#### Scenario: 双侧无引用时删除

- **WHEN** 具备角色写入资格的操作者删除一个既无绑定用户、也无授权记录的角色
- **THEN** 角色行与其权限绑定一并被移除并留下审计
- **AND** 任何用户的资格都不发生改变

#### Scenario: 仍有绑定用户

- **WHEN** 删除请求的目标角色仍被至少一个用户绑定
- **THEN** 系统返回冲突错误并说明需要先解除用户绑定
- **AND** 角色、绑定与权限集均保持不变

#### Scenario: 仍有授权记录

- **WHEN** 删除请求的目标角色仍是某条空间或文档授权记录的主体
- **THEN** 系统返回冲突错误并说明需要先撤销这些授权
- **AND** 角色与授权记录均保持不变

#### Scenario: 删除不留悬空授权

- **WHEN** 任一角色被成功删除
- **THEN** 系统中不存在任何以该角色标识为主体的残留授权记录
- **AND** 此后新建的角色不会因标识重用而继承任何既有授权

#### Scenario: 未授权操作者

- **WHEN** 已登录但不具备角色写入资格的操作者提交删除
- **THEN** 系统返回禁止错误，数据与审计均不发生改变

### Requirement: 角色权限集变更必须受保护、幂等且可审计

系统 SHALL 仅允许具备角色写入资格的操作者授予或移除角色的权限；权限取值 MUST 来自服务端权限目录。变更 MUST
带请求标识幂等并留下含操作者、目标角色与权限 code 的审计。变更提交后，受影响用户的资格 MUST 在下一次请求即生效，不得依赖会话过期。

#### Scenario: 授予权限

- **WHEN** 具备角色写入资格的操作者把某权限授予某角色
- **THEN** 该角色的全部持有者在下一次请求即获得该权限对应的资格
- **AND** 留下可按角色与时间检索的审计

#### Scenario: 移除权限

- **WHEN** 具备角色写入资格的操作者从某角色移除某权限
- **THEN** 该角色的持有者在下一次请求不再凭该角色获得该资格
- **AND** 持有者若经其他角色仍绑定同一权限，其资格不受影响

#### Scenario: 权限不在目录中

- **WHEN** 请求的权限 code 不存在于服务端权限目录
- **THEN** 系统返回取值错误且不改变该角色的权限集

#### Scenario: 未授权操作者

- **WHEN** 已登录但不具备角色写入资格的操作者提交权限变更
- **THEN** 系统返回禁止错误，绑定与审计均不发生改变

#### Scenario: 变更请求重试

- **WHEN** 同一请求标识的权限变更被重复提交
- **THEN** 系统至多执行一次并至多保留一条对应审计事件

### Requirement: 文档密级调整必须具有独立功能权限

服务端权限目录 SHALL 包含 `document:security-level:write` 及其用途说明，保护文档密级管理查询和调整。该权限 MUST 与
`identity:clearance:write`、空间 manage、edit 及 `space:manage-all` 分开，按既有角色权限并集精确匹配；角色名称或 code 本身
MUST NOT 作为运行时资格依据。

#### Scenario: 权限目录可查询新权限

- **WHEN** 具备角色读取资格的用户查询服务端功能权限目录
- **THEN** 返回 `document:security-level:write` 及文档密级管理用途说明

#### Scenario: 普通角色显式绑定专用权限

- **WHEN** 非 `ROLE_ADMIN` 角色被显式绑定该权限
- **THEN** 其启用持有者获得文档密级管理资格，操作仍受当前密级上限约束
- **AND** 不因此获得用户密级调整或正文阅读资格

#### Scenario: 管理员角色不再绑定专用权限

- **WHEN** 用户虽然持有 `ROLE_ADMIN`，但其全部角色的权限并集中不含该专用权限
- **THEN** 文档密级管理请求返回 `403`

### Requirement: 新增密级权限的初始化不得恢复已撤销授权

升级迁移 SHALL 向迁移时已存在的 `ROLE_ADMIN` 角色一次性绑定文档密级专用权限；首次引导新管理员角色时 SHALL
将该权限纳入服务端完整目录授予。既有角色在迁移后撤销该权限，后续启动或重复引导 MUST NOT 自动恢复；其他角色不得因升级而隐式获得该权限。

#### Scenario: 已有管理员升级

- **WHEN** 已有 `ROLE_ADMIN` 的数据库首次应用本变更迁移
- **THEN** 该角色获得新权限，其他既有绑定保持不变
- **AND** 新权限不修改任何用户的密级

#### Scenario: 空库首次管理员引导

- **WHEN** 迁移时没有管理员角色，后续通过正式引导创建管理员角色
- **THEN** 新角色的权限集中包含文档密级专用权限

#### Scenario: 撤销后重启

- **WHEN** 管理员明确撤销该权限后重启服务或重新运行引导
- **THEN** 既有角色仍不具有该权限，不因角色 code 被自动补齐

### Requirement: embedding 管理必须使用独立功能资格

服务端权限目录 SHALL 定义 `embedding:read` 和 `embedding:rebuild`；前者保护 profile/状态/进度查询，后者保护发起与恢复。两项
MUST 按既有角色权限并集精确匹配，不相互蕴含，也不由角色 code、空间管理、密级管理或死信处置资格代替。管理资格 MUST
不授予正文读取与下载权限。

#### Scenario: 只持读取资格

- **WHEN** 用户只有 embedding:read
- **THEN** 可查询脱敏状态，发起或恢复返回 403

#### Scenario: 只持其他管理资格

- **WHEN** 用户持有空间管理或解析死信重放权限，但没有 embedding:rebuild
- **THEN** 重建请求返回 403，状态、向量与成功审计均不改变

#### Scenario: 资格被撤销后重放请求

- **WHEN** 首次请求成功后操作者资格被撤销，再次提交相同标识
- **THEN** 返回 403，不因匹配幂等记录而返回受保护回执

#### Scenario: 无会话或身份停用

- **WHEN** 未认证用户，或已认证但用户/主部门已停用的主体访问管理接口
- **THEN** 前者返回 401，后者返回 403，不泄露作业是否存在

#### Scenario: 全局运维与正文隔离

- **WHEN** 用户具有 embedding:rebuild 但没有某文档的 view/download
- **THEN** 可发起预配置目标的全局维护，但不能通过管理响应或既有读接口取得该文档正文

### Requirement: embedding 权限初始化不得恢复已撤销绑定

升级迁移 SHALL 向当时已存在的 ROLE_ADMIN 一次性绑定两项 embedding 权限；空库引导新角色时纳入完整权限目录。后续启动、重建或再次引导
MUST NOT 自动补回既有角色已撤销的绑定，其他角色 MUST 不因升级隐式获权。

#### Scenario: 既有管理员升级

- **WHEN** 数据库首次应用本变更迁移
- **THEN** 当时存在的 ROLE_ADMIN 获得两项绑定，其他既有绑定不变

#### Scenario: 撤销后重启

- **WHEN** 角色的 embedding 权限已被明确撤销后服务重启或执行引导
- **THEN** 权限仍保持撤销，不能凭角色 code 执行管理操作

#### Scenario: 新空库管理员引导

- **WHEN** 首次引导创建新的管理员角色
- **THEN** 新角色完整权限集中包含两项 embedding 权限

### Requirement: 新管理读取能力必须具有独立的功能权限

服务端权限目录 SHALL 定义 `audit:read` 和 `identity:external:read`，分别保护跨目标审计查询和外部身份绑定读取。两者 MUST
继续按全部角色权限并集精确匹配；任一读取、写入、资源管理权限或 ROLE_ADMIN 名称 MUST 不隐含另一项资格。既有
`identity:audit:read` 与 `identity:external:write` 的语义 MUST 保持不变。

#### Scenario: 分别分配新读取资格

- **WHEN** 普通角色仅被授予 audit:read
- **THEN** 其启用持有者可查询全局安全审计投影，但不能读取外部身份绑定或正文

#### Scenario: 权限目录与角色详情

- **WHEN** 合格角色读取者查询权限目录或含新权限的角色详情
- **THEN** 返回新权限的精确 code 及用途，判定与目录同源

#### Scenario: 角色名称不代表资格

- **WHEN** 用户持有名为 ROLE_ADMIN 的角色，但相应新权限已从其全部角色中撤销
- **THEN** 对应新接口返回 403

### Requirement: 当前用户有效功能权限必须能够自助查询

系统 SHALL 提供 `GET /api/auth/permissions`，仅从已验证会话及当前启用用户、有效主部门、持久角色权限并集返回去重且按 code
排序的权限字符串列表。调用者无需身份管理读取资格；接口 MUST 不接受目标用户、角色或客户端权限声明，不返回资源 ACL
或其他用户的权限。此结果是当前请求事实，不是后续请求的授权凭据。

#### Scenario: 普通用户没有管理权限

- **WHEN** 有效用户没有任何功能权限绑定
- **THEN** 返回成功空列表，不额外要求 identity:user:read 或 identity:role:read

#### Scenario: 多角色以及下一次请求撤权

- **WHEN** 多个角色包含相同权限，其中某项独有权限随后被撤销
- **THEN** 首次查询去重，变更后的下一次查询不包含已撤销的独有权限
- **AND** 原会话无需重建，不返回其他用户或角色的权限明细

#### Scenario: 夹带其他身份或强制改密

- **WHEN** 请求携带 userId 等非契约参数，或调用者处于强制改密状态
- **THEN** 前者返回 400，后者返回 403，不将新接口加入强制改密豁免

#### Scenario: 查询不可信或发生依赖故障

- **WHEN** 请求携带伪造身份头，或当前授权事实读取失败
- **THEN** 前者不改变查询主体；后者返回安全 503，不把不可确认的权限当作成功空集
- **AND** 成功响应标记 Cache-Control: no-store

### Requirement: 新读取权限初始化必须一次性且不恢复撤权

升级迁移 SHALL 仅向迁移时已存在的 ROLE_ADMIN 一次性绑定两项新读取权限；全新引导角色 SHALL 纳入当时完整目录。其他既有角色
MUST 不因身份读取、审计读取或外部身份写权限被隐式补授新权限。后续启动和重复引导 MUST 不恢复已撤销绑定，存量权限、角色与 ACL
标识 MUST 保留。

#### Scenario: 存量管理员升级

- **WHEN** 首次执行新增迁移，数据库已有 ROLE_ADMIN 和其他角色
- **THEN** 仅 ROLE_ADMIN 获得两项一次性绑定，其余绑定与业务数据保持不变

#### Scenario: 迁移后明确撤销再重启

- **WHEN** 新权限被明确撤销后重启或再次运行管理员引导
- **THEN** 新权限仍为撤销状态，不按角色 code 自动恢复

#### Scenario: 空库正式引导

- **WHEN** 正式空库完成迁移且首次引导创建新的管理员角色
- **THEN** 新角色包含两项权限，不依赖开发种子数据

### Requirement: 新权限升级必须遵循目录兼容边界

新增权限入库前 SHALL 排空不认识新目录的旧 app 实例；升级说明 MUST 明示这些旧实例不能与新实例混部，也不能在新绑定仍存在时直接回退。MUST
保留现有“发现未知权限 code 则拒绝启动”的约束，不为兼容旧二进制忽略新权限或自动删除绑定。

#### Scenario: 旧二进制读取新增权限

- **WHEN** 不认识新 code 的旧 app 在新增迁移后启动
- **THEN** 仍按现有未知权限检查拒绝启动，部署流程不得把它记为可兼容回退

### Requirement: AI 用量和调用审计必须具有独立读取资格

服务端权限目录 SHALL 定义 ai:usage:read 和 ai:audit:read，分别保护跨部门聊天用量统计和调用事件读取。两项 MUST 按当前启用主体的持久角色权限并集精确匹配，彼此不蕴含；audit:read、identity:audit:read、空间管理或 ROLE_ADMIN 名称不能代替。新资格不授予问题、回答、文档正文或私有会话读取权。

#### Scenario: 权限目录可查询
- **WHEN** 合格角色读取者查询权限目录或角色详情
- **THEN** 可看到两项新权限的准确 code 和用途，目录与判定同源

#### Scenario: 仅授权统计
- **WHEN** 角色只绑定 ai:usage:read
- **THEN** 其启用持有者可查询跨部门用量统计，调用事件列表和详情仍被拒绝

#### Scenario: 旧管理权限与角色名
- **WHEN** 用户具有 audit:read、空间管理或名为 ROLE_ADMIN 的角色，但没有对应 AI 读取权限
- **THEN** AI 查询被拒绝，不因角色名、前缀或其他管理资格放行

#### Scenario: 下一次请求撤权
- **WHEN** 用户所有角色中的某项 AI 读取资格被撤销
- **THEN** 下一次对应查询返回 403，已有会话或游标不延续该资格

### Requirement: AI 新权限初始化必须一次性且遵守升级兼容

首次新增迁移 SHALL 仅向当时已有 ROLE_ADMIN 一次性绑定两项 AI 读取权限；空库正式引导创建新管理员角色时纳入当时完整目录。其他角色不隐式获得权限，后续启动不恢复已撤销绑定。迁移前 MUST 排空不认识新 code 的旧 app；旧版本的未知权限拒绝启动约束保持有效，不自动删除绑定以回退。

#### Scenario: 已有管理员首次升级
- **WHEN** 新迁移首次应用到已有管理员角色的数据库
- **THEN** 仅该角色获得两项一次性绑定，原角色、权限和 ACL 标识保持不变

#### Scenario: 撤销后重新启动
- **WHEN** 管理员撤销其中一项新权限后重启或重复执行正式引导
- **THEN** 被撤销权限不自动恢复

#### Scenario: 旧二进制回退
- **WHEN** 不认识新 code 的旧 app 在新绑定仍存在时启动
- **THEN** 继续按未知权限约束拒绝启动，升级说明不得将这种回退宣称为兼容

### Requirement: 运营报表必须具有独立读取资格

服务端固定权限目录 SHALL 定义 operations:reports:read 及全局安全运营汇总用途，按当前有效主体全部角色的持久权限并集精确匹配。身份／审计／AI 权限、空间 manage、space:manage-all 或 ROLE_ADMIN 名称 MUST 不替代报表资格；该资格也不授予正文、资源明细、私有审核意见、评论或 AI 用量／审计读取权。

#### Scenario: 权限目录及普通角色绑定
- **WHEN** 合格角色读取者查询目录，或普通角色被显式绑定 operations:reports:read
- **THEN** 目录返回精确 code 和用途，该角色的启用持有者获得全局固定汇总读取资格而非文档访问资格

#### Scenario: 多角色并集与撤权
- **WHEN** 多个角色共同授予报表资格，随后其中一个或全部绑定被撤销
- **THEN** 仍有其他绑定时资格保留，全部撤销后下一次报表请求为 403，不等待会话过期

#### Scenario: 其他权限及伪造声明
- **WHEN** 用户只有 ai:usage:read、audit:read、空间管理或管理员角色名，或请求自称具有报表资格
- **THEN** 未命中当前服务端角色权限并集时拒绝，不以名称、前缀或客户端声明放行

### Requirement: 报表权限初始化必须一次性且遵守目录兼容

升级迁移 SHALL 仅向当时已存在的 ROLE_ADMIN 一次性绑定报表读取权限；空库正式引导创建新管理员角色时纳入完整目录。其他角色不隐式获权，后续启动／重复引导 MUST 不恢复已撤销绑定。入库前排空不识别新 code 的旧 app，保留未知权限拒绝启动约束，不通过删绑定或忽略 code 伪装兼容回退。

#### Scenario: 存量管理员首次升级
- **WHEN** 新迁移首次应用到已有管理员角色和普通角色的数据库
- **THEN** 仅当时 ROLE_ADMIN 获得一次性新绑定，其余角色、权限和 ACL 标识不变

#### Scenario: 撤销后重启或重复引导
- **WHEN** 管理方撤销报表权限后重新启动或执行正式引导
- **THEN** 既有角色保持撤销，不按角色 code 自动补授

#### Scenario: 空库正式引导
- **WHEN** 迁移时没有管理员角色，随后首次正式引导创建新管理员角色
- **THEN** 新角色完整权限集中包含 operations:reports:read，不依赖开发种子数据

#### Scenario: 旧二进制回退
- **WHEN** 不认识新报表 code 的旧 app 在新绑定仍存在时启动
- **THEN** 按既有目录校验拒绝启动，部署说明不得宣称新旧实例可混部或直接回退

### Requirement: 全局标签管理必须具有独立读写权限

服务端固定权限目录 SHALL 定义 document:tag:read 和 document:tag:write，分别保护管理目录读取及创建、改名、启停。两项按当前有效主体全部角色权限并集精确匹配，彼此不蕴含；空间 manage、space:manage-all、文档 edit、身份管理权限或 ROLE_ADMIN 名称不能替代。标签管理资格不授予任何文档正文或关联明细读取权。

#### Scenario: 查询权限目录
- **WHEN** 合格角色读取者查询服务端权限目录或角色详情
- **THEN** 可以看到两项标签权限的准确 code 及用途，并可通过现有角色权限维护分别分配

#### Scenario: 只读角色
- **WHEN** 用户只有 document:tag:read
- **THEN** 可读取管理目录，创建、改名和启停返回 403

#### Scenario: 空间管理者尝试维护全局标签
- **WHEN** 用户具有某空间 manage 或 space:manage-all，但没有 document:tag:write
- **THEN** 全局标签写入返回 403，不因其可维护空间分类而隐含全局标签管理资格

### Requirement: 词库管理资格与文档选用资格必须分开

空间分类管理 SHALL 使用对应空间 manage 或 space:manage-all；文档元数据修改及编辑候选 SHALL 使用目标文档当前 view/edit 和密级规则，不额外要求全局标签管理权限。普通筛选候选按当前可查看文档生成。任何候选或能力响应都不是后续授权凭据，每次实际写入及匹配重试必须重新鉴权。

#### Scenario: 编辑者没有全局标签管理权限
- **WHEN** 用户对某文档有 view/edit，但没有 document:tag:read/write
- **THEN** 可为该文档选择已有启用标签和本空间分类，不能直接进入全局标签管理目录或修改字典

#### Scenario: 撤权后匹配重试
- **WHEN** 首次标签维护成功，随后写权限被全部撤销，用户以原请求标识重试
- **THEN** 返回 403，旧回执和会话不能延续已经撤销的资格

### Requirement: 标签权限初始化必须一次性并遵守目录兼容

新增迁移 SHALL 只向迁移时已有 ROLE_ADMIN 一次性绑定两项标签权限；空库引导新管理员角色时纳入完整目录，其他角色不隐式获权。后续启动或重复引导 MUST 不恢复已撤销权限。新增绑定前须排空不认识新 code 的旧 app，保留未知目录项拒绝启动规则，回退不能自动删除权限绑定或忽略未知项。

#### Scenario: 存量和空库引导
- **WHEN** 存量管理员首次执行迁移，或空库之后正式引导创建管理员角色
- **THEN** 对应管理员角色获得两项标签权限，其他现有角色与权限绑定保持原义

#### Scenario: 撤销后重启
- **WHEN** 管理者撤销标签写权限后重新启动或再次引导
- **THEN** 该权限仍保持撤销，不按 ROLE_ADMIN 名称自动恢复

#### Scenario: 旧程序回退
- **WHEN** 不识别新增标签权限的旧 app 在新绑定仍存在时启动
- **THEN** 按既有目录检查拒绝启动，发布说明明确这一兼容边界

### Requirement: 生命周期操作必须使用独立精确权限

服务端权限目录 SHALL 定义 `identity:lifecycle:read`、`identity:lifecycle:manage`、`identity:lifecycle:restore` 和 `identity:emergency:manage`。分别保护生命周期及应急摘要读取、员工映射与原事件重试、复职核对与确认、应急登记与轮换。四项权限互不蕴含，角色名称及既有账号写权限不得代替；它们不授予正文、SSO 绑定、角色或密级修改权。

#### Scenario: 只有生命周期读取权限
- **WHEN** 启用主体只持有 identity:lifecycle:read
- **THEN** 可以读取受控状态和有界事件结果，映射修改、事件重试、复职及应急登记被拒绝

#### Scenario: 有映射管理但无复职资格
- **WHEN** 主体持有 identity:lifecycle:manage 但没有 identity:lifecycle:restore
- **THEN** 可执行合法映射核验及管理、重试原事件，但不能核对或确认复职

#### Scenario: 普通用户管理权限不足
- **WHEN** 主体只有 identity:user:write 或仅有 ROLE_ADMIN 角色名称，没有对应持久权限绑定
- **THEN** 生命周期管理和应急管理接口拒绝请求，不根据角色名称隐含放行

#### Scenario: 写资格不隐含通用读取
- **WHEN** 主体只持有某项生命周期写资格而没有生命周期读取资格
- **THEN** 只能读取该写操作必要的受控核对结果及本人回执，不能枚举事件、读取通用生命周期摘要或其他写操作回执

### Requirement: 生命周期鉴权必须先于目标和外部事实查询

生命周期接口 MUST 从当前有效用户、主部门及持久角色权限并集取得精确资格，并在目标查询、历史回执读取或供应商调用之前完成鉴权。重放请求不得复用历史授权结果。状态冲突响应只返回调用者有权知道的固定类别；无读取资格者不得借通用启用接口取得离职或员工资料。

#### Scenario: 撤权后重试已成功请求
- **WHEN** 管理员在写请求成功后失去该操作资格，又用原请求标识重试
- **THEN** 拒绝请求，不返回之前成功回执或事件详情

#### Scenario: 无权访问不存在的员工关联
- **WHEN** 无资格主体提交目标标识，无论目标是否存在
- **THEN** 均在目标及平台查询前拒绝，不能通过结果差异判断员工关联或离职存在性

### Requirement: 新权限迁移必须兼顾存量管理员与撤权持久性

本次迁移 SHALL 对迁移当时已有的 ROLE_ADMIN 一次性赋予四项新权限，空库初始化使用完整权限目录。迁移后的普通启动、重启或角色加载 MUST 不恢复被管理员撤销的权限；新 code 不得由旧节点以未知权限继续运行。新增权限本身不自动登记应急管理员或员工映射。

#### Scenario: 存量系统升级
- **WHEN** 系统首次执行包含生命周期权限的迁移
- **THEN** 当时已有管理员角色得到四项新 code，其他角色不被自动扩权，账号不被自动纳管或登记为应急保障

#### Scenario: 撤销新权限后重启
- **WHEN** 管理员合法撤销其中某项权限并重启新版本
- **THEN** 撤销继续生效，系统不以默认管理员目录为由补回该绑定

#### Scenario: 空库引导与旧节点排空
- **WHEN** 新版本在空库初始化，或已有系统发布新增权限目录
- **THEN** 空库按完整目录引导首个管理员；已有系统先排空不识别新权限的旧节点，再按协调方案承接流量

### Requirement: 知识问题单必须具有独立精确功能资格

服务端固定目录 SHALL 定义 `knowledge:gap:read`、`knowledge:gap:assign`、`knowledge:gap:handle`、`knowledge:gap:close`，分别用于统一受理读取、分派、处理和带原因关闭。四者按当前有效主体的全部持久角色权限并集精确匹配，互不蕴含；身份管理、文档管理、空间 manage、运营报表及管理员角色名称不代替。它们不授予文档、文件、私有会话或他人通知的读取权。

#### Scenario: 目录与显式授予
- **WHEN** 合格角色读取者查询权限目录，或普通角色被显式绑定 handle
- **THEN** 目录返回四项准确用途，普通角色的有效持有者进入合格处理候选范围，但不能枚举全局问题或读取他人私有会话

#### Scenario: 只有读取权限
- **WHEN** 当前用户只有 read
- **THEN** 可读取统一队列，不能分派、代处理或关闭问题；原提问者自身操作另按归属规则判定

#### Scenario: 角色名称或其他管理资格
- **WHEN** 用户只有管理员角色名称、空间管理或 identity:user:read，没有对应问题单权限
- **THEN** 对应受理与处理动作拒绝，不隐式开放新页面或问题内容

### Requirement: 问题单功能资格与当前参与访问必须同时满足

问题单分派、处理和关闭 SHALL 分别核对动作所需的单项精确权限及问题当前可访问范围，不从动作权限推导全局 read。分派和关闭先核对动作资格再读取目标；处理还须为当前负责人。提问者的本人提交、补充、确认、退回方案和撤回不要求管理权限，但不能藉此处理或确认他人问题。每个新请求和匹配重放都重新鉴权，无跨请求授权快照。

#### Scenario: 写权限不授予队列
- **WHEN** 用户持有 assign 但没有 read，也不是目标提问者或合格当前负责人
- **THEN** 不能读取或分派该单；不存在与无问题访问权统一拒绝，不能枚举队列或取得旧回执

#### Scenario: 处理资格下一次请求撤销
- **WHEN** 原负责人全部角色中 handle 已撤销，且不再以其他身份获得问题访问
- **THEN** 下一次处理和匹配重放拒绝，原分派、页面、游标和回执不延续资格

#### Scenario: 分派与本人确认分离
- **WHEN** 用户有 assign 或 handle，却不是提问者
- **THEN** 不能通过其功能权限代替提问者确认解决

### Requirement: 问题分派候选必须为受控最小身份投影

对当前可访问问题持有 assign 的用户 SHALL 可按名称及有界游标检索有效、主部门有效、已完成必需改密且持有 handle 的处理候选，返回 userId 和显示标签，不要求或授予 identity:user:read。候选为当次事实，实际分派必须重新核验。候选接口不开放用户名、部门、角色、密级、SSO 或生命周期资料，不提供身份目录回退。

#### Scenario: 人员池搜索
- **WHEN** 合格分派人员以 POST 正文提交合法名称搜索、limit 和 cursor
- **THEN** 只返回当前合格的最小候选，名称不进入 URL，候选失败返回 503 而非成功空目录

#### Scenario: 候选资格变化
- **WHEN** 选择后目标账号、主部门、改密状态或 handle 变为不合格
- **THEN** 实际分派返回 409，不基于旧候选扩大权限或回显失效身份的管理资料

### Requirement: 问题单权限初始化必须一次性且保留撤权及兼容边界

首次迁移 SHALL 向当时已有 ROLE_ADMIN 一次性绑定四项知识问题单权限，其他角色不隐式获权；空库正式引导新管理员角色时纳入完整目录。普通重启、重复引导和角色加载不恢复已撤销绑定。新增绑定前排空不认识权限目录的旧 app，保留未知 code 拒绝启动规则，不以删除绑定或忽略未知项实现回退；不调整任何文档 ACL。

#### Scenario: 首次升级与空库引导
- **WHEN** 已有管理员首次升级，或空库随后正式引导创建管理员
- **THEN** 对应角色获得持久精确绑定，其他角色及全部资源授权不变；运行时不依据 ROLE_ADMIN 名称放行

#### Scenario: 撤销并重启
- **WHEN** 管理方撤销其中某项权限后重启或重复执行引导
- **THEN** 该权限保持撤销，不因目录默认值自动恢复

#### Scenario: 旧实例启动
- **WHEN** 不认识新权限的旧 app 在新绑定存在时启动
- **THEN** 仍拒绝启动，不宣称新旧实例可安全混部或直接回退
